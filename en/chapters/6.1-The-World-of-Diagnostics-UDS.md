# 6.1 The World of Diagnostics: UDS

## Talking machine

1965, Detroit. A V8-engined car was towed into the repair shop due to intermittent loss of power. When the maintenance technician opened the hood, what he faced was not a fault code, but a completely silent metal lump. Replacing the distributor cap won't work. Adjusting the carburetor mixture ratio doesn't work. On the third day of disassembly, I removed the entire intake system and found a hairline crack on the manifold gasket that only appears when it expands due to heat expansion.

Diagnosis time: two weeks. The only way is to dismantle, look, try and guess.

Fifty years later, a car fire was detected on the highway. The ECU confirmed the fault within several monitoring cycles and stored DTC P0302 with complete freeze frame data. The diagnostic instrument is connected to the OBD port and sends a request. The car replied: "Cylinder No. 2 misfired. Conditions when it occurred: vehicle speed 87km/h, rotation speed 2450rpm, coolant temperature 92°C, long-term fuel correction +3.1%."

Diagnosis takes: three seconds.

This is not a matter of tools, but a matter of philosophy. The car of 1965 was a system that did just that: it performed a function but never explained itself. Today's car is a system that speaks and acts: it has built-in the ability to describe itself. UDS (Unified Diagnostic Services, ISO 14229) is the syntax of this language.

---

## The posture of diagnosis: not “dismantle”, but “ask”

All complex systems have two ways of being.

The first type: you can only do it, but you can’t say it. It performs functionality but never interprets state. When something goes wrong, you can only observe from the outside, guess, and dismantle it layer by layer. You are like an archaeologist facing ancient artifacts, inferring the internal structure based on external traces.

The second type: Not only can it be done, but it can also be said. It has built-in self-monitoring loops. Every abnormal condition is logged proactively. Every internal state it wants to make public. When it goes wrong, it doesn't need to be dissected. It tells you what's wrong, when it started to go wrong, and what contextual data it comes with.

UDS defines the language for the second system.

In this language, the diagnostic tool asks the ECU "What is your software version?" and the ECU replies with the version byte. The diagnostic tool asks "Report all the currently detected fault codes", and the ECU returns each DTC and its status one by one. The diagnostic tool said to the brake ECU, "Activate your ABS pump for two seconds. I want to test the hydraulic circuit." The brake ECU pump turned on for two seconds and then replied, "Executed, hydraulic pressure is normal."

There is a whole protocol stack behind this: the UDS application layer defines "what to ask" and "how to ask", the ISO 15765-2 transport layer is responsible for splitting the long reply into CAN frames and coordinating the sending and receiving between multiple frames, and the CAN data link layer and differential physical layer are responsible for the actual transmission of bits. This set of details has been exhausted in the layered analysis of the diagnostic protocol stack in the companion volume ["UDS Technical Book"] (https://github.com/Lularible/uds-book).

Here you just need to see **why**. Why did humans create diagnostic protocols? Because the more complex a system is, the less it can be repaired by "taking it apart and taking a look." When a car has 100 ECUs, it is impossible to dismantle all 100 ECUs and test each one individually. The man-hours are sky-high, and the disassembled ECUs need to be recalibrated, reconfigured, and re-safety-checked. The only way to solve this problem is to let each ECU learn to speak on its own.

## The core of the diagnostic protocol stack: how DCM distributes requests

After the UDS request reaches the ECU, the first one to handle it is **DCM (Diagnostic Communication Manager)**. DCM's role is similar to that of the network's HTTP server. It receives the request, parses the service ID, and distributes it to the corresponding processing function.

A minimalist DCM distributor implementation:

```c
/* DCM_ServiceDispatcher.c, simplified diagnostic communication manager */

#define UDS_SID_DIAGNOSTIC_SESSION_CONTROL  0x10
#define UDS_SID_ECU_RESET                    0x11
#define UDS_SID_READ_DATA_BY_IDENTIFIER      0x22
#define UDS_SID_READ_DTC_INFORMATION         0x19
#define UDS_SID_SECURITY_ACCESS              0x27
#define UDS_SID_CLEAR_DIAGNOSTIC_INFORMATION  0x14
#define UDS_SID_ROUTINE_CONTROL              0x31
#define UDS_SID_TESTER_PRESENT               0x3E

typedef enum {
    DCM_SESSION_DEFAULT  = 0x01,
    DCM_SESSION_PROGRAMMING = 0x02,
    DCM_SESSION_EXTENDED = 0x03,
} Dcm_SessionType;

static Dcm_SessionType g_current_session = DCM_SESSION_DEFAULT;
static uint8_t g_security_level = 0;  /* 0=locked, 1=unlocked */

/* UDS negative response code */
#define NRC_SERVICE_NOT_SUPPORTED     0x11
#define NRC_CONDITIONS_NOT_CORRECT    0x22
#define NRC_SECURITY_ACCESS_DENIED    0x33

void Dcm_ProcessRequest(const uint8_t *req, uint16_t req_len,
                         uint8_t *resp, uint16_t *resp_len)
{
    uint8_t sid = req[0];

    /* First check whether the diagnostic instrument is "alive" and refresh the session timeout */
    Dcm_ResetSessionTimer();

    switch (sid) {
    case UDS_SID_DIAGNOSTIC_SESSION_CONTROL:
        Dcm_HandleSessionControl(req, req_len, resp, resp_len);
        break;

    case UDS_SID_READ_DATA_BY_IDENTIFIER:
        Dcm_HandleReadDataById(req, req_len, resp, resp_len);
        break;

    case UDS_SID_READ_DTC_INFORMATION:
        Dcm_HandleReadDTC(req, req_len, resp, resp_len);
        break;

    case UDS_SID_SECURITY_ACCESS:
        Dcm_HandleSecurityAccess(req, req_len, resp, resp_len);
        break;

    case UDS_SID_CLEAR_DIAGNOSTIC_INFORMATION:
        Dcm_HandleClearDTC(req, req_len, resp, resp_len);
        break;

    case UDS_SID_ROUTINE_CONTROL:
        Dcm_HandleRoutineControl(req, req_len, resp, resp_len);
        break;

    case UDS_SID_TESTER_PRESENT:
        Dcm_HandleTesterPresent(req, req_len, resp, resp_len);
        break;

    case UDS_SID_ECU_RESET:
        Dcm_HandleEcuReset(req, req_len, resp, resp_len);
        break;

    default:
        /* Unsupported service, returns negative response */
        resp[0] = 0x7f;  /* Negative response SID */
        resp[1] = sid;
        resp[2] = NRC_SERVICE_NOT_SUPPORTED;
        *resp_len = 3;
        break;
    }
}

void Dcm_HandleSessionControl(const uint8_t *req, uint16_t req_len,
                               uint8_t *resp, uint16_t *resp_len)
{
    uint8_t new_session = req[1];

    switch (new_session) {
    case DCM_SESSION_DEFAULT:
        g_current_session = DCM_SESSION_DEFAULT;
        g_security_level = 0;  /* Back to default session → Automatically lock secure access */
        resp[0] = 0x50;  /* Positive response SID = request SID + 0x40 */
        resp[1] = new_session;
        *resp_len = 2;
        break;

    case DCM_SESSION_EXTENDED:
        g_current_session = new_session;
        resp[0] = 0x50;
        resp[1] = new_session;
        *resp_len = 2;
        break;

    // In production code, g_security_level >= 1 should be checked here before allowing entry into the programming session
    case DCM_SESSION_PROGRAMMING:
        g_current_session = new_session;
        resp[0] = 0x50;
        resp[1] = new_session;
        *resp_len = 2;
        break;

    default:
        resp[0] = 0x7f;
        resp[1] = UDS_SID_DIAGNOSTIC_SESSION_CONTROL;
        resp[2] = NRC_CONDITIONS_NOT_CORRECT;
        *resp_len = 3;
        break;
    }
}

/* Session timeout timer, if TesterPresent is not received within 5 seconds, it will automatically return to the default session */
void Dcm_ResetSessionTimer(void)
{
    g_session_timer = DCM_SESSION_TIMEOUT_MS;
}

void Dcm_SessionTimer_Tick(void)
{
    if (g_session_timer > 0) {
        g_session_timer--;
        if (g_session_timer == 0) {
            /* Session times out and returns to default */
            g_current_session = DCM_SESSION_DEFAULT;
            g_security_level = 0;
        }
    }
}
```

DCM is not complicated, it is just a lookup table that maps service IDs to processing functions. The complexity of the entire UDS protocol does not lie in the DCM itself, but within each service processing function, as well as the lower-level modules called by these processing functions (such as DEM's management of DTC).

## Three levels of diagnosis: look, act, and modify

Diagnosis is not a single operation, it has three levels.

**Read. ** The diagnostic tool can read various information of the ECU: software version, hardware number, fault code, sensor real-time value, communication counter. This is "let the system report itself". No permissions are required. Any diagnostic tool can ask any ECU "Who are you?" The corresponding UDS services are 0x22 (ReadDataByIdentifier) ​​and 0x19 (ReadDTCInformation).

**control. ** The diagnostic tool can activate the ECU's actuators: let the ABS pump run briefly, let the air conditioning fan start, let a certain injector spray. This is "making the system act according to your requirements." The corresponding UDS service is 0x31 (RoutineControl): the diagnostic instrument says "Execute routine 0x0201 (activate ABS pump for 100ms)", and the ECU returns the result after execution.

**Write. ** The diagnostic tool can write calibration data to the ECU: update engine map, modify sensor thresholds, and flash new firmware. This is "changing the behavior of the system". The corresponding services are 0x2E (WriteDataByIdentifier), 0x34/0x36/0x37 (RequestDownload/TransferData/RequestTransferExit).

The philosophy of the first two levels is: the system actively exposes itself to help maintainers locate faults faster.  The third level is a different story: you give the maintainer the power to modify the system, but this requires a lock.

## Secure Access: Who gave you the authority to write?

When the ECU leaves the factory, a key is stored inside its HSM. This key never leaves the HSM: the main CPU can request the HSM to use this key for encryption operations, but the main CPU cannot read the value of the key itself.

When the diagnostic tool needs to perform a write operation, the ECU will not directly agree. It requires the diagnostic tool to prove that it knows this key:

```
Tester ECU
    |                                      |
    |  Request Seed (0x27 0x01)            |
    |  ─────────────────────────────────>    |
    | | Generate random number Seed (4 bytes)
    |  Seed: 0x5A8F_3C21                   |
    |  <─────────────────────────────────    |
    |                                      |
    |  Key = AES(Seed, SecretKey)           |
    | Intercept the first 4 bytes |
    |                                      |
    |  Send Key (0x27 0x02, key)           |
    |  ─────────────────────────────────>    |
    | | HSM recalculates Key'
    |                                      |  Key == Key' ?
    | | Match → Unlock Security Level 1
    |  Positive Response                    |
    |  <─────────────────────────────────    |
```

The core design principle of Challenge-Response: **Keys are never transmitted on the bus. ** The seed is a random number each time, and the key is different each time. Even if the attacker records all communications, he cannot extract the key or replay it with the recorded key because the next time the seed will be different.

If the wrong key is sent continuously, for example three times, the ECU will enter the "Secure Access Delay" state and reject further unlocking attempts before the delay timer (the duration is configured by the OEM) expires. This is a measure against brute force attacks.

After successful unlocking, the diagnostic tool enters **Programming Session** or **Extended Session** to obtain write permission. After execution, exit to the default session and write permission is turned off. If there is no communication from the diagnostic tool within the specified time (usually 5 seconds), the ECU automatically returns to the default session. This is the "people go behind closed doors" strategy.

**The session is the door and secure access is the key. ** If the diagnostic tool wants to enter the door, it must first use the key to prove its identity, and then complete the task before the door closes.

## Diagnose session state machine

Diagnostic sessions are not a simple "default/programmed" choice. It is a complete state machine:

```
                          ┌──────────────┐
         Power-on/Reset        │              │
    ┌──────────────────→ │  Default     │←──────────────┐
    │                     │  (0x01)      │               │
    │                     │              │               │
    │                     └──────┬───────┘               │
    │                            │                       │
    │                   0x10 0x03                        │ 0x10 0x01
    │                            │                       │ (return to default)
    │                            ↓                       │
    │                     ┌──────────────┐               │
    │                     │  Extended     │───────────────┤
    │                     │  (0x03)      │               │
    │                     │              │               │
    │                     └──────┬───────┘               │
    │                            │                       │
    │                   0x10 0x02                        │ 0x10 0x01
    │                            │                       │
    │                            ↓                       │
    │                     ┌──────────────┐               │
    │                     │  Programming     │───────────────┘
    │                     │  (0x02)      │
    │                     │              │
    │                     └──────────────┘
    │                            │
    └────────────────────────────┘
              ECU reset (0x11 0x01)
```

- **Default Session (0x01)**: Read-only permissions. Read DID, Read DTC, TesterPresent. No write permission.
- **Extended Session (0x03)**: Read and write permissions. Calibration data can be written and routine control can be executed. Requires security access unlock to write.
- **Programming Session (0x02)**: Highest authority. Allow firmware flashing (RequestDownload). This usually requires security access in an extended session.

In many OEM's diagnostic strategies, you cannot jump directly from the default session to the programming session. A typical approach is: Default Session → Extended Session → Security Access Unlock → Programming Session. This is not a mandatory requirement of ISO 14229-1, but an additional protection implemented by OEMs through session security policies to ensure that attackers cannot gain write access without bypassing security access.

## DTC life: it is not a boolean value

Beginners think that DTC is the "fault/no fault" flag, but this understanding is not accurate.A DTC has a complete life cycle. It is not "the light is on because it is detected", but a finite state machine managed by DEM (Diagnostic Event Manager).

Let's see how DEM tracks the status of a DTC:

```c
/* DEM_DTCStatus.c, diagnostic event manager: DTC status byte management */

/* Bit definition in DTC status byte (UDS bit numbering) */
#define DTC_BIT_TEST_FAILED 0x01 /* bit 0: This test failed */
#define DTC_BIT_TEST_FAILED_THIS_OP 0x02 /* bit 1: This operation cycle failed */
#define DTC_BIT_PENDING_DTC 0x04 /* bit 2: DTC to be confirmed */
#define DTC_BIT_CONFIRMED_DTC 0x08 /* bit 3: DTC confirmed */
#define DTC_BIT_TEST_NOT_COMPLETE_SINCE_CLEAR  0x10 /* bit 4 */
#define DTC_BIT_TEST_FAILED_SINCE_CLEAR        0x20 /* bit 5 */
#define DTC_BIT_TEST_NOT_COMPLETE_THIS_OP      0x40 /* bit 6 */
#define DTC_BIT_WARNING_INDICATOR_REQUESTED    0x80 /* bit 7 */

typedef struct {
    uint32_t dtc_code;          /* Such as 0x030200 = P0302 */
    uint8_t  status;            /* DTC status byte */
    uint8_t  fault_counter;     /* Fault confirmation counter */
    uint8_t  aging_counter;     /* Aging counter */
    uint8_t  healing_counter;   /* Self-healing counter */
    uint32_t occurrence_count;  /* Cumulative number of occurrences */
    uint32_t freeze_frame_data[4]; /* freeze frame snapshot */
} Dem_DTCRecord_t;

static Dem_DTCRecord_t g_dtc_table[MAX_DTC_COUNT];

/* The SWC monitoring function calls this API to report fault events */
void Dem_SetEventStatus(uint32_t dtc_code, uint8_t event_status)
{
    Dem_DTCRecord_t *dtc = Dem_FindOrCreateDTC(dtc_code);
    if (!dtc) return;

    /* The results of this test */
    if (event_status == DEM_EVENT_FAILED) {
        dtc->status |= DTC_BIT_TEST_FAILED;
        dtc->status |= DTC_BIT_TEST_FAILED_THIS_OP;
        dtc->status |= DTC_BIT_TEST_FAILED_SINCE_CLEAR;
        dtc->fault_counter++;

        /* Confirmation logic: Fault detected for N consecutive operating cycles → Confirm DTC */
        if (dtc->fault_counter >= DEM_CONFIRMATION_THRESHOLD) {
            dtc->status |= DTC_BIT_CONFIRMED_DTC;
            dtc->status &= ~DTC_BIT_PENDING_DTC;
            dtc->aging_counter = 0;

            /* Write to non-volatile storage, DTC is permanently recorded */
            NvM_WriteBlock(NVM_DTC_BLOCK_ID, g_dtc_table);

            /* If you need to light up the MIL lamp */
            if (Dem_IsEmissionRelated(dtc_code)) {
                dtc->status |= DTC_BIT_WARNING_INDICATOR_REQUESTED;
            }

            /* Save the freeze frame, the environment snapshot when first confirmed */
            if (dtc->occurrence_count == 0) {
                Dem_CaptureFreezeFrame(dtc);
            }
            dtc->occurrence_count++;
        } else if (dtc->fault_counter >= DEM_PENDING_THRESHOLD) {
            /* Not yet confirmed, marked as pending */
            dtc->status |= DTC_BIT_PENDING_DTC;
        }
    } else if (event_status == DEM_EVENT_PASSED) {
        dtc->status &= ~DTC_BIT_TEST_FAILED;
        dtc->status &= ~DTC_BIT_PENDING_DTC;

        /* Aging logic: N consecutive cycles passed → Clear confirmation status */
        if (dtc->status & DTC_BIT_CONFIRMED_DTC) {
            dtc->aging_counter++;
            if (dtc->aging_counter >= DEM_AGING_THRESHOLD) {
                dtc->status &= ~DTC_BIT_CONFIRMED_DTC;
            }
        }

        /* Self-healing */
        if (dtc->fault_counter > 0) {
            dtc->healing_counter++;
            if (dtc->healing_counter >= DEM_HEALING_THRESHOLD) {
                dtc->fault_counter = 0;
                dtc->healing_counter = 0;
                dtc->status &= ~DTC_BIT_TEST_FAILED_THIS_OP;
            }
        }
    }
}
```

The complete timeline of this DTC state machine is as follows:

```
Operation cycle 1: Fault detected → TestFailed=1, TestFailedThisOp=1, faultCounter=1
Operation cycle 2: Fault detected → faultCounter=2, PendingDTC=1
Operation cycle 3: Fault detected → faultCounter=3, ConfirmedDTC=1, PendingDTC=0
           → Write to NVM, capture freeze frame, MIL light may be on
Operation cycle 4: Pass detected → TestFailed=0, agingCounter=1
Operation cycle 5: Pass detected → agingCounter=2
...
Operation cycle 43: Pass detected → agingCounter=40 (threshold reached)
           → ConfirmedDTC=0 (DTC changes from "Confirmed" to "aged out")
           → but occurrenceCount is not zero, so the technician can still see"This DTC happened in history"
```

**After a fault occurs, it needs to be confirmed for 3 consecutive monitoring cycles before it becomes a "real fault". This is to filter out occasional voltage glitches, poor contacts, and transient EMI. ** After a fault disappears, it requires 40 consecutive monitoring cycles before it is automatically cleared. This is to prevent intermittent faults from being considered "already resolved". 3 cycles for confirmation and 40 cycles for clearing. These figures are not randomly determined. They are the result of the OEM weighing "no omissions" and "no false positives" based on years of after-sales data.

## Penetration: from a DTC status bit to an electron in Flash

**Bit 3 (ConfirmedDTC) of a DTC status byte flips from 0 to 1. Physically, this is a bit in Flash that completes the programming operation in tens of microseconds. **

Let's penetrate this moment.

Top level: `dtc->status |= DTC_BIT_CONFIRMED_DTC`, a bitwise OR in C language code.

One level down: the compiler generates `LDRB R0,[R1]; ORR R0,#0x08; STRB R0,[R1]`, a byte loaded from SRAM, ORed with 0x08, written back.

Next level: `NvM_WriteBlock()` writes the entire DTC table to Flash. The Flash controller receives the command: "Write 64 bytes to the sector at address 0x0801E000".

One level down: the Flash controller starts an internal state machine. The charge pump boosts VDD (3.3V) to the programming voltage (approximately 10V). The channel hot electrons of the NOR Flash cell are injected into the floating gate under high voltage. The negative charge accumulated in the floating gate changes the threshold voltage of the cell transistor from the "erased state" (reading as 1) to the "programmed state" (reading as 0).

One level down: Several cells in the sector have been programmed at the physical location corresponding to bit 3. This 0 is the **physical existence** of ConfirmedDTC in non-volatile storage. It is not a logical value recorded by the software, but a group of electrons trapped in the silicon dioxide layer that affects the switching behavior of the transistor.

**The reason why DTC can still exist after power outage is not because there is software to save it for you, but because these electrons are physically trapped in the floating gate. ** A floating gate is an island of polysilicon surrounded by a layer of silicon dioxide, giving electrons nowhere to escape. Unless you let it leak naturally at a high enough temperature (data retained for 20 years), or you apply a high voltage erase pulse to pull them away through Fowler-Nordheim tunneling (sector erase).

From a yellow MIL light on the dashboard, to electrons trapped in a NOR Flash floating gate. Diagnostics connect every layer of the car from the human-machine interface to the physical structure of the silicon wafer. This is "penetration", you don't just look at the superficial fault phenomenon, you follow the causal chain all the way back to the physical root.

## Engineer’s letter to the future

A good diagnostic system designer is not writing code, he is writing a letter.

The recipient of the letter is the maintenance technician who will be helpless with this car ten years later, the next generation of engineers who will take over the maintenance of this code, and the self who one day in the future has forgotten his original design ideas.

Every time you define a DID: "This data identifier 0xF190 reads the coolant temperature", you are telling future people: "When the system behaves abnormally here, think about the temperature sensor." Every time you configure a DTC confirmation threshold: "It must fail for 3 consecutive monitoring cycles before it is confirmed as a real fault." You are balancing "no missed negatives" and "no false positives", and you are making a trade-off decision for future people. Every time you write a test routine for a RoutineControl: "Activate the ABS pump for 2 seconds and then read the pressure sensor," you are preparing an automated troubleshooting path for future people.Service technicians in 1965 could only take the engine apart because the car was never designed to "let the machine describe itself." That manifold crack was an engineering flaw, but silent metal can't tell itself.

**Diagnosis is the baton handed over by engineers. **

Every DTC and every line of troubleshooting code you write is a baton passed to the future. The person who takes the baton may be a maintenance technician in a certain 4S store 10 years from now. He has never met you, but the diagnostic logic you left behind will speak the moment he connects the OBD port. You are not present, but your engineering judgment is.


While diagnostics can identify problems, it doesn't prevent someone from deliberately causing them.

The diagnostic tool can read fault codes and write calibration data. If an attacker can gain access through security, or bypass security access, he can override the behavior of the ECU. In 2015, two security researchers remotely controlled a Jeep Cherokee on the highway. They didn't go through the diagnostic protocol. They took the infotainment system's Internet portal and entered the car's CAN network, a broadcast network with no authentication mechanism. They directly faked the CAN frames of "brake release", "full throttle", and "steering wheel locked".

**Diagnosis is the letter you leave to future repairers, and security is the letter you prevent attackers from opening. **

## Summary

Today we did one thing: **Understand that diagnosis is not "reading a fault code", but a letter written by engineers across time to the future, penetrating every layer of abstraction from the human-machine interface to the physical structure of the silicon wafer. **

Key takeaways:
1. **DTC is a state machine with a life cycle**: from "fault detected in the current operation cycle", to "confirmed for N consecutive cycles", to "written to non-volatile storage" to cleared, each state transition has a clear engineering trade-off (sensitivity vs false alarm rate).
2. **Diagnosis is a letter written by engineers to future maintainers**: Every DID definition, every confirmation threshold, and every RoutineControl test routine you write is laying an automated troubleshooting path for the maintenance technicians who will repair this car 10 years later. You are not present, but your engineering judgment is.
3. **From the dashboard MIL light to the trapped electrons in the NOR Flash floating gate, diagnostics connects every layer of this physical causal chain**: `dtc->status |= DTC_BIT_CONFIRMED_DTC` ultimately becomes trapped charges in the floating gate. It is not lost when power is turned off, not because of software, but because of physics.

Diagnostics can identify problems, but they can't prevent someone from deliberately creating them.
