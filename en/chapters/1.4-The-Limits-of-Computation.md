# 1.4 The Limits of Computation

## An impossible KPI

You are an engineer at an auto parts factory. The boss has given you a request:

"Write a program that will read the source code of another program and then automatically determine whether this program will run away."

"Running away" means: Will the program enter an infinite loop? Will it access the null pointer? Will the stack explode under certain input? Will priority inversion occur in interrupt nesting and cause deadlock?

After you received this task, you thought about it for three days and three nights, and then you went to your boss and said, "I can't write this program."

The boss was stunned: "Why?"

"It's not because I'm not capable. It's because it's **mathematically impossible**."

## Halting problem: Turing’s second shock

In his 1936 paper, Turing not only invented the Turing machine, but also proved a world-shaking conclusion:

**There is no universal algorithm that can determine whether any program will eventually stop on any input. **

This is the Halting Problem.

The core idea of ​​the proof is extremely elegant, and is exactly the same as Gödel: **Construct a self-referential paradox**.

Suppose there is a Turing machine H that reads the code of "program P" and the code of "input I" and outputs either 1 (P will halt on I) or 0 (never halt).

Now we construct a "trick-or-treat" Turing machine D. The behavior of D is simple, it receives a program P (encoding) and then:

```
Internal logic of D:

1. Call H(P, P)
   → Ask H:"Will program P with P as input stop?"

2. If H returns 1 (will stop):
   → D enters an infinite loop (never stops)

3. If H returns 0 (no shutdown):
   → D Stop immediately
```

Now, let’s ask the fatal question: Will D(D) shut down?  That is: feed D's own encoding as input to D and ask it what will happen.

| Hypothesis | Reasoning | Conclusion |
|------|------|------|
| D(D) will stop | Then H(D,D) returns 1 | D enters an infinite loop → **Contradiction** |
| D(D) will not stop | Then H(D,D) returns 0 | D will stop immediately → **Contradiction** |

In either case, it is a contradiction. So **H cannot exist**.

The beauty of this proof is that D does not require any complex attack on H. It simply calls H honestly and then honestly acts contrary to H's prejudgment. The contradiction does not come from "malice", but from "self-reference."  Gödel constructed "a proposition that says 'I am not provable'", and Turing constructed a "program that asks 'will I stop'", with exactly the same structure. The two papers were published only 5 years apart, but together they define the fact that any sufficiently powerful formal system (or computational model) cannot escape the shadow of the self-referential paradox.

## Rice's Theorem: Not just "halting" - all non-trivial properties

Downtime issues are just the tip of the iceberg.

In 1953, Henry Gordon Rice proved a theorem that drove all programmers to despair.

**Rice's theorem says: For any non-trivial semantic attribute of a program, there is no general algorithm that can determine whether the program has this attribute. **

What is "non-trivial"? It is an attribute that "not all programs have, and not all programs have". For example:

- "Will this program access the null pointer?": Some programs will, some won't → non-trivial → undecidable.
- "Will this program print 'hello' on line 42?": non-trivial → undecidable.
- "When this program is run, will the value of variable x appear to be greater than 1000?": non-trivial → undecidable.
- "When this program reaches function foo(), does the stack pointer exceed the stack space?": non-trivial → undecidable.

Note: These properties are what you really want to know in daily development. But Rice's theorem says: There is no program that can help you determine these attributes automatically, correctly, and without omissions. 

Rice's theorem is a surprising generalization of the halting problem. The halting problem says "you can't automatically tell whether a program will halt", and Rice says "you can't automatically tell any non-trivial semantic properties of a program".This explains why coding standards such as MISRA C, CERT C, and AUTOSAR C++14 prohibit so many things: recursion, goto, dynamic memory allocation, function pointers, variable-length arrays, type puns on unions. These constraints don't limit your programming freedom; they remove language features that make program properties undecidable. You remove recursion and the stack depth becomes statically analyzable. You remove dynamic memory allocation and memory leaks become impossible. You delete the function pointers and the control flow graph becomes completely static.

**Behind every "you don't" is a verdict of Rice's theorem. **

## Busy Beaver Carnival: Knowing it exists but never figuring it out

The halting problem is not the only example that reveals the boundaries of computing. There is also a more intuitive one: **Busy Beaver** (Busy Beaver).

In 1962, the Hungarian mathematician Tibor Radó proposed a brilliant thought experiment. Consider all Turing machines with n states (not counting halting states) that eventually halt. Among these Turing machines, there was the "hardest" one, which wrote the most 1's on the tape before shutting down. This "number at most 1" is BB(n).

How fast does the BB function grow:

```
BB(1) = 1 (A Turing machine with 1 state can only write at most 1 1 and then stop)
BB(2) = 4 (4 ones)
BB(3) = 6 (6 ones)
BB(4) = 13 (13 ones)
BB(5) = 47,176,870 (to be determined in 2024)
BB(6) ≥ 10↑↑15 (The exact value is unknown, but it is at least this large. This number is too large to be written down in regular notation and far exceeds the total number of atoms in the universe)
```

Note: BB is a well-defined function: for every n, BB(n) is a definite value. Since the total number of candidate Turing machines is finite (albeit very large), you can enumerate all n-state Turing machines, check which ones will halt, count their outputs, and take the maximum. **BB(n) definitely exists and is definitely unique. **

But can you calculate it?

cannot. Lado proved: **BB function is not computable. There is no universal algorithm that takes n as input and outputs BB(n). ** The reason is short: if it exists, the value of the BB function can be used to determine shutdown. And the downtime issue has proven this is impossible.

**The BB function is the simplest "well-defined but not computed" function known to man. ** It defines the boundaries of "computability": not all well-defined mathematical objects can be evaluated algorithmically. For some questions, even questions as simple as "How many 1's can be written at most with an n-state Turing machine?" Although the answer exists, the path to the answer is blocked by the self-referential paradox jointly created by Gödel and Turing.

## P and NP: Immovable traps

The Halting Problem and Busy Beaver are undecidable and mathematically impossible. But there is another type of problem: **It is solvable in theory, but "cannot be calculated" in practice. **

This is the P versus NP problem.

P (Polynomial time) is a problem that can be solved by an algorithm in polynomial time. "Polynomial time": O(n), O(n²), O(n³), O(n log n), all OK. As the size of the problem increases, the computational growth is "controllable" (relatively speaking).

NP (Nondeterministic Polynomial time) are those problems where "if you guess the answer correctly, you can verify it in polynomial time to see if it is correct."

P means "can find the answer" and NP means "can verify the answer". **P = NP? ** This is one of the seven major mathematical puzzles of the millennium, with a reward of one million US dollars, and it remains unsolved.

But engineers’ intuition tells us: **P ≠ NP. ** Otherwise, bank encryption, HTTPS certificates, digital signatures, all these technologies that rely on "some problems are hard to solve" will collapse overnight. If P = NP, breaking RSA encryption is as difficult as solving an anagram.

**What is a typical NP-hard problem for automotive engineers? ****Optimal wiring harness layout. ** You need to route power lines, CAN bus, and sensor signal lines on the vehicle body with the shortest overall length and lightest weight. Cross wiring is not allowed, avoid high-temperature areas (near the exhaust pipe), and avoid sources of electromagnetic interference. This is a variation of the Traveling Salesperson Problem (TSP). The search space of TSP is n! level. At 30 connection points, the number of possible path combinations is approximately 10³², which is more than the stars in the universe. Optimizing it requires heuristic algorithms, genetic algorithms, simulated annealing, not a perfect solution, but "good enough".

**Network topology design of ECU. ** In the in-vehicle network, the problem of which ECUs are hung on CAN A, which are hung on CAN B, which are hung on FlexRay (high-speed deterministic bus), and which are hung on LIN (the block partitioning problem of "minimizing gateway forwarding delay + minimizing bus load") is NP-hard. Automotive network architects spend months designing a topology, essentially making engineering compromises in a space that cannot be brute force searched.

**NP Hard problems are immovable traps. ** The halting problem is "undecidable" and there is no algorithm at all. NP problems are "decidable". But the algorithm that exists is not finished until you die. The engineering consequences of both are the same: **You'll never get a perfect solution, you have to compromise. **

## From undecidable to decidable: Engineer’s “dimensionality reduction attack”

Since the halting problem and Rice's theorem declare that "perfect automated analysis is impossible," how do we ensure the safety of automotive software?

The answer is: **Change the question. **

We are not trying to prove the "arbitrary nature of any program", that is Rice's forbidden area. Our strategy is:

**Strategy 1: Constrain the language and reduce the problem space. **

You are not using the full C23 feature set. You use MISRA C: recursion is prohibited, dynamic memory allocation is prohibited, and goto jumps are prohibited. This is equivalent to drawing a rectangle in the universe of "all possible C programs", and the program properties within the rectangle are decidable. What you pay for is "programming freedom" in exchange for "analytic certainty."

**Strategy 2: Constrain hardware and shut out physical uncertainty. **

WCET (Worst Worst Execution Time) is theoretically undecidable when analyzed accurately on modern CPUs because of cache, branch prediction, pipelines, and out-of-order execution. But on automotive ASIL D level ECUs, you can lock the instruction cache and data cache (cache locking), raise the interrupt priority of critical tasks to the highest level and turn off preemption, turning off the branch predictor. In this way, the execution time of the instruction becomes a certain value, LDR is 2 cycles, and STR is 2 cycles. You re-squeeze the physical world into a "well-determined" subset.

**Strategy 3: Use guards instead of proofs. **

You don't prove "this program will not run away", you write an independent watchdog timer. The program kicks it in the main loop every cycle. If the program runs away, enters an infinite loop, or explodes the stack, the watchdog times out, the hardware is reset, and the system enters the safe state. You don't need to prove "not running away", you just need to "recover when running away".

**Strategy 4: Use sampling instead of exhaustion. **

You don't test all possible input combinations because the input space is too large. You design equivalence classes, boundary values, worst-case scenarios. The testing methodology of ISO 26262 from Part 6 to Part 11 is all about this. You don't swim in an infinite ocean of input, you shrink the ocean into a swimmable swimming pool, and then ensure that every branch of your program is covered in this pool.

## Stop determination in bounded environment: code demonstration

To help you build intuition, here is a Python program. It determines in **limited steps** (1 million steps) whether a (specific, extremely simplified) program will halt. Note that this is not "the halting problem is solved", this is "in a clearly drawn circle, the halting problem is decidable":

```python
def bounded_halt_check(prog, input_val, max_steps=1000000):
    """
    Within max_steps steps, determine whether prog(input_val) stops.
    If max_steps was stopped before, return (True, number of steps).
    If it exceeds max_steps and has not stopped, return (False, max_steps).

    This is not a general halt arbiter, it has a max_steps upper limit.
    But for the ECU, this is what we need: before the 10ms deadline,
    Can this task be completed?
    """
    ip = 0 #Instruction pointer
acc = input_val # Accumulator
    steps = 0

    while ip < len(prog) and steps < max_steps:
        op = prog[ip]
        if op == "INC":
            acc += 1
            ip += 1
        elif op == "DEC_JZ":
            if acc == 0:
                ip += 2
            else:
                acc -= 1
                ip += 1
        elif op == "HALT":
            return (True, steps)
        else:
            ip += 1
        steps += 1

    if steps >= max_steps:
        return (False, max_steps) # Timeout, not sure if it is really an infinite loop
    return (True, steps)

# Test: A program that counts to 10 and then halts
prog = ["INC"] * 10 + ["HALT"]
print(bounded_halt_check(prog, 0, 100))  # (True, 10)
```What does this code do? It rewrites the original halting problem ("determine in infinite steps") into a bounded halting problem ("determine in N steps"). The bounded version is **decidable** because you only need to perform at most N steps.

**This is the watchdog principle on the ECU. **Watchdog does not prove that the program will not loop endlessly. It only limits the time limit: I give you 10ms and you kick me once. "You don't kick = you die = I reset you". Time constraints themselves are weapons that turn undecidable problems into decidable problems.

## Industry Practice: Walking a Tightrope on the Precipice of Computational Boundaries

Once you understand the above theories, you will be able to understand the seemingly “overly restrictive” regulations in the industry.

AUTOSAR's OS module stipulates that tasks must reach the schedule point within a limited time and cannot occupy the CPU for a long time. **This is a bounded shutdown requirement. **

Freedom From Interference (FFI) in ASIL D systems requires memory partitioning and does not allow a QM-level task to access the memory of an ASIL D task. This is a physical wall that prevents low-security programs from contaminating the data of high-security programs.  Note that if you use software to check ("if (address < boundary) ..."), the check itself may go wrong. Made with MPU (Memory Protection Unit) hardware, the CPU intercepts illegal access at the bus level, which is a layer of physical guarantee. Physics is more reliable than logic because there is no "self-referential paradox" in physics. 

The technology used by the Astrée static analyzer on the Airbus A380 and some ASIL D projects is called "Abstract Interpretation", which does not track every specific state of the program, but tracks the "abstract domain" of states. For example, the abstract state "variable x is between 0 and 100". If the abstract domain of x does not conflict with an array boundary, it proves that there is no out-of-bounds access. **This is trading "conservative approximation" for "guarantee": if Astrée says "no runtime errors", there really aren't. If it cannot determine, it will report a "possible error" for you to check manually. False positives can exist, false negatives cannot, because false negatives = safety claims are false. **

This tradeoff: allowing false positives and eliminating false negatives is the basic strategy of static analysis in the face of computational boundaries. **We do not pursue "perfect judgment". We go for the “safe side.” **

## Chip Yield and Computational Boundaries – Same Story

In the panel factory, one of my jobs is online defect inspection (Inspection). You can't check every TFT in every panel unit. You put the substrate into a scanning electron microscope, scan several areas with an electron beam with 10nm resolution, and count the defect density to calculate the yield of the entire substrate.

**Is this a “perfect” yield determination? No, it is a bounded approximation based on sampling and statistical inference. ** But it's good enough. It is enough to allow your automotive MCU to run for 15 years in an environment from -40°C to +125°C.

**This is the same as the shutdown problem tells us: perfection is not available, but good enough is. ** The definition of "good enough" is driven by engineering needs, not a mathematical definition. In the language of ISO 26262, "good enough" is called ASIL's probabilistic measurement target for random hardware failures: PMHF (Probabilistic Metric for random Hardware Failures) is less than 10 FIT. 10 FIT means fewer than 10 failures in 1 billion hours of operation, which is roughly equivalent to one failure every 11,415 years. **This number is not a mathematical guarantee, it is a confidence interval given by statistical inference. **

## Only when you know the boundaries can you know how to walk

The philosophical inspiration of the shutdown problem is: **There are some questions for which the answer does not exist. It is either "not found yet" or "never found". **

It's cruel, but it's also liberating.

You don’t beat yourself up because you can’t fix all the bugs because math says “impossible.” You don't get anxious because the test doesn't cover all the boundaries because the math says "impossible." The ISO 26262 security case in your hand, the unit tests you write, and the permissions you set for each MPU area are not "proving perfection". They are "proving that under given constraints, security is not lower than a certain threshold."

**Only when you understand boundaries can you be truly free. **

But that doesn't mean giving up. On the contrary, we know that general bug detection is not decidable, so we invented formal methods, model checking, and symbolic execution, which cannot solve everything, but can be perfect in a specific, decidable subset.

We know that shutdown is undecidable, so we invented the watchdog timer. If the program runs away, the hardware will reset it for you. You don't need to prove that it won't run away, you just need to be able to recover when it does.

We know that the precise bounds of WCET are undecidable on complex hardware, so we turn off caching, turn off branch prediction, and disable the use of shared resources in safety-critical tasks, shutting out uncertainty.

**When we face unsolvable problems, we don’t surrender, we take a sideways approach. **

Walking sideways is the most important tactical quality for engineers. Programming language designers have carved out a "safe subset" of the Turing-complete minefield: MISRA C. Hardware architects insert a "deterministic anchor" into the fog of unpredictable caches: lock caches. Compiler authors ensure "high-impedance isolation" in the out-of-order world of instruction reordering: memory barriers.

Every time I walk sideways, I find a small corner of light under the unpredictable shadows.

This is exactly what you do every day in automotive electronics: faced with physical limits: EMC interference, chip yield, temperature drift, you don't beat the laws of physics, you work around them. Add a shield, choose a wide-temperature chip, and make a redundant design.

**Knowing where the boundaries are is the first step to crossing them. **

## Your brain is also a computer, it just uses different constraints.

When discussing the boundaries of computing, a natural question is: What about the human brain? Your brain has approximately 86 billion neurons, each with an average of 7,000 synaptic connections. It does image recognition, language understanding, motion control, all of these, while consuming only about 20W. A GPU cluster training GPT-4 may consume several megawatts. Your brain not only crushes the chip on "low power consumption", it also crushes on "fault tolerance": thousands of neurons die naturally every day, but your consciousness is not affected. If a key transistor on a chip fails, the entire die may be scrapped.

But your brain also has its own "limited resources." And its limitations run deeper than the chip. Your working memory can only hold about 4-7 chunks of information at a time. You can't "memorize a million numbers" like a computer, you can only "memorize patterns." Your calculation speed is equivalent to dozens of "consciousness operations" per second. A 112MHz Cortex-M4 can do 112 million instructions per second. You are not "slower" than the chip, you are "computing" using a completely different strategy. You use pattern recognition instead of exhaustive search. You replace algorithms with experience. You use "gut feeling" to skip intermediate steps of reasoning.

Understanding the limitations of the "computer" that is your brain will give you an interesting respect for writing code yourself: you are using a "human brain" that consumes 20W, has extremely high fault tolerance, but has extremely low accuracy, to command a "chip" that consumes 100mW, has zero fault tolerance, but has extremely high accuracy. This is a conversation between two completely different "philosophies of computing."
