# 5.2 Real-Time Operating Systems

## Leaving "one person's tribe"

The world of bare metal programming is a human world. You schedule everything yourself, you manage every register yourself. This sense of absolute control is addictive, but also exhausting.

Now, imagine you leave this tribe and come to a mid-sized enterprise.

There are multiple departments running in the enterprise at the same time. R&D must deliver the drawings by 3 p.m. The quality inspection department must complete random inspections within 10 minutes after each batch of products comes off the production line. Security must patrol 24 hours a day.

You can't "do it one by one" like bare metal programming, and let the R&D department wait for the quality inspection department to finish before starting? impossible.

You need a **manager**. It is responsible for deciding which task gets the CPU at each moment, which task is suspended, and which task is preempted.

This manager is the **RTOS (Real-Time Operating System) kernel**.

---

## Scheduling table: Who runs first, who waits

The first thing RTOS does is to split the application into multiple tasks. Each task has its own stack, its own register context, and its own priority. You can imagine a schedule:

```
Priority 5 → Engine Torque Control (100μs period, hard real-time)
Priority 4 → ABS wheel speed processing (1ms cycle, hard real-time)
Priority 3 → CAN transmit queue management (soft real-time)
Priority 2 → Diagnostic UDS response (soft real-time)
Priority 1 → Background tasks (data logging, status monitoring)
```

This table is your "enterprise organization chart." Tasks with higher priority have stricter time constraints, and millisecond-level delays are absolutely unacceptable.

But priority alone is not enough. The core magic of RTOS is **preemption**.

---

## Preemption: the highest priority ready task always wins

At any time, the highest priority ready task gets the CPU. This is an iron law of RTOS scheduling.

The scene is this:

1. The low-priority diagnostic task T2 is running.
2. Suddenly, the CAN controller's receive interrupt triggers. The ISR pushes a frame of chassis message into the message queue and wakes up the high-priority ABS task T4.
3. When the ISR returns, the scheduler checks the ready queue and finds that T4 has a higher priority than T2.
4. **Seize it now. ** The register context of T2 is saved to the stack of T2, the context of T4 is restored from the stack of T4, and T4 starts running.

This process is called **bounded delay preemption**, that is, the time from readiness to execution of a high-priority task ≤ the context switch time of the scheduler. On a Cortex-M4, this is typically a few microseconds.

Let's zoom in to see what exactly happens with a context switch.

---

## Context switching under the microscope

Taking FreeRTOS on Cortex-M4 as an example (112MHz is taken from the main line S32K144), the timeline of a complete context switch:

1. SysTick interrupt trigger (or PendSV exception): **12 cycles** (interrupt latency).
2. CPU automatically pushes xPSR, PC, LR, R12, R3, R2, R1, R0: **8 words = 8 bus cycles** (when FPU is not enabled; enabling FPU will also automatically push S0-S15 and FPSCR).
3. The interrupt vector table jumps to PendSV_Handler.
4. PendSV manually pushes the remaining registers R4-R11 onto the stack: **8 words = 8 bus cycles**.
5. Save the current task stack pointer to TCB (Task Control Block).
6. Select the highest priority ready task: read the ready list head pointer (2-3 bus cycles).
7. Restore the new task stack pointer from the new TCB.
8. Pop R4-R11: **8 bus cycles**.
9. Exception return: CPU automatically pops R0-R3, R12, LR, PC, xPSR.

**Total overhead is approximately 1-2μs at Cortex-M4@112MHz. **

In a 100μs control period, this is less than 2% of the period. You spend 2% of a cycle in exchange for the ability to parallelize multiple tasks. This is an extremely good deal.

---

## Penetrating PendSV: A true compilation of context switchesFreeRTOS uses the **PendSV (Pendable System Service)** exception on Cortex-M to implement context switching. PendSV's priority is set to the lowest, which ensures that context switches never interrupt a running ISR. When the SysTick interrupt fires and finds a higher priority task ready, it doesn't switch directly, it just hangs the PendSV exception. After the SysTick ISR exits, the CPU does not execute PendSV until it exits the interrupt context and returns to the task context.

This is the PendSV_Handler assembly code for FreeRTOS (simplified but retains the core logic):

```asm
PendSV_Handler:
    /* Check bit4 of EXC_RETURN (whether to use FPU to extend the stack frame) */
    MRS  R0, PSP              ; Get the process stack pointer of the current task

    /* Manually save floating point registers (if FPU is used) */
    TST  R14, #0x10           ; Check bit4 of EXC_RETURN
    IT   EQ
    VSTMDBEQ R0!, {S16-S31}   ; Save FPU high half area

    /* Save integer registers R4-R11 */
    STMDB R0!, {R4-R11}       ; The register group is pushed onto the stack and R0 is decremented.

    /* Save the current task stack pointer to TCB (indirectly through R1) */
    LDR  R1, =pxCurrentTCB
    LDR  R1, [R1]             ; R1 = current TCB pointer
    STR  R0, [R1]             ; Write back the top of the new stack to TCB

    /* Call the scheduler to select the next task */
    PUSH {R14}
    BL   vTaskSwitchContext
    POP  {R14}

    /* Load the stack pointer of the new task */
    LDR  R1, =pxCurrentTCB
    LDR  R1, [R1]             ; R1 = new TCB pointer
    LDR  R0, [R1]             ; R0 = top of stack for new task

    /* Restore integer registers R4-R11 */
    LDMIA R0!, {R4-R11}       ; Pop off the stack and increment R0

    /* Restore floating point registers (if FPU is used) */
    TST  R14, #0x10
    IT   EQ
    VLDMIAEQ R0!, {S16-S31}

    /* Update PSP to the new stack pointer and return an exception */
    MSR  PSP, R0
    BX   R14                   ; Exception return, CPU automatically pops up R0-R3, R12, LR, PC, xPSR
```

There are several exquisite designs in this compilation:

1. **VSTMDBeq/VLDMIAeq**: The floating-point register is saved by **lazy loading**, which is only saved when the current task has actually used the FPU. Bit4 of EXC_RETURN is automatically maintained by the hardware. If the task has executed floating point instructions, bit4=0; otherwise, bit4=1. No software is required to maintain FPU usage flags.
2. **Exception return processing**: The EXC_RETURN value used by `BX R14` automatically tells the CPU "whether to use PSP (process stack pointer) or MSP (main stack pointer) after return." The mission context is always on the PSP. The interrupt context is always on the MSP. This hardware feature allows FreeRTOS to only manage one PSP.

## Physical connection: where the time is spent on context switching

**A significant portion of the 1-2μs overhead of context switching is spent on bus cycles: reading and writing SRAM from the pop and push registers. ** Cortex-M4's AHB bus is ~9ns per bus cycle at 112MHz. 16 words pushed + 16 words popped = 32 bus cycles = approximately 288ns. Adding interrupt latency (12 cycles = about 107ns), TCB read and write (several bus cycles), ready list operations (finding the highest priority = O(1) on Cortex-M with CLZ instruction), plus pipeline refresh and Flash wait, the actual measurement is usually 1-2μs.

**Every nanosecond here is a constraint in the physical world**. The access delay of SRAM is not infinitesimal (capacitor charging, signal propagation, sense amplifier output stabilization), each nanosecond is the sum of the RC delay of the transistor switching and metal wiring. You're doing operating system design, but your constraints come from CMOS physics.

## Create tasks: Task life of FreeRTOS

You don’t manage context switching yourself, FreeRTOS does it for you. You just tell it to "create these tasks":

```c
#include "FreeRTOS.h"
#include "task.h"
#include "queue.h"
#include "semphr.h"

/* Task handle */
TaskHandle_t xTorqueTask;
TaskHandle_t xCANProcessTask;
TaskHandle_t xDiagTask;
TaskHandle_t xBackgroundTask;

/* Synchronization object */
QueueHandle_t xCANRxQueue;
SemaphoreHandle_t xDTCSemaphore;

/* Task stack, in the bare metal era you were worried about stack overflow, now FreeRTOS helps you monitor it */
/* The stack depth unit is StackType_t (1 word = 4 bytes on Cortex-M) */
static StackType_t torque_task_stack[512];
static StackType_t can_task_stack[512];
static StackType_t diag_task_stack[256];
static StackType_t bg_task_stack[256];

static StaticTask_t torque_task_tcb;
static StaticTask_t can_task_tcb;
static StaticTask_t diag_task_tcb;
static StaticTask_t bg_task_tcb;

void app_create_tasks(void)
{
    /* Create message queue, CAN ISR → CAN processing task */
    xCANRxQueue = xQueueCreate(32, sizeof(can_frame_t));

    /* Create a semaphore, DTC update mutex */
    xDTCSemaphore = xSemaphoreCreateMutex();

    /* Create task, highest priority (5): torque control, 100μs cycle */
    xTorqueTask = xTaskCreateStatic(
        vTorqueControlTask,
        "Torque",
        512,
        NULL,
        tskIDLE_PRIORITY + 5,
        torque_task_stack,
        &torque_task_tcb);

    /* Priority (3): CAN message processing, wake up by queue */
    xCANProcessTask = xTaskCreateStatic(
        vCANProcessTask,
        "CANProc",
        512,
        NULL,
        tskIDLE_PRIORITY + 3,
        can_task_stack,
        &can_task_tcb);

    /* Priority (2): Diagnostic task, awakened by UDS request */
    xDiagTask = xTaskCreateStatic(
        vDiagTask,
        "Diag",
        256,
        NULL,
        tskIDLE_PRIORITY + 2,
        diag_task_stack,
        &diag_task_tcb);

    /* Priority (1): Background task, lowest priority */
    xBackgroundTask = xTaskCreateStatic(
        vBackgroundTask,
        "BG",
        256,
        NULL,
        tskIDLE_PRIORITY + 1,
        bg_task_stack,
        &bg_task_tcb);

    vTaskStartScheduler();
    /* After the scheduler starts, this line of code will never be executed until */
}
```

## From ISR to task: the complete FreeRTOS flow of CAN processing

You saw in the bare metal chapter that the CAN ISR operates directly on the ring buffer. Under FreeRTOS, the communication between ISR and tasks is decoupled through Message Queue (the following CAN register writing method follows the STM32 example of 5.1, focusing only on the structure of ISR → Queue):

```c
/* CAN receive interrupt, only do minimal work in ISR */
void CAN1_RX0_IRQHandler(void)
{
    can_frame_t frame;
    BaseType_t xHigherPriorityTaskWoken = pdFALSE;

    /* Read a frame from the hardware FIFO, the faster the better */
    frame.id  = (CAN1->sFIFOMailBox[0].RIR >> 21);
    frame.dlc = CAN1->sFIFOMailBox[0].RDTR & 0x0f;
    frame.data[0] = CAN1->sFIFOMailBox[0].RDLR & 0xff;
    frame.data[1] = (CAN1->sFIFOMailBox[0].RDLR >> 8) & 0xff;
    frame.data[2] = (CAN1->sFIFOMailBox[0].RDLR >> 16) & 0xff;
    frame.data[3] = (CAN1->sFIFOMailBox[0].RDLR >> 24) & 0xff;
    frame.data[4] = CAN1->sFIFOMailBox[0].RDHR & 0xff;
    frame.data[5] = (CAN1->sFIFOMailBox[0].RDHR >> 8) & 0xff;
    frame.data[6] = (CAN1->sFIFOMailBox[0].RDHR >> 16) & 0xff;
    frame.data[7] = (CAN1->sFIFOMailBox[0].RDHR >> 24) & 0xff;

    CAN1->RF0R |= CAN_RF0R_RFOM0;

    /* Push the frame into the queue and wake up the CAN processing tasks waiting for the queue */
    xQueueSendFromISR(xCANRxQueue, &frame, &xHigherPriorityTaskWoken);

    /* If the queue send wakes up a higher priority task,
     * Request a context switch immediately after the ISR exits */
    portYIELD_FROM_ISR(xHigherPriorityTaskWoken);
}

/* CAN processing task, processed in task context */
void vCANProcessTask(void *pvParameters)
{
    can_frame_t frame;

    while (1) {
        /* Blocks waiting for data in the queue, and wakes up immediately after the ISR pushes the frame in */
        if (xQueueReceive(xCANRxQueue, &frame, portMAX_DELAY) == pdTRUE) {
            switch (frame.id) {
            case 0x100: /* ABS wheel speed */
                process_abs_wheel_speed(&frame);
                break;
            case 0x200: /* Engine speed */
                process_engine_speed(&frame);
                break;
            case 0x300: /* Intake air temperature */
                process_intake_temp(&frame);
                break;
            default:
                break;
            }
        }
    }
}
```

ISR latency is minimized by simply pushing frames into the queue and then exiting them immediately. Task processing is executed in the task context, can be preempted, can be blocked on other queues, and can use floating point operations without worrying about FPU context saving (FreeRTOS automatically manages).

## Scheduling theory: Rate Monotonic Scheduling

You assign priorities to tasks, not based on gut feeling. **Rate Monotonic Scheduling (RMS)** is the cornerstone of real-time system scheduling theory.

The rules of RMS are extremely simple: **The shorter the cycle, the higher the priority. ** Not based on "importance", but based on "frequency". The reason is straightforward: tasks with short cycles also have short deadlines and must be scheduled first.But you assign priorities to all tasks, and you have to make sure they are completed before the deadline. Here's a schedulability test: **Utilization Upper Bound**:

For n periodic tasks, if their sum of CPU utilization U satisfies:

```
U = Σ(Ci/Ti) ≤ n × (2^(1/n) - 1)
```

where Ci is the worst execution time of task i and Ti is its period. Then this set of tasks is **definitely schedulable** under RMS. regardless of their relative phase relationship.

Asymptotic value of this formula: as n → ∞, the upper bound approaches ln(2) ≈ 0.693. In other words, under RMS, as long as the CPU utilization does not exceed 69.3%, the task set must be schedulable.

For n=3 tasks, the exact upper bound is 3 × (2^(1/3) - 1) ≈ 0.78.

Back to your engine ECU. Torque control 100μs period, 50μs execution (utilization 0.5). ABS wheel speed 1ms period, 200μs execution (utilization 0.2). CAN processing 5ms period, 1ms execution (utilization 0.2). Total utilization 0.9 > 0.78, the RMS schedulability theorem is not guaranteed. You need a more precise schedulability analysis, or use EDF (earliest deadline first) scheduling, which guarantees schedulability when utilization ≤ 1.0. However, EDF behaves erratically under overload and is rarely used in automotive ECUs.

RMS is what you do intuitively on bare metal. "The task with the shortest cycle has the highest priority", but it gives you a mathematically rigorous formalization of this intuition.

## RTOS is not a free lunch - three classic "explosion" scenarios

The scheduler is your most loyal assistant, and it can also be your most dangerous time bomb. Sooner or later you will encounter the following three problems.

### Scenario 1: Priority inversion

This is the most notorious bug in the RTOS world. Imagine a specific timeline:

```
t=0ms: T3 (low priority, prio=2) starts execution.
t=1ms: T3 obtains Mutex M (protected DTC record table). T3 is still executing.
t=2ms: T1 (high priority, prio=5) ready. Seize T3. T1 starts execution.
t=3ms: T1 tries to get Mutex M. Found to be held by T3. T1 obstruction.
         T3 resumes execution, T3 holds the Mutex and needs to complete work before it can be released.
t=4ms: T2 (medium priority, prio=3) ready. T2 does not require Mutex.
         The scheduler sees that T2 has higher priority than the currently running T3. Seize T3. T2 starts execution.
t=10ms: T2 is completed. T3 recovery.
t=11ms: T3 completes its work and releases Mutex M.
t=11ms: T1 obtains Mutex M and resumes execution.
```

T1 blocks from t=3ms to t=11ms, a total of **8 ms**. Its deadline may be only 500μs. High-priority tasks are starved, not because T3 (the one who holds the lock) is too slow, but because T2 (the one who does not hold the lock and does not need the lock) always preempts T3. There is no competition between T2 and T1. T2 is the truly innocent party. But it had disastrous consequences.

**Solution: Priority Inheritance. ** When T1 blocks on the Mutex held by T3, RTOS temporarily raises the priority of T3 to the level of T1 (prio=5). T2 only has prio=3 and cannot preempt T3. T3 quickly completes its work with high priority, releases the mutex, and T1 can continue. After T3 completes its release, the priority drops back to its original setting.

FreeRTOS's Mutex (`xSemaphoreCreateMutex()`) has built-in priority inheritance; binary semaphores do not. The OS of AUTOSAR CP follows the Priority Ceiling Protocol of OSEK/VDX, which raises the task priority to the ceiling priority of the resource when acquiring resources to avoid reversal from the source. In safety-critical systems, this is not an optional feature, it is a basic guarantee.

This bug cannot exist in bare metal code: bare metal does not have preemptive multitasking. While RTOS provide convenience, they also introduce a whole new class of problems.

### Scenario 2: Task stack overflow - where does HardFault come from?

Symptom: System occasionally HardFaults. Cannot be reproduced.

You allocate 512 bytes of stack space to T3. Only 420 bytes are used in a normal control cycle, which seems more than enough. But under certain conditions, such as fault handling (recording DTC to NVM + sending fault notification CAN message). The call chain goes 5 levels deep, and local variables and function parameters push stack usage to 560 bytes. The stack overflows into the stack space of the adjacent task (T4). Overwrites the stack frame of T4. T4 reverts to a corrupted context on next dispatch → HardFault.**Stack overflow detection: magic number method**

```c
/* FreeRTOS stack overflow detection hook, magic digital technology */
#define STACK_MAGIC_NUMBER  0xA5A5A5A5UL

void vApplicationStackOverflowHook(TaskHandle_t xTask,
                                    char *pcTaskName)
{
    /* A stack overflow occurred! Log the fault and attempt a safe shutdown */
    record_dtc(DTC_STACK_OVERFLOW);

    /* Print the task name, at least know who crossed the line */
    while (1) {
        /* Unable to safely restore, do not schedule again */
    }
}

/* FreeRTOS internals: Check the magic number at the beginning of the stack on every context switch */
/* Schematic logic: actually check the 20 bytes of 0xA5 padding at the beginning of the stack in the FreeRTOS kernel (port.c) */
void vPortCheckStack(void)
{
    TCB_t *task = pxCurrentTCB;   /* TCB_t is a FreeRTOS internal type */
    StackType_t *stack_start = task->pxStack;

    /* Check whether the magic number at the beginning of the stack (low address) is overwritten */
    if (*stack_start != STACK_MAGIC_NUMBER) {
        /* The magic number is corrupted and the stack overflows */
        vApplicationStackOverflowHook(task, task->pcTaskName);
    }
}

/* Enabled in FreeRTOSConfig.h */
#define configCHECK_FOR_STACK_OVERFLOW    2
/* Method 2: Check whether the 0xA5 fill pattern at the beginning of the stack (low address end) is destroyed */
```

When the task stack is created, FreeRTOS fills the entire stack space with 0xA5; method 1 checks whether the current stack pointer is out of bounds when switching, and method 2 checks whether the 0xA5 filling pattern at the beginning of the stack (low address end) is destroyed. At the same time, `uxTaskGetStackHighWaterMark()` returns the minimum remaining space of the stack: the closer the high water mark is to zero, the more dangerous it is; returning 0 means it has been exhausted or even overflowed.

There is a cruel reality in troubleshooting stack overflow: the consequences of stack overflow (HardFault) often occur long after the stack overflow, and are not exposed until another completely unrelated task is scheduled.  There may be dozens of context switches between the fault site you see (HardFault of T4) and the source of the fault (stack overflow of T3). This is one of the most crushing scenes in embedded debugging.

### Scenario 3: Idle tasks starve to death

Symptoms: The longer the system runs, the less heap memory becomes, `pvPortMalloc` eventually returns NULL, and new tasks or queues fail to be created.

Your proud high-priority task T1 (100μs period) acquires a spin lock every time it runs. T1 period 100μs, each run 50μs, CPU utilization 50%. The remaining 50μs are occupied by low- and medium-priority tasks. But the Idle Task never gets the CPU because at least one task is always ready. 

The idle task has an important responsibility: to release the memory of the deleted dynamically allocated task. When you call `vTaskDelete(NULL)` to delete the task itself, the task's memory is not released immediately: the task is still running and its own stack cannot be released. The TCB and stack of the deleted task are put into a "to be recycled list". It is an idle task that releases these memories one by one when the CPU has nothing else to do. If idle tasks never get the CPU, more and more memory accumulates, and eventually the heap is exhausted, `pvPortMalloc` returns NULL, and the system crashes.

Idle tasks are not waste. **It is the system's garbage collector. ** If you find that the CPU utilization of idle tasks is always 0%, there is something wrong with your system design: either there are tasks waiting (busy-wait), or the CPU demand has exceeded 100% and the deadline has begun to be lost.

## Scheduling: the lowest and core issue of the computer system

The essence of a real-time operating system is: **optimally allocate time under limited resources. **

You have 1 CPU (or N CPUs on multi-core), but there are many tasks competing for it. The job of the RTOS is to ensure that each task gets the necessary CPU time before its deadline.

This and SPI/CAN arbitration, AMBA bus arbitration, and Ethernet switch priority queue scheduling are all different instances of the same problem. That is: how to schedule shared resources according to priority and worst delay in multi-party competition.

From the signal competition of logic gates on the silicon chip, to the ID arbitration of the CAN bus, to the task scheduling of the RTOS, to the QoS policy of the Internet router, these are all different faces of scheduling.  You solved one and understood them all.

Of course you can make your own RTOS, and custom scheduling strategies are also very flexible, but the entire automotive industry needs a standard. If a Tier-1 engine controller is written for Peugeot Citroën and an engine controller is written for Volkswagen, the hardware is the same but the software cannot be shared at all: the same CAN driver needs to be rewritten five times, and the same diagnostic stack needs to be rewritten five times. The scale effect of software is completely swallowed up.

In 2003, a group of European OEM and Tier-1 representatives sat in a conference room and decided to change all that.

## Summary

Today we did one thing: **Understand the essence of a real-time operating system: optimal allocation of time under limited resources, and how the system crashes when this allocation goes wrong. **Key takeaways:
1. **The essence of RTOS is a scheduling problem: SPI arbitration, CAN ID arbitration, and AMBA bus arbitration are different instances of the same problem**: how to allocate shared resources according to priority and worst delay in multi-party competition. You solve one and understand them all.
2. **Semaphores, mutexes, and priority inheritance are not "design patterns" but accurate modeling of physical race conditions**: Priority inversion makes high-priority tasks wait indefinitely. Priority inheritance breaks the chain of waiting by temporarily increasing the priority while the lock is held.
3. **Stack overflow is the most dangerous time bomb in the RTOS world**: There may be dozens of context switches between the fault site (HardFault of a certain task) and the source of the fault (stack overflow of another task). Stack watermark detection and high-water marks are the most commonly used detection techniques.
