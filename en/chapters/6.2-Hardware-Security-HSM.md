# 6.2 Hardware Security: HSM

## Remote hijacking on the highway

July 2015. St. Louis Expressway. A Jeep Cherokee is traveling in traffic at a speed of 110km/h.

The driver's hands are on the steering wheel and his foot is on the accelerator. Everything works fine.

Then, the air conditioning volume jumped to maximum, the radio volume exploded, and the wipers began to swing wildly on a sunny day without rain. Then, the transmission was remotely shifted into neutral and the accelerator pedal failed. Finally, the steering wheel locks in its current position.

The driver lost control of the steering wheel, accelerator, and brakes on the highway.

This is not a movie, this is a public safety demonstration given to FCA (Fiat Chrysler) by safety researchers Charlie Miller and Chris Valasek.

Their attacks are not magic, every step is systematic.

**Step One: External Entrance. ** Uconnect infotainment system maintains Internet connectivity via Sprint cellular network. The attacker scanned the IP address range of the cellular network and discovered that the Uconnect head unit had port 6667 (D-Bus debug interface) open, no firewall, and no authentication.

**Step 2: Lateral movement. ** The infotainment system's OMAP processor communicates with the V850 gateway controller via an internal SPI bus. The attacker used the D-Bus interface to obtain the root shell on the OMAP and re-flashed the V850 firmware. The V850 now becomes an attacker's puppet and can send arbitrary messages to the CAN bus.

**Step 3: CAN injection. **The CAN protocol does not have any authentication mechanism. Any node with access to the CAN bus can send out any data with any CAN ID. The attacker sent CAN frames of "brake release", "transmission into neutral", and "steering wheel angle offset" from V850 to CAN-C (chassis CAN). The brake ECU cannot distinguish between "deceleration command from the brake pedal" and "deceleration command from the attacker". The steering wheel ECU cannot distinguish between the "corner signal from the driver's corner sensor" and the "corner signal injected by the attacker."

FCA recalls 1.4 million vehicles. For the first time, the automotive industry collectively realized that the automobile is no longer a closed mechanical system, but a computing node connected to the Internet, with multiple network interfaces, and can be remotely attacked.

## Why does it have to be hardware?

A natural question: Why not rely on software? If you write good code, do a good job of code auditing, and add a firewall, can software security still prevent attacks?

The answer is cruel but true: **The code will always have bugs. **

There are more than 3,000 open flaws in the Linux kernel as of 2024. The complete basic software stack of AUTOSAR CP exceeds one hundred thousand lines of C code. There is no guarantee that any non-trivial software system will be bug-free.

The Jeep attack, if Uconnect's infotainment system code had been written flawlessly and the firewall configuration was flawless, that attack would not have happened. But requiring any complex software to be "perfect" is a promise that cannot be kept. The attacker only needs to find a vulnerability. Defenders must close all loopholes. The costs between offense and defense are asymmetric.

Therefore, another layer of guarantee is needed, one that does not rely on code quality.

This layer of protection is **physical isolation + cryptography**.

Physical isolation means that even if all the code of the main CPU is compromised and the attacker gets full execution rights of the main CPU, the attacker cannot read the key. Because the key is not in the main CPU's address space.

Cryptography means: To forge a legitimate secure CAN message, an attacker needs to know the key. Without knowing the key, no matter how much you modify the main CPU code, you cannot forge a legitimate signature.

Together, the two form a foundation of trust that does not rely on code quality.

## HSM: An independent kingdom inside a silicon wafer

HSM (Hardware Security Module) is an independent security processor embedded inside the MCU chip die."Independence" is not rhetoric. HSM has its own CPU core (usually ARM Cortex-M0 or a dedicated security core), with its own independently packaged Flash and RAM. These memory locations do not exist in the main CPU's address map, and the physical traces are not connected to the main CPU's crossover bus at all. Even if the attacker plugs the JTAG debugger into the debug port of the chip and dumps the entire contents of the main Flash, he cannot read a single bit inside the HSM.

HSM does only three things. Only three pieces are made, but each one is a cornerstone of trust.

---

## The first pillar: key storage

All encryption keys needed by the ECU: AES keys for secure communication, public keys for firmware signing, private keys for unique device identification, are all stored inside the HSM. The master CPU does not know the value of the key. The main CPU can only say to the HSM "Please encrypt this data with the key of slot 3" or "Please verify this CMAC value with the key of slot 5". The HSM performs cryptographic operations internally and returns the results to the main CPU. The key passes through the encryption engine inside the HSM during the operation and never appears on the bus of the main CPU.

This is typical API usage of CSEc (Cryptographic Services Engine, NXP's SHE-compatible cryptographic services engine): The main CPU interacts with the HSM through shared memory and command registers:

```c
/* CSEc_API.c, the interface for the main CPU to call the HSM encryption service (simplified version of the SHE specification) */

#define HSM_CMD_ENC_ECB 0x01 /* AES-128 ECB encryption */
#define HSM_CMD_DEC_ECB 0x02 /* AES-128 ECB decryption */
#define HSM_CMD_GENERATE_MAC 0x03 /* AES-CMAC generation */
#define HSM_CMD_VERIFY_MAC 0x04 /* AES-CMAC verification */
#define HSM_CMD_LOAD_KEY 0x05 /* Load the key into slot */
#define HSM_CMD_RND 0x06 /* True random number generation */

/* HSM command interface, communicates through shared memory and status register */
typedef struct {
    volatile uint32_t CMD;        /* command register */
    volatile uint32_t STATUS;     /* Status: 0=idle, 1=busy, 2=complete, 3=error */
    volatile uint32_t KEY_SLOT;   /* Key slot number (exact number depends on device/SHE configuration) */
    uint8_t           INPUT[16];  /* Input data (plain text/cipher text/message) */
    uint8_t           OUTPUT[16]; /* Output data (ciphertext/plaintext/MAC) */
} HSM_Interface_t;

static HSM_Interface_t *const hsm = (HSM_Interface_t *)HSM_BASE_ADDR;

/* Use the key of HSM slot 3 to perform AES-128 encryption on 16-byte plaintext */
int HSM_AES_Encrypt(uint8_t key_slot, const uint8_t *plaintext,
                     uint8_t *ciphertext)
{
    /* 1. Copy the plaintext to the HSM input buffer */
    memcpy((void *)hsm->INPUT, plaintext, 16);

    /* 2. Select key slot */
    hsm->KEY_SLOT = key_slot;

    /* 3. Send encrypted command */
    hsm->CMD = HSM_CMD_ENC_ECB;

    /* 4. Polling and waiting, HSM executes AES on its own core */
    while (hsm->STATUS == HSM_STATUS_BUSY) {
        /* Within the 100μs control period, such a wait is unacceptable, and the actual code
         * Interrupt + callback will be used. The most primitive synchronization interface is shown here. */
    }

    if (hsm->STATUS != HSM_STATUS_DONE) {
        return -1;  /* HSM reports error */
    }

    /* 5. Read the ciphertext from the HSM output buffer */
    memcpy(ciphertext, (void *)hsm->OUTPUT, 16);
    return 0;
}

/* Verify AES-CMAC using the key of HSM slot 5 */
int HSM_Verify_CMAC(uint8_t key_slot, const uint8_t *message,
                     uint8_t msg_len, const uint8_t *expected_mac)
{
    /* Copy the message to shared memory */
    memcpy((void *)hsm->INPUT, message, msg_len);

    hsm->KEY_SLOT = key_slot;
    hsm->CMD = HSM_CMD_VERIFY_MAC;

    while (hsm->STATUS == HSM_STATUS_BUSY);

    if (hsm->STATUS != HSM_STATUS_DONE) {
        return -1;
    }

    /* The verification result of HSM is in OUTPUT[0]:
     * 0x00 = CMAC mismatch
     * 0x01 = CMAC match */
    return (hsm->OUTPUT[0] == 0x01) ? 0 : -1;
}

/* Get random numbers from HSM’s true random number generator (for SecurityAccess seed) */
int HSM_GetRandom(uint8_t *random_bytes, uint8_t len)
{
    for (uint8_t i = 0; i < len; i += 16) {
        hsm->CMD = HSM_CMD_RND;
        while (hsm->STATUS == HSM_STATUS_BUSY);
        memcpy(random_bytes + i, (void *)hsm->OUTPUT,
               (len - i > 16) ? 16 : len - i);
    }
    return 0;
}
```

Key point: `plaintext` plaintext enters the HSM-specific buffer after `memcpy` to `hsm->INPUT`. The HSM's INPUT register is mapped in the HSM-specific address space and is connected by the HSM internal bus. The main CPU accesses through the bridge (bridge), but the bridge only exposes the INPUT/OUTPUT and command registers. Keys, intermediate round keys, S-Box lookup tables, these are all inside the HSM. No logic analyzer on the main CPU bus, no debugger, no compromised kernel code can see the keys and intermediate states inside the HSM.

## Second Pillar: Secure Boot (Secure Boot)

After the MCU is powered on, the HSM starts before the main CPU. It has its own independent clock and reset logic and does not rely on the main CPU.

The complete process of secure boot:

```
Power on
  │
  ▼
Voltage climb → HSM internal RC oscillator starts → HSM reset release
  │
  ▼
HSM loads HSM firmware from internal ROM (small, ~4KB)
  │
  ▼
HSM Firmware Self-Test: Verify the integrity of the firmware signature in HSM Flash
  │  (hash of HSM firmware public key in OTP)
  │
  ├── bad signature → HSM stops; main CPU never boots (brick protection)
  │
  ▼The signature is valid
HSM reads main CPU firmware image (new partition) from external Flash
  │
  ▼
HSM calculates the SHA-256 hash of the firmware image
  │
  ▼
The HSM uses the public key to verify the digital signature at the end of the firmware image (RSA-2048 or ECC P256)
  │
  ├── bad signature → HSM holds reset
  │      try old partition (A/B fallback)
  │      ├── old signature OK → release reset, run old firmware
  │      └── old signature bad → never boot (no trusted firmware)
  │
  ▼The signature is valid
HSM releases the reset line of the main CPU
  │
  ▼
The main CPU starts running from the firmware start address
At this point, the main CPU is convinced that every line of code it is about to execute comes from the OEM's signature server.
Not a single bit has been changed.
```

Before `main()` is executed, before the first global variable of the main CPU is initialized, trust is established. This trust is not derived from the code, the code itself is the object being verified. The anchor of trust is at a lower level.

## Penetration: The physical anchor of trust - Fuse

**The OTP (One Time Programmable) storage inside the HSM is composed of a fuse array. **

During the final stages of chip manufacturing, or at a secure programming station on the ECU production line, a programmer applies a high voltage pulse to a selected fuse. The current density of this pulse (approximately 10^6 A/cm²) produces Joule heating and electromigration in the metal wiring. The metal atoms are physically pushed out of place and the resistance of the wiring jumps from near zero to near infinity. A fuse changed from "on" to "off".

Once broken, always broken. The second law of thermodynamics determines that the atoms on this line cannot spontaneously return to their original positions. You don't need any software to protect this state, the physical laws of the universe protect it.

The secure boot public key hash is burned in these fuses. OTP can be read immediately after power-on and does not require any software initialization. The upstream firmware verification logic uses this hash to verify the public key in the signature block, uses the public key to verify the firmware signature, and uses the signature to confirm that the firmware has not been tampered with.

The starting point of the chain is the high voltage pulse used to blow the fuse. **Trust is not derived, trust is anchored in physical reality. ** On the die of the chip, beneath the layers of silicon dioxide and aluminum interconnects, in an array of metal wires permanently severed by electromigration, the trust is here.

This is what Root of Trust means: the final anchor of the chain of trust is not in software, but in physics.

## The third pillar: crypto accelerationHSM has built-in hardware encryption engines: AES-128/256, SHA-256, RSA-2048, ECC P256/P384, TRNG true random number generator. The specific algorithm combination depends on the HSM level: SHE/CSEc level one mainly provides AES-128 and CMAC, and RSA/ECC signature verification usually requires a higher level HSM (such as EVITA Full).

A set of AES-128 encryption requires only 11 clock cycles in the HSM's hardware engine (pipelined AES core). If the software library of the main CPU is used, even a highly optimized T-table lookup implementation will take about 200 cycles. In a real-time system with a 100μs control cycle, the 189 cycles saved may be the difference between "being able to send the safe CAN message before the deadline" and "too late".

For asymmetric encryption (RSA-2048 signature verification), the gap in hardware acceleration is still significant. Software RSA-2048 verifies a signature once, usually on the order of milliseconds to ten milliseconds, depending on the platform and implementation. HSM's hardware accelerator can push it down to sub-millisecond to millisecond levels. In secure boot, you only have a few tens of milliseconds to budget for boot time, and the overhead and jitter of software RSA eats up considerable headroom.

## SecOC: Signature CAN messages

Secure boot ensures startup, but every frame of CAN messages sent by the main CPU while running is running naked on the bus. Can an attacker forge it?

One of the core vulnerabilities that caused Jeep to be hacked was that CAN was not certified. Any node can send any CAN ID, and the receiver cannot tell the difference between true and false.

SecOC (Secure Onboard Communication) is an in-vehicle secure communication mechanism defined by AUTOSAR.

ECU A and ECU B share an AES symmetric key (stored in the slot of the respective HSM).

**Sender (ECU A):**
1. Construct the data part of the CAN frame (4 bytes, such as steering wheel angle signal; a classic CAN frame only has 8 bytes, leaving space for the authenticator).
2. Get the current Freshness Value (FV = monotonically increasing counter) from the HSM.
3. Concatenate FV (4 bytes) + CAN data (4 bytes) into an 8-byte message.
4. Send the HSM command: "Compute AES-CMAC on this 8-byte message using the key from slot 3."
5. HSM returns a 16-byte CMAC and intercepts the first 4 bytes as "Authenticator".
6. Attach the Authenticator to the end of the data field of the CAN frame and send it to the bus (4 + 4 = 8 bytes).
7. FV++ (synchronized to non-volatile storage according to policy to prevent replay after power outage).

**Receiver (ECU B):**
1. Receive CAN frame, extract data part and Authenticator.
2. Get the FV of your own record from the HSM (should be ≥ the sender’s FV).
3. Check if this FV > the last accepted FV. If ≤ last value, this is a replay attack and discarded.
4. Recalculate the CMAC using the FV + CAN data and compare it with the received Authenticator.
5. Matching, data has not been tampered with, processed. If there is no match, the sender's key is incorrect, the message is forged and discarded.

**Freshness Value is SecOC’s most ingenious design. ** It is a monotonically increasing counter, +1 for each frame sent. The attacker records a frame of legitimate messages on the bus and wants to replay it later. The receiver checks the FV and finds that this value ≤ the last value received: "This is an old message, you are replaying it." Discard.

No need for a GPS synchronized clock, no need for millisecond time accuracy, just a monotonically increasing number. Replay attacks are completely prevented.**The attacker does not know the key (cannot forge CMAC), cannot reuse old messages (FV is outdated), and cannot tamper with the content (CMAC does not match). ** Triple protection, all from a symmetric key that lives inside the HSM and is never seen by the main CPU.

## Penetration: From steering wheel to silicon wafer

We do a safe penetration.

You turn the steering wheel to the left. The EPS controller receives the command and drives the steering motor.

If there is an attacker: The attacker injects a "turn the steering wheel right" message into the CAN bus through the OBD port. The EPS controller cannot tell the difference between genuine and fake, and the CAN protocol is not certified.

If SecOC is enabled: After the EPS controller receives the "steering wheel turn right" message, the HSM verifies the attached CMAC. If there is no match, the sender’s key is incorrect and discarded. The steering motor does not move. The attack failed.

Penetrating one level down: This CMAC verification is done in the HSM's hardware encryption engine: AES-128 operation, 11 clock cycles.

Further down: The AES key used for authentication is stored in key slot 3 of the HSM and cannot be read by the main CPU. The bridge between the HSM internal bus and the main CPU AHB bus does not expose any key registers.

Further down: The HSM itself goes through a secure boot self-test on power-up, and the HSM firmware has not been tampered with. This self-test uses the public key hash burned into the HSM OTP. From OTP to signature verification, the entire chain of trust spans the fuse array, HSM internal ROM, and external Flash.

Further down: the fuse array. High voltage pulse. Electromigration of metal atoms. The selected fuse is physically blown, and the others remain conductive. Not lost after power outage. 20-year data retention. stored in the physical laws of the universe.

**From the physical rotation of the steering wheel, to a metal connection permanently severed by electromigration in the silicon chip OTP. ** Security chains run throughout this entire path. If any link in the chain breaks, the entire trust collapses.

## Security is a social contract

You get into a car, put on your seat belt, turn on the ignition, and get on the highway.

You have a basic assumption about the car: The steering wheel responds to your hands, the brakes respond to your feet, and no one can remotely take away control. 

This assumption is so basic that you never consciously doubt it. But it is not established naturally, it is guaranteed by engineering.

Car manufacturers have a promise to every driver: "The car we deliver to you will always be yours to control." The legal form of this promise is product liability. The technical form is HSM, secure boot, SecOC, secure programming process, which is a complete set of hardware security architecture.

Whenever someone questions "is it worth spending the extra two dollars to add an HSM chip to the ECU?" the answer is: **This is not cost accounting, this is the physical basis of trust. **

**The driver entrusts his life to you, what guarantee do you have? **


But what secure boot verifies is "whether the signature of the firmware is legal." A more fundamental question is: How does the firmware itself get to the car? How can the new version of firmware be written into every piece of Flash safely, completely, and without errors?

1 million ECUs distributed around the world, 200MB of new firmware, unreliable cellular networks. Zero fault tolerance: not even a single failure.

## Summary

Today we did one thing: **Understand that the foundation of security is not in any line of code, but in a metal connection that is physically burned out by high-voltage pulses in the silicon chip. **Key takeaways:
1. **The root of trust for security is not in the software, but in the physical laws of silicon**: In the HSM's OTP fuse array, high-voltage pulses physically cut off the metal connections through electromigration. This is a thermodynamic guarantee, not a code guarantee. Data will not be lost even if the power is off, and the data will be retained for 20 years.
2. **The verification of secure boot is not "whether the code is written correctly", but "whether the code has been tampered with"**: HSM verifies the firmware before the main CPU during startup. The chain of trust starts from OTP→HSM internal ROM→bootloader→app, and is interlocking. If any link breaks, the entire trust will collapse.
3. **Safety is a social contract for drivers**: When you sit in the car, by default the steering wheel will respond to your hands and the brakes will respond to your feet. This basic assumption is not inherently valid. It is protected by the hardware security architecture of HSM, secure boot, and SecOC.
4. **More implementation details of HSM**: See the companion article ["HSM Technical Book"] (https://github.com/Lularible/hsm-book).
