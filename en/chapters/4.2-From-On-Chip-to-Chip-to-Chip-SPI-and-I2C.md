# 4.2 From On-Chip to Chip-to-Chip: SPI and I2C

## A new board, a waveform, a lesson

The day you first dialed up I2C on a newly designed circuit board.

After powering on, the code runs into the I2C init function, sends the Start condition, and the SDA and SCL on the logic analyzer are correct. The slave address is sent and ACK is received. But the read data is all 0xFF. After checking for a long time, I found that the pull-up resistor was forgotten to be soldered, and SDA was floating when idle.

After soldering the 4.7kΩ resistor, everything is normal. The content at address 0x00/0x01 of the I2C EEPROM is read back, and it spells out exactly 0x2026 written in the manual.

**At this moment you understand: the communication between chips is not just software. It is a combination of electrical, timing, protocol, and waveforms on the oscilloscope. **

## SPI: Four Lines of Minimalism

SPI is a serial communication protocol with **full-duplex**, **synchronous**, and **master-slave** architecture. Four lines:

| Signal | Name | Direction | Function |
|------|------|------|------|
| SCLK | Serial Clock | Master→Slave | Clock |
| MOSI | Master Out, Slave In | Master→Slave | Data |
| MISO | Master In, Slave Out | Slave→Master | Data |
| CS/SS | Chip Select / Slave Select | Master→Slave | Enable slave |

SPI does not have a standardized protocol layer. The rate, clock polarity (CPOL), clock phase (CPHA, the two are combined to form four timings of Mode 0–3), data bit order (MSB first / LSB first), and frame length (8 bits/16 bits/variable) are all defined by the specific device. This brings great flexibility, but also means that the driver for each SPI peripheral is customized.

A typical SPI transfer:
1. The master pulls CS low and selects the slave.
2. The master starts generating clock pulses on SCLK.
3. At each SCLK edge (CPOL determines the idle level, CPHA determines whether to sample on the first or second edge), the master station sends 1 bit on MOSI, and the slave station sends 1 bit on MISO.
4. After sending and receiving N bits, the master station pulls CS high to end the transmission.

SPI is full-duplex, every time you send a bit, you will also receive a bit. Even if you just want to "read", you have to send a piece of dummy data (usually 0x00 or 0xFF) to generate SCLK so that the slave can push the data to MISO.

SPI is a push-pull output, and each signal line is driven by a pair of complementary MOSFETs, which can be actively pulled high or low. The driving capability is strong (usually ±4mA to ±8mA), and in short PCB traces (<10cm) the speed can reach tens of MHz.

## Penetration: Configure SPI on S32K to send one byte

Let's write a piece of SPI code that actually runs on S32K. Goal: Send commands to MCP3008 via SPI1 and then read back the conversion results of the ADC.

```c
// ========== SPI1 initialization ==========
// S32K144: SPI1 is mounted on the LPSPI1 module
// LPSPI1 register base address = 0x4002c000 (check the Memory Map of S32K RM)

#define LPSPI1_BASE  0x4002c000

// LPSPI register offset (simplified version)
#define LPSPI_CR      (*(volatile uint32_t *)(LPSPI1_BASE + 0x10))  // Control
#define LPSPI_SR      (*(volatile uint32_t *)(LPSPI1_BASE + 0x14))  // Status
#define LPSPI_IER     (*(volatile uint32_t *)(LPSPI1_BASE + 0x18))  // Interrupt Enable
#define LPSPI_CFGR1   (*(volatile uint32_t *)(LPSPI1_BASE + 0x24))  // Config 1
#define LPSPI_CCR     (*(volatile uint32_t *)(LPSPI1_BASE + 0x40))  // Clock Config
#define LPSPI_FCR     (*(volatile uint32_t *)(LPSPI1_BASE + 0x58))  // FIFO Control
#define LPSPI_TCR     (*(volatile uint32_t *)(LPSPI1_BASE + 0x60))  // Transmit Cmd
#define LPSPI_TDR     (*(volatile uint32_t *)(LPSPI1_BASE + 0x64))  // Transmit Data
#define LPSPI_RDR     (*(volatile uint32_t *)(LPSPI1_BASE + 0x74))  // Receive Data

void spi1_init(void)
{
    // 1. Make sure SPI1 clock gating is on (PCC→SPI1)
    //    PCC_LPSPI1[CLK] = SIRCDIV2 (8MHz) or SPLLDIV2 (80MHz)
    //    (PCC register configuration is usually completed by startup code and is omitted here)

    // 2. Reset the SPI1 module
    LPSPI_CR = (1 << 1);  // RST = 1
    while (LPSPI_CR & (1 << 1));  // Wait for reset to complete (RST hardware cleared)

    // 3. Set to main mode, PCS[0] as CS, 24-bit frame, CPOL=0/CPHA=0 (Mode 0)
    LPSPI_CFGR1 = (1 << 0);  // CFGR1[MASTER] = 1
    LPSPI_TCR = (1 << 27)    // PRESCALE = 1 (divide by 2)
              | (23 << 0);   // FRAMESZ = 23 → 24-bit frame

    // 4. Configure clock frequency division → SCLK = SPI module clock / ((SCKDIV+2) * 2)
    //    If the module clock is 80MHz, SCKDIV=7 → SCLK = 80/(9*2) ≈ 4.44MHz
    LPSPI_CCR = (7 << 0)     // SCKDIV = 7
              | (0 << 8)     // DBT: Data-to-data delay = 0
              | (0 << 16);   // PCSSCK: PCS→SCK delay = 0

    // 5. Configure FIFO water level: Transmit FIFO empty water level = 0 (send as soon as there is data)
    LPSPI_FCR = (0 << 0)     // TXWATER (transmit FIFO water level)
              | (0 << 16);   // RXWATER (receive FIFO water level)

    // 6. Enable module
    LPSPI_CR = (1 << 0);  // MEN = 1 (module enable)
}
```

The frequency division value you just wrote into the CCR register eventually becomes a series of square waves on the SCLK pin that are accurate to nanoseconds. The hardware divider of the SPI controller is a counter chain that flips the output level every time it reaches a preset value.

```c
// ========== SPI1 send and receive ==========
uint32_t spi1_transfer(uint32_t tx_data)
{
    // Waiting for transmission FIFO to be empty (TDF = Transmit Data Flag)
    while (!(LPSPI_SR & (1 << 0)));  // Wait for SR[TDF]=1

    // Write the data to be sent
    LPSPI_TDR = tx_data;

    // Waiting for the receive FIFO to have data (RDF = Receive Data Flag)
    while (!(LPSPI_SR & (1 << 1)));  // Wait for SR[RDF]=1

    // Read back the received data
    return LPSPI_RDR;
}
```

Behind this line `while (!(LPSPI_SR & (1 << 0)))` is a bit of the LPSPI status register. TDF is set to indicate that there are still vacancies in the transmit FIFO; the 1 you read in the C code is the drain voltage of a transistor, which passes through five layers of metal interconnection lines and becomes read data on the AHB bus.

```c
// ========== Usage example ==========
void example_spi_adc_read(void)
{
    spi1_init();

    // CS is automatically controlled by LPSPI hardware (PCS[0])
    // MCP3008: start=1, SGL/DIFF=1 (single-ended), CH0 → command byte 0x80
    // A 24-bit frame: 0x80 + two dummy bytes, CS remains low during the entire conversion
    uint32_t rx = spi1_transfer(0x800000);
    uint8_t b2 = (uint8_t)(rx >> 8);   // null + D9..D3
    uint8_t b3 = (uint8_t)rx;          // D2..D0 + padding

    // Result of MCP3008: The lower 7 bits of b2 are D9..D3, the higher 3 bits of b3 are D2..D0
    uint16_t adc_value = ((b2 & 0x7f) << 3) | ((b3 >> 5) & 0x07);
    float voltage = adc_value * (3.3f / 1024.0f);
}
```

**Every register write operation in this code passes through AHB → Peripheral Bridge (APB/AIPS) → LPSPI module internal state machine. ** When `LPSPI_TDR = tx_data` is executed, data is sent from the CPU register to the peripheral bridge through the AHB write cycle, and the Bridge pushes the data into the LPSPI transmission FIFO. The bit engine inside LPSPI is generated from the SCLK edge to the MOSI pin push-pull output. We have completely walked through this path in 4.1.

## I2C: The elegance of two wires

I2C is a **half-duplex**, **synchronous**, **multi-master-multi-slave** (with arbitration) serial bus. Two lines:

| Signal | Name | Function |
|------|------|------|
| SDA | Serial Data | Data (bidirectional) |
| SCL | Serial Clock | Clock (master driver) |

The core design idea of I2C is **open-drain output + pull-up resistor**. Any device can pull the bus low (the N-MOS tube is connected to ground), but it cannot actively pull it high. Pulling it high requires a pull-up resistor (Rpullup). This design brings two good properties:

1. **Level compatible. ** As long as the pull-up resistor is connected to the target VDD and the I/O withstand voltage of each device allows this voltage (or level conversion is added), devices with different supply voltages (3.3V, 5V, 1.8V) can share the same bus. The open-drain output does not actively drive high level, so there will be no problem of two push-pull outputs fighting.

2. **Multiple host arbitration. ** When multiple master stations try to control the bus at the same time, it is judged by monitoring the SDA level. If it wants to send "1" (release SDA) but actually sees "0" on SDA (pulled low by another device), it means that another master station is driving at the same time. The result is that it fails arbitration and stops immediately.

The trade-off of the I2C pull-up resistor: too large a resistance → the rising edge is too slow (τ = Rpullup × Cbus), too small a resistance → the device needs to sink more current when it is pulled low (I_OL = VDD/Rpullup), which may exceed the I_OL capability of the device. The typical value of Rpullup is 4.7kΩ in standard mode and 2.2kΩ in fast mode.

**The ghost of I2C: rise time. **

Bus capacitance Cbus includes: pin capacitance of each device (~10pF/device), PCB trace capacitance (~3pF/cm), and connector capacitance. An I2C bus with 3 devices on a board and 10cm trace, Cbus is about 50pF.

Fill the bucket with water through a thin straw: the thickness of the straw is the resistance R, and the capacity of the bucket is the capacitance C. The time it takes for water to be filled from an empty bucket to a full bucket is the RC time constant. The rising edge of I2C is not instantaneous. It is an exponential curve of the pull-up resistor charging through the bus capacitance after the open-drain NMOS releases the bus. If the pull-up resistor is too large (the straw is too thin) and the curve rises too slowly, SDA will not reach the logic 1 decision threshold before the next clock edge of SCL, and the slave will not see "1".

Rise time t_rise = 2.197 × Rpullup × Cbus (from 10% to 90%).

- Rpullup=4.7kΩ, Cbus=50pF → t_rise ≈ 517ns. In standard mode (100kHz, period 10μs), no problem.
- Rpullup=4.7kΩ, Cbus=150pF (multiple devices, long traces) → t_rise ≈ 1.55μs. In fast mode (400kHz, period 2.5μs), the rising edge accounts for 62% of the period, and SCL may not reach the legal VIH (usually 0.7×VDD=3.5V) when it is high. The slave does not recognize logic 1.

This is the physical source of the slowness of I2C. It is not the protocol that stipulates the slowness, but the RC charging process of the open-drain output + pull-up resistor that "stipulates" the slowness.

## Penetration: Reading and writing I2C EEPROM through LPI2C on S32K

```c
// ========== LPI2C0 initialization ==========
// S32K144: LPI2C0 register base address = 0x40066000

#define LPI2C0_BASE  0x40066000

#define LPI2C_VERID   (*(volatile uint32_t *)(LPI2C0_BASE + 0x00))
#define LPI2C_PARAM   (*(volatile uint32_t *)(LPI2C0_BASE + 0x04))
#define LPI2C_MCR     (*(volatile uint32_t *)(LPI2C0_BASE + 0x10))  // Master Config
#define LPI2C_MSR     (*(volatile uint32_t *)(LPI2C0_BASE + 0x14))  // Master Status
#define LPI2C_MIER    (*(volatile uint32_t *)(LPI2C0_BASE + 0x18))  // Master Int Enable
#define LPI2C_MDMR    (*(volatile uint32_t *)(LPI2C0_BASE + 0x40))  // Master Data Match
#define LPI2C_MCCR0   (*(volatile uint32_t *)(LPI2C0_BASE + 0x48))  // Master Clock Config
#define LPI2C_MFCR    (*(volatile uint32_t *)(LPI2C0_BASE + 0x58))  // Master FIFO Control
#define LPI2C_MFSR    (*(volatile uint32_t *)(LPI2C0_BASE + 0x5c))  // Master FIFO Status
#define LPI2C_MTDR    (*(volatile uint32_t *)(LPI2C0_BASE + 0x64))  // Master Tx Data
#define LPI2C_MRDR    (*(volatile uint32_t *)(LPI2C0_BASE + 0x70))  // Master Rx Data
#define LPI2C_SCR     (*(volatile uint32_t *)(LPI2C0_BASE + 0x110)) // Slave Config

void lpi2c0_init_100khz(void)
{
    // Make sure the LPI2C0 clock is enabled in PCC (omitted)

    // 1. Reset module
    LPI2C_MCR = (1 << 1);  // RST=1
    while (LPI2C_MCR & (1 << 1));  // Wait for reset to complete

    // 2. Master mode enabled, no FIFO
    LPI2C_MCR = (1 << 0);  // MEN=1 (Master Enable)

    // 3. Configure clock: Set module clock=8MHz, target SCL=100kHz
    //    SCL = module clock / (CLKHI+1 + CLKLO+1 + SCL_LATENCY)
    //    Among them SCL_LATENCY ≈ 2 (filter glitch)
    //    Target SCL=100kHz; SCL=8MHz/(38+1+38+1+2)=100kHz
    LPI2C_MCCR0 = (38 << 0)       // CLKLO = 38
                | (38 << 8)       // CLKHI = 38
                | (3 << 24)       // DATAVD = 3 (data valid delay)
                | (3 << 16);      // SETHOLD = 3 (establish hold)
}

// ========== I2C Start Condition (Start) ==========
void i2c_start(uint8_t addr_rw)
{
    // The START command of LPI2C is written to MTDR together with the slave address
    while (!(LPI2C_MSR & (1 << 0)));   // Waiting for TDF
    LPI2C_MTDR = ((0x4 & 0x7) << 8) | addr_rw;  // CMD=START, DATA=address + read and write bits
}

// ========== I2C Stop Condition (Stop) ==========
void i2c_stop(void)
{
    while (!(LPI2C_MSR & (1 << 0)));   // Waiting for TDF
    LPI2C_MTDR = ((0x2 & 0x7) << 8);   // CMD=STOP
}
```

I2C Start condition: When SCL remains high, SDA is pulled from high to low. Behind the scenes, the SDA open-drain NMOS is turned on and the line is pulled to ground. The "Start condition" you see on the oscilloscope is a falling edge on SDA during the high period of SCL.

```c
// ========== I2C sends a data byte ==========
uint8_t i2c_write_byte(uint8_t data)
{
    // Waiting for transmit FIFO to be available
    while (!(LPI2C_MSR & (1 << 0)));  // TDF

    // Write data + send command CMD=TRANSMIT
    LPI2C_MTDR = (data & 0xff)
               | ((0x0 & 0x7) << 8);  // CMD=TRANSMIT DATA

    // Waiting for send FIFO to drain
    while ((LPI2C_MFSR & 0xf) != 0);

    // Read back ACK/NACK: MSR[NDF]=1 means NACK received
    if (LPI2C_MSR & (1 << 4))  // NDF = NACK detected
        return 1;  // NACK
    return 0;       // ACK
}

// ========== I2C receives a byte ==========
uint8_t i2c_read_byte(void)
{
    // Wait for FIFO to be available
    while (!(LPI2C_MSR & (1 << 0)));  // TDF

    // CMD=RECEIVE, DATA=0 → receive 1 byte; the last byte is automatically NACKed by hardware
    LPI2C_MTDR = ((0x1 & 0x7) << 8) | 0;

    // Waiting for the receive FIFO to have data (RDF = Receive Data Flag)
    while (!(LPI2C_MSR & (1 << 1)));  // RDF

    return (uint8_t)(LPI2C_MRDR & 0xff);
}

// ========== Complete I2C EEPROM read ==========
// Read a byte at address 0x00 of an EEPROM (such as AT24C02)
uint8_t eeprom_read_byte(uint8_t slave_addr, uint8_t mem_addr)
{
    uint8_t data;

    // --- Phase 1: Write operation → Send memory internal address ---
    i2c_start((slave_addr << 1) | 0x00);  // START + address + write
    if (i2c_write_byte(mem_addr)) {       // Send memory internal address
        // NACK, the slave is not on the bus
        i2c_stop();
        return 0xff;
    }
    // Note: EEPROM does not need STOP at this stage, but sends Repeated START

    // --- Phase 2: Read operation → receive data ---
    i2c_start((slave_addr << 1) | 0x01);  // Repeated START + address + read
    data = i2c_read_byte();               // Read one byte, the last byte is automatically NACKed by hardware
    i2c_stop();

    return data;
}

// ========== Usage example ==========
void example_eeprom(void)
{
    lpi2c0_init_100khz();
    uint8_t hi = eeprom_read_byte(0x50, 0x00);
    uint8_t lo = eeprom_read_byte(0x50, 0x01);
    uint16_t device_id = (hi << 8) | lo;  // 0x2026
}
```

**Behind this code, the state machine of the I2C controller samples SDA on each rising edge of SCL and updates SDA during the low level interval of SCL. ** The detection of the ACK bit is automatically completed by hardware. The LPI2C controller samples SDA on the rising edge of the 9th SCL pulse. If it is high (NACK), MSR[NDF] is set. Your code reads this flag to decide what to do next.

## Clock Stretching: "Wait a minute" from the slave

Some I2C slaves (including security chips such as NXP SE050) are not ready for the next byte when processing received data, so they will actively pull SCL low. The host must detect that SCL is pulled low, pause sending the next clock pulse, and wait for SCL to be released (go high) before continuing.

This is **Clock Stretching**. It's not a bug, it's behavior clearly defined by the I2C spec.

Here comes the practical problem: not every MCU's I2C controller handles clock stretching correctly. Software emulation of I2C often requires polling SCL; some thin hardware controllers may timeout when the slave stretches the clock. The LPI2C module of S32K supports clock extension. It automatically detects the actual level of SCL after each SCL is released, and enters wait when SCL is pulled low by the slave.

**If you adjust it all afternoon, I2C will stop every time after the slave address is sent: check the pull-up resistor first, and then check the clock extension. **

## Physical layer of SPI: signal integrity

The SCLK signal of SPI comes out from the MCU pin and reaches the peripherals through the PCB trace. What happens if this trace is too long?

**reflection. ** The characteristic impedance Z₀ of the trace is usually 50Ω (microstrip line) or 90Ω (differential pair). The output impedance of the MCU's output driver is usually 20-40Ω, which does not exactly match 50Ω. When the signal reaches the peripheral side, the input impedance of the peripheral is very high (usually >100kΩ), it is equivalent to an open circuit, and the signal is almost completely reflected back. The reflected wave is superimposed on the original signal, and a step-like "ringing" is seen on the MCU side. If the delay of the reflected wave is comparable to the SCLK period, the reflection of the previous bit will cause interference within the sampling window of the next bit.

For SPI above 20MHz and traces exceeding 5cm, it is recommended to add a 22-33Ω series termination resistor close to the peripheral end. The sum of this resistor and the driver output impedance is ≈50Ω, which matches the characteristic impedance of the wiring and absorbs reflections.

**Crosstalk. **MOSI and SCLK are adjacent traces. The fast transition of SCLK (edge ​​slope may reach 1-2V/ns) is coupled to MOSI through mutual capacitance and mutual inductance. If the MOSI data is disturbed near the SCLK sampling edge, the sampled bits may be wrong. Crosstalk doesn't kill the signal, it changes the value of the signal at the wrong moment.SPI also has its own crosstalk issues. SCLK is a high-frequency square wave, and a 20MHz clock means it flips every 25ns. Fast transitions on this line are coupled to the adjacent MISO or MOSI lines through the parasitic capacitance of adjacent traces on the PCB (approximately 0.5pF/cm). If you look at the MISO signal on an oscilloscope, you'll see a tiny spike on MISO every time SCLK transitions, and that's crosstalk. At low rates, this spike disappears quickly and does not affect data sampling. But at 20MHz, the spike may last half a clock cycle. Enough to cause the slave to misread a bit. Solution: Add a GND trace (protection trace) between SCLK and MOSI/MISO, or simply widen the trace spacing.

## SPI vs I2C: Two philosophies, one wisdom

| Dimensions | SPI | I2C |
|------|-----|-----|
| Number of lines | 4 (1 CS per slave) | 2 (shared by all devices) |
| Duplex | Full Duplex | Half Duplex |
| Speed | Dozens of MHz | 100k-3.4M |
| Output type | Push-pull | Open drain + pull-up |
| Protocol layer | No standard | Standard (address, ACK/NACK) |
| Multi-master | Not supported (hardware CS) | Supported (arbitration) |
| Number of slaves | CS pin number limit | Address space limit (7/10 bits) |
| Pin Efficiency | Poor | Good |
| Power consumption | High (push-pull continuous drive) | Low (high in static state) |

SPI and I2C were born in the 1980s. No one thought at the time: 40 years later, they would be running in every ECU in the car, with SPI connecting the MCU and the high-side driver, and I2C connecting the MCU and the security chip.

The philosophy of the SPI designer: **Simple, fast and flexible**, there is no fixed protocol, no device state machine, push-pull output can run very fast. But they pushed "error handling, protocol compatibility, device management" all to software developers.

The philosophy of I2C designers: **Minimum pins, shared bus, multi-master collaboration**, using only two lines to connect dozens of devices, and solving problems with low-cost PCB and low power consumption. The trade-off is slow speed, annoying pull-up resistor adjustments, and unwieldy clock extensions.

When you choose SPI or I2C, you are not comparing "which one is better", you are evaluating: How many pins are left? Is 100kbps enough? How many slave stations does one master station have? How long are the PCB traces? How many volts is the supply voltage? What is the power budget? Each constraint adds up to naturally lead you to a solution.

**There is no absolutely good technology, only the most appropriate solution under constraints. The choice of project is always a choice of context. **

## Summary

Today we did one thing: **understand the respective philosophies of SPI and I2C under the multiple constraints of pins, speed, power consumption, and PCB area. **

Key takeaways:
1. **SPI is a fast and expensive philosophy**: push-pull output, full duplex, no standard protocol, pushing complexity to software in exchange for speed. The price is that each additional slave requires one more CS line.
2. **I2C is a philosophy of saving and slow**: open-drain output, two-wire shared bus, standard address and ACK/NACK mechanism, minimal hardware complexity. The price is that the adjustment of the pull-up resistor is cumbersome and the speed is limited by the RC time constant.
3. **The choice is not which one is better, but which one is most suitable under the constraints**: How many pins are left? What is the speed requirement? How long are the traces? What is the power budget? Each constraint adds up to naturally lead you to a solution.
