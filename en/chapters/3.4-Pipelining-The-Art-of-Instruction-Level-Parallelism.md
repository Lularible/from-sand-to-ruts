# 3.4 Pipelining: The Art of Instruction-Level Parallelism

## Quartet in a fast food restaurant

You make a sandwich in a fast food restaurant. Four steps for each sandwich: cut bread (2 seconds) → spread sauce (3 seconds) → place fillings (4 seconds) → wrap (2 seconds).

If you do it from start to finish alone: ​​11 seconds per sandwich, 327 in an hour.

Now you hire 4 people and line them up in a row. The first person only cuts the bread and passes it to the second person to spread the sauce while the first person starts to cut off a piece of bread. The second person finishes coating and passes it to the third person to put the filling... and so on.

You still have to wait 11 seconds for the first sandwich, but starting with the second one, each sandwich only takes 4 seconds (the time for the slowest step).

After stabilization, the rate is 900 per hour, and the efficiency has nearly tripled.

You're not making anyone do it faster, you're not buying an extra knife. You just make use of the "waiting" time. This is the pipeline.

Of course, you can also choose to let 4 people make sandwiches independently, which will produce a higher output, but that requires 4 sets of tools and 4 versatile employees. The ingenuity of the assembly line is that it improves efficiency through process optimization alone without increasing resources.

## Classic five-level assembly line

David Patterson and John Hennessy established a five-stage pipeline in their classic MIPS processor, and most subsequent RISC processors followed this design:

1. IF (Instruction Fetch): PC driver address, fetch instructions from the instruction memory.
2. ID (Instruction Decode): Decode and read the source operand in the register file.
3. EX (Execute): ALU performs arithmetic/logical/address calculations.
4. MEM (Memory): access data storage (Load or Store).
5. WB (Write Back): Write the result back to the register file.

```
Clock period: 1 2 3 4 5 6 7 8 9
Instruction 1: IF ID EX MEM WB
Instruction 2: IF ID EX MEM WB
Instruction 3: IF ID EX MEM WB
Instruction 4: IF ID EX MEM WB
Instruction 5: IF ID EX MEM WB
```

After the 5th clock cycle, one instruction completes each cycle. Ideally, IPC (Instructions Per Cycle) = 1. Compared with a single-cycle processor, the throughput rate of the five-stage pipeline is increased by about 5 times, not by making a single instruction run faster, but by allowing multiple instructions to overlap in time.

ARM Cortex-M4 uses a three-stage pipeline (Fetch → Decode → Execute). So ideally it is also close to IPC=1, but in practice it cannot be achieved because overlap will cause conflicts.

## Use C to simulate a five-stage pipeline

Let us intuitively understand the operation of the pipeline by manually tracing the execution process of an instruction sequence in the pipeline. The following trace shows three core mechanisms: the pipeline registers (IF/ID, ID/EX, EX/MEM, MEM/WB) save the status of each instruction in each stage; the forwarding logic bypasses the results of the EX or MEM stage (ALU results or Load data) directly back to the ALU input of the EX stage, without waiting for WB to finish writing the register file; the bubble logic inserts a NOP when the Load-Use risk occurs, so that the instruction using the Load result can be used in the ID The stage waits for one more beat.

## Trace a sequence of instructions

Use this piece of ARM assembly to trace the precise behavior of the pipeline:

```asm
ADD R1, R2, R3       ; (1)
SUB R4, R1, R5       ; (2) ← RAW on R1
LDR R6, [R7, #4]     ; (3)
ADD R8, R6, R9       ; (4) ← Load-Use on R6
```

Cycle 1: Instruction(1) IF. There is only one person working on the assembly line.

Cycle 2: Instruction (1) ID, Instruction (2) IF.

Cycle 3: Instruction (1) EX (ALU is calculating R2+R3), instruction (2) ID (preparing to read R1 and R5), instruction (3) IF.

At this time, instruction (2) requires R1, but the value of R1 is being calculated by instruction (1) in the EX stage and has not yet been written back in the EX/MEM pipeline register. Forward path activation: The value of R1 is pulled directly from EX/MEM.alu_result back to the EX stage operand input of instruction (2), bypassing the register file, with zero bubbles.Cycle 4: Instruction (1) MEM (blank), instruction (2) EX (use the forwarded R1 value to make SUB), instruction (3) ID, instruction (4) IF.

Cycle 5: Instruction (1) WB (R1 is officially written to reg_file), instruction (2) MEM, instruction (3) EX (calculate R7+4 to obtain the effective address), instruction (4) ID (prepare to read R6 and R9).

At this time, instruction (4) requires R6, but it comes from Load instruction (3), and the data cannot be obtained until the end of cycle 6. If instruction (4) does not wait, it will enter EX at the beginning of the 6th cycle to use it. Forwarding logic cannot come to the rescue: the result of Load does not enter the MEM/WB pipeline register until the end of cycle 6, and the EX stage of instruction (4) starts requiring it at the beginning of cycle 6, inserting a bubble.

Cycle 6: Instruction (2) WB, instruction (3) MEM (read data from memory[addr]), instruction (4) ID (pause. Bubble).

Cycle 7: Instruction (3) WB, instruction (4) EX (use the forwarded R6 value to do ADD).

Cycle 8: Instruction(4) MEM.

Cycle 9: Instruction(4) WB.

This trace shows you: 4 instructions plus 1 bubble, taking a total of 9 cycles, IPC = 4 / 9 ≈ 0.44. Data hazards, especially Load-Use hazards, are one of the main reasons why actual IPC is lower than ideal IPC.

## The Price of Overlap: Three Adventures

Overlap is not free, and when multiple instructions are flying in the pipeline at the same time, "dependencies" can complicate things.

Assume that the CPU is executing the following three instructions:

```asm
ADD R1, R2, R3   ; R1 = R2 + R3
SUB R4, R1, R5   ; R4 = R1 - R5  ← RAW on R1
BEQ R1, R0, target ; if R1==R0 goto target
```

Trace these three instructions in the five-level pipeline:

Cycle 1: ADD IF, there is only one instruction flying in the pipeline.

Cycle 2: ADD ID, SUB IF.

Cycle 3: ADD EX (ALU is calculating R2+R3), SUB ID (need to read R1 and R5), BEQ IF.

At this time, SUB needs R1, but the final result of R1 has not yet been calculated in the EX phase of ADD. This is data hazard (RAW, or Read After Write). But ADD has already output R1 from the ALU at the end of the EX phase, and there is no need to wait for WB to finish writing the register file. The solution is forwarding/Bypassing: as soon as ADD calculates R1 in the EX phase, it immediately bypasses the input to the EX phase of SUB in the next cycle, bypassing the register file and creating zero bubbles.

Cycle 4: ADD MEM, SUB EX (subtract the forwarded R1 value), BEQ ID.

Cycle 5: ADD WB, SUB MEM, BEQ EX (determine whether to jump).

BEQ figures out in the EX phase (Cycle 5): To jump or not to jump? If it jumps, the instruction at the target address should be fetched in the 6th cycle. But there are already two sequential instructions in the pipeline in cycle 5: one in ID and one in IF. This is a control risk. If BEQ jumps, both of these must be flushed, and the pipeline will re-fetch instructions from the target, wasting two cycles. This is the branch penalty.

Finally, consider another situation: if SUB is a Store instruction (writes memory in the MEM stage), and BEQ reads the instruction memory in the IF stage at the same time. This is an architectural hazard if they share the same set of buses, and the Harvard architecture solves this problem with independent instruction/data buses. Most of the ARM Cortex-M series adopt Harvard architecture or modified Harvard (unified address space but independent bus interface), so structural risks are relatively rare on Cortex-M.

There are three instructions: ADD, SUB, and BEQ. Although there are only three, they show all three adventures of the pipeline. Let’s go into depth one by one below.

### Data Adventure: You haven’t finished yet, I already need itRAW (Read After Write) is the most common data hazard. In the five-stage pipeline, the WB of the first instruction does not finish writing R1 until the 5th cycle, but the second instruction requires the value of R1 in the EX stage of the 3rd cycle, which is a difference of two cycles. The other two types: WAW (Write After Write) and WAR (Write After Read), do not occur in the sequential pipeline (because there is no out-of-order writeback), but are a major problem in out-of-order execution.

Physically, the forwarding path is a set of wires added in front of a MUX. It leads out the alu_result field of the EX/MEM pipeline register and connects it to an additional input of the ALU input MUX. The control signals "forward_a" and "forward_b" determine whether the input to the ALU comes from the register file or the forwarding bus. This design has zero clock overhead, and forwarding operations and ALU operations are completed in the same cycle.

Cortex-M4 has forwarding logic, but not all risks can be solved by forwarding alone. The Load instruction only gets the data in the MEM stage, and the user who follows it (Load-Use adventure) must first insert a bubble, let the pipeline idle for a beat, and then forward the MEM/WB data to the next instruction.

### Control the adventure: Did you guess the right direction?

The branch instruction only knows whether to jump or not in the EX stage. But before that, two subsequent instructions have entered the IF and ID stages. If a branch occurs, these two items must be flushed.

```
Clock period: 1 2 3 4 5 6
B command: IF ID EX MEM WB ← Only in the third cycle will we know whether to jump or not.
Next chapter: IF ID X X ← has been fetched, but was cleared after the ID
Target: IF ID EX
```

Cortex-M3 uses static branch prediction to alleviate this: always assume that a backward jump (`BEQ back`) will jump (because it is usually a loop), and a forward jump will not jump (because it is usually an if-else).

But this is a "static" forecast. Treat all backward jumps equally. Dynamic branch prediction is different, it learns the past behavior of each branch instruction.

### Prediction of 2-bit saturation counter

The simplest dynamic predictor is a 2-bit saturating counter. Each branch instruction has a corresponding 2-bit status in the BTB (Branch Target Buffer):

```
  Strong does not jump. Weak does not jump. Weak jumps. Strong jumps.
  [00]  ──jump──→ [01]  ──jump──→ [10]  ──jump──→ [11]
   ↑                │                ↑                │
   └──hold──────────┘                └──hold──────────┘
```

States 00 and 01 predict "no jump", and states 10 and 11 predict "jump". When the branch actually occurs, the state moves to the right; when it does not, it moves to the left.

Effect: For a branch that strictly alternates jumps/no jumps, the 2-bit counter will make an error of about 50%; but for a branch that always jumps (99% loop body), the prediction accuracy is close to 100%.

### Tournament Predictor and Return Address Stack

Modern high-performance CPUs (Cortex-A series) use more complex solutions:

Tournament Predictor: Run two predictors simultaneously. One is based on local history ("How has this branch been in the past few times"), one is based on global history ("What is the overall pattern of all recent branches"), and then a third-party "selector" is used to dynamically learn which predictor is more accurate. Intel introduced a similar solution in later high-performance microarchitectures, and it is still one of the mainstream ideas for high-performance branch prediction.

Return Address Stack (RAS): The return address stack (RAS) is an extremely small hardware stack, usually only 8-16 entries deep. When the CPU executes a BL (function call) instruction, the hardware automatically pushes the return address (current PC+4) into RAS. When executing a BX LR (function return), the CPU does not guess the target address from the branch predictor, it pops it directly from the top of the RAS stack. Because function calls and returns are strictly paired, RAS's prediction accuracy exceeds 99% in most codes. This 8-item micro-stack is embedded next to the fetch unit, only a few tens of microns away from the assembly line. Every function call and return you make in C code is talking to this hardware structure smaller than the diameter of your hair.

### Structured Adventure: Two Instructions, One ResourceOccurs when two instructions require the same hardware resource at the same time. As mentioned before, the Harvard architecture naturally solves the bus conflicts between fetching and Load/Store. But in high-performance out-of-order execution CPUs, structures risk returning to the stage, not because of bus conflicts, but because of conflicts in execution units (execution ports). If the CPU has only two integer execution ports and 3 integer instructions are ready at the same time in the same cycle, then one must wait.

## Out-of-order execution: let ready instructions go first

The essence of the pipeline is "time overlap", which splits the execution process of an instruction into multiple stages, allowing different stages of different instructions to overlap in time, thereby improving the overall throughput rate.

However, this efficiency is based on the premise that instructions are independent of each other. If you can only issue instructions sequentially (that is, feed the pipeline one by one in program order), then once an instruction is stalled due to data dependencies or resource conflicts, the entire pipeline will be blocked, even if the instructions following it do not depend on the blocked instruction at all.

It's like queuing up in front of a self-service code scanning checkout machine in a supermarket: the previous customer has finished scanning all the products, but when it's his turn to pay via mobile phone, the payment page cannot be displayed due to poor mobile phone network. All the people in line at the back, even if they only bought a bottle of water, were stuck waiting in place.

Out-of-Order Execution breaks the order restriction. Core idea:

1. Launch: Instructions enter the reorder buffer (ROB) in program order.
2. Readiness detection: Each instruction monitors whether its source operand is ready. Once ready, enter the execution unit.
3. Complete: The execution results are written to the ROB entry, but not written back to the register file.
4. Retire: When the instruction reaches the ROB head, its result is officially written to the architectural register file, and the ROB entry is released.

In the middle of the ROB, instructions are executed out of order, whichever one is ready first goes first. But at the end of the ROB (retirement end), they are submitted strictly in program order, ensuring precise exceptions: if a page fault occurs in instruction 3, instructions 1 and 2 have been retired and the results are visible, but instructions 4 and 5 will not be retired even if they have been executed. They will be discarded and the program state will return to before instruction 3.

Register Renaming is a prerequisite for out-of-order execution. If instruction 1 writes R3 and instruction 5 also writes R3, this is a WAW adventure. The solution is: map R3 to a different physical register in a physical register pool. Instruction 1 actually writes to P23, and instruction 5 actually writes to P41. Instruction 2-4 If R3 is read, is P23 or P41 being read? Depends on their position in the program sequence. The hardware rename table keeps track of which physical register currently holds the latest value of architectural register R3.

Out-of-order execution + register renaming + forwarding logic + branch prediction, these are the four pillars of modern high-performance CPUs.

## Physical limits of the pipeline

The number of pipeline stages is limited by the critical path delay of each stage. The critical path delay is limited by the drive capabilities of the transistors and the RC delay of the interconnect lines.

By splitting the 5-stage pipeline into 15 stages, the critical path of each stage becomes shorter. A single stage only needs to do 1/3 of the original work, and the clock frequency can be increased to nearly 3 times. This is the Pentium 4 idea: 31-stage pipeline, target frequency 10GHz.

But there are three physical costs for an overly deep pipeline:

1. The overhead of pipeline registers: for each additional level of pipeline, a set of D flip-flops (dozens to hundreds) must be inserted. The clock frequency is increased, but each flip-flop is flipping, causing dynamic power consumption to rise linearly. In deeply pipelined designs like the Pentium 4, the pipeline registers themselves account for a significant portion of the power consumption.2. The interconnect RC delay does not scale with the transistor: from 90nm to 28nm, the transistor gate delay is reduced to about 1/3~1/4 (the speed is increased by about 3-4 times). But the resistance per micron of the top metal changes little (copper's resistivity is a physical constant), while shrinking line spacing increases capacitive coupling. By the 7nm node, interconnect delay has surpassed gate delay as the dominant factor in the critical path. No matter how deep you add the pipeline, the delay of the data transfer itself cannot be "pipelinized" because the data must physically move between the two levels of registers.

3. Branch prediction failure penalty: In the worst case, a 31-stage pipeline may bring about a flush penalty of about 31 cycles. Assuming a branch ratio of 20% and a prediction accuracy of 95%, the effective IPC = 1 / (1 + 0.2 × 0.05 × 31) = 1 / 1.31 ≈ 0.76. The worst case scenario for an 8-stage pipeline is 8 cycles based on the same calculation. Effective IPC = 1 / (1 + 0.2 × 0.05 × 8) = 1 / 1.08 ≈ 0.93. The deeper the pipeline, the greater the loss of branch prediction failure, and the more the actual gains are eroded.

This is why after Pentium 4, Intel abandoned the deep pipeline route and turned to the Core microarchitecture (14-stage pipeline). This is also the fundamental physical reason why ARM’s Cortex-A series has stabilized between levels 8-15 and has not continued to deepen.

## Determinism vs Performance: Pipelining in Real-Time Systems

Your engine controller needs to complete combustion calculations within a fixed time window. The crankshaft position sensor triggers an interrupt every tooth revolution. At 6000 RPM, each tooth is spaced approximately 0.1 to 0.2 milliseconds apart. Your ISR (Interrupt Service Routine, interrupt service routine) must complete within a few microseconds.

Now consider the impact of the pipeline: branch prediction may be wrong, data forwarding may introduce uncertain bubbles, and the number of Flash access wait cycles may vary under different voltages and temperatures.

For hard real-time systems, determinism is more important than peak performance.

That’s why the ARM Cortex-R series (for functional safety real-time control) has these special designs:

- Tightly coupled memory (TCM): Unlike Cache, the contents of TCM are explicitly managed by software, and there is no uncertainty about cache misses. ISR code and data are locked directly in the TCM, and access latency is deterministic single cycle.
- MPU (Memory Protection Unit): It is not an MMU, does not involve the uncertain delay of page table translation, and uses fixed area protection attributes for memory isolation.
- Lockstep dual-core (Lockstep): Two Cortex-R5 cores run the same code, and the hardware compares their outputs at the cycle level. If one core makes an error, the other will detect it immediately.

One more key point: Cortex-R5 can disable branch prediction. For security-critical code paths, certainty trumps all else. If branch prediction brings unpredictable flush delays, it is better not to use them at all and let the branches adopt a fixed static strategy (always not-taken), and the delays can be accurately calculated. The core requirement of WCET analysis is that "the execution time of each piece of code has a certain upper bound." If the branch prediction has a non-negligible probability of being missed, WCET must assume that it misses every time. The WCET calculated in this way is larger than the static strategy, and disabling branch prediction is better.

## Time overlap: from CPU to distributed system

The essence of the pipeline is simple: break a large task into small steps so that the steps of multiple instructions overlap in time. It didn't change more resources, it just used the idle hardware.

This is actually the common design logic of all efficient systems:- CPU pipeline: one instruction is being executed, the next instruction is being decoded, and the next instruction is being fetched, achieving time overlap.
- DMA: The CPU is calculating and the DMA is moving numbers to achieve time overlap.
- The hardware buffer of the CAN controller: the CPU is sending the Nth frame, and the CAN controller is receiving the N+1th frame, achieving time overlap.
- FreeRTOS task switching: When a task is suspended by I/O, another ready task immediately preempts it to achieve time overlap.

The extent to which the system you design takes advantage of time overlap is the extent to which the capabilities of the hardware are utilized.

But "overlap" comes at a cost, namely hazards. The essence of the risk is the inconsistency of information caused by parallel execution. You have to design forwarding logic, bubble cleaning, and arbitration mechanisms. This is completely isomorphic to the logic of designing time synchronization in distributed systems (such as CAN networks): Highly overlapping work of each ECU (sending messages at the same time) → conflict (resolved by CAN ID arbitration) → time drift (resolved by PTP synchronization).

From CPU pipeline adventures to time drift in distributed systems, "management overlap" is the projection of the same type of problem at different scales.

### Guarantee is more important than optimal

When running hard real-time tasks (ABS, steering, engine management) in your designs, the pipeline is your assistant. But always remember: its "best case" is not its "guaranteed case".

What you write is brake control code, not "it can come in time in most cases", but "it must come in time every time". Pipeline worst-case execution time (WCET) analysis requires you to assume that all cache misses, all branch prediction failures, and all load-use bubbles will occur on the worst path.

This is the most fundamental difference between automotive embedded software and Internet software: they want "peak performance", and you want "worst-case guarantee".

## Summary

Today we did one thing: we understood the pipeline, split large tasks into small steps, and allowed multiple instructions to overlap in time.

Key takeaways:
1. The five-level pipeline makes the IPC close to 1: IF→ID→EX→MEM→WB. After the 5th cycle, one instruction is completed per cycle. This does not make a single instruction faster, but allows multiple instructions to overlap.
2. The three types of risks are overlapping costs: data risks are solved by forwarding, control risks are mitigated by branch prediction, and Load-Use risks must be inserted into bubbles before forwarding. The actual IPC is always lower than 1.
3. Hard real-time systems require determinism, not peak performance: WCET analysis assumes all cache misses and all branch prediction failures. The brake code must come in time every time.
