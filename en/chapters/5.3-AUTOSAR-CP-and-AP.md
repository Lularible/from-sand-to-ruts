# 5.3 AUTOSAR CP and AP

## 2003, a decision in a conference room

In 2003, a group of European OEM and Tier-1 representatives sat in a conference room. The topic is very straightforward:

“We need a standard, a common framework for automotive ECU software.”

The situation at that time was a mess. Each Tier-1 supplier develops ECU software individually for each OEM. Peugeot-Citroen's engine controller and Volkswagen's engine controller hardware can be exactly the same (for example, both use Infineon TriCore or Renesas RH850), but the software is completely incompatible.

The same CAN driver needs to be rewritten five times, the same diagnostic stack needs to be rewritten five times, and the same safety components (WDOG, MPU, lockstep core management) need to be repeated five times.

**This is the root cause of software cost inflation. ** It’s not that engineers don’t work hard, it’s that they start from scratch every time.

Attendees agreed: define a standard, layered decoupling. Hardware-independent application layers can be reused on different ECUs. The basic driver layer, communication stack, and operating system are packaged once and used on all ECUs.

This standard is called **AUTOSAR** (AUTomotive Open System ARchitecture).

---

## Blueprint: The layered universe of AUTOSAR Classic Platform (CP)

CP targets ECUs with high real-time performance and limited resources: engines, gearboxes, ABS, EPS, BCM, etc. The OS is an OSEK/VDX compliant real-time kernel.

Imagine a building with five floors from top to bottom:

| Layer | Name | Role |
| :--- | :--- | :--- |
| Layer 5 | **Application Layer (SWC)** | Independent application logic: torque control, wheel speed calculation, without touching any hardware |
| Layer 4 | **RTE** | SWC's "software bus", connecting data exchange between SWCs |
| Layer 3 | **Services** | System status management, storage service (NvM), communication service (Dcm/Com) |
| Layer 2 | **ECU abstraction layer** | Abstracts microcontroller peripherals into high-level interfaces, CAN Interface is here |
| Layer 1 | **MCAL** | Directly manipulate hardware registers: GPIO, ADC, PWM, SPI, CAN, GPT |

There is also a special layer: **Complex Drivers**, used for special hardware that cannot be fit into the standard framework: analog signal conditioning of wheel speed sensors, precise timing control of engine injection chips.

Key principles:
- SWC does not have direct access to BSW or hardware, it can only operate via RTE.
- The sending call direction between BSW layers is generally downward: Com → PduR → CanIf → Can; only diagnostic/segmentation messages pass through CanTp (PduR → CanTp → CanIf).
- Each layer primarily accesses the layers below it; the receive and acknowledgment paths are notified upward via callbacks (e.g. CanIf_RxIndication, Com_RxIndication).

## Standing at the bottom: MCAL’s CAN driver

MCAL is the main contact point between the standard software stack and the hardware. It directly reads and writes peripheral registers (complex drivers can also directly access special hardware). MCAL is generally provided by chip manufacturers. If you are an ECU integration engineer, you usually do not modify the MCAL code, but you must understand its interface.

A simplified CAN driver MCAL module looks like this:

```c
/* Can.h - MCAL CAN driver interface (simplified) */
#ifndef CAN_H
#define CAN_H

#include "Can_Types.h"

/* Initialize CAN controller */
void Can_Init(const Can_ConfigType *config);

/* Send a frame of CAN message */
Std_ReturnType Can_Write(Can_HwHandleType hoh, const Can_PduType *pdu);

/* Receive interrupt callback, call by Can driver, notify the upper layer (actually declared in CanIf_Cbk.h) */
void CanIf_RxIndication(const Can_HwType *mailbox, const PduInfoType *pduInfo);

/* Send confirmation callback (actually declared in CanIf_Cbk.h) */
void CanIf_TxConfirmation(PduIdType pduId);

#endif /* CAN_H */

/* Can.c - MCAL CAN driver implementation (simplified) */
void Can_IrqHandler(uint8_t controller_id)
{
    Can_PduType rx_pdu;
    Can_HwType rx_mailbox;
    PduInfoType pdu_info;
    uint32_t rx_data[2];

    /* Read from the receive FIFO of the hardware CAN controller */
    rx_pdu.id = CAN0->sFIFOMailBox[0].RIR >> 21;
    rx_pdu.length = CAN0->sFIFOMailBox[0].RDTR & 0x0f;

    uint32_t *src = (uint32_t *)&CAN0->sFIFOMailBox[0].RDLR;
    uint32_t *dst = rx_data;
    dst[0] = src[0];
    dst[1] = src[1];

    CAN0->RF0R |= CAN_RF0R_RFOM0;

    /* MCAL only reports the hardware mailbox and original ID; ID→PDU matching is in CanIf */
    rx_mailbox.CanId = rx_pdu.id;
    rx_mailbox.Hoh = 0;  rx_mailbox.ControllerId = controller_id;

    /* Construct PduInfo */
    pdu_info.SduDataPtr = (uint8_t *)rx_data;
    pdu_info.SduLength  = rx_pdu.length;

    /* Notify the upper level that this is the only exit from MCAL */
    CanIf_RxIndication(&rx_mailbox, &pdu_info);
}
```

Note that `CanIf_RxIndication`, MCAL does not route data, it just reads it from the hardware, packages it, and hands it to the upper layer. Routing is a matter of the upper layer.

## Trace: the complete journey of a CAN message from the physical bus to the application logicAssume that SWC "VehicleSpeed" reads the vehicle speed signal from the CAN bus, and let this message take you through the five-story building of AUTOSAR.

**Layer 1: MCAL (CAN Driver)**

When the hardware CAN controller's receive FIFO is full, a CAN receive interrupt is triggered. `Can_Irq.c` in MCAL reads the frame from the hardware register and calls `CanIf_RxIndication()` to notify the upper layer that a message has arrived.

**Layer 2: CAN Interface (CanIf)**

What `CanIf_RxIndication()` does:
- Match the received CAN ID to the PDU ID defined in the configuration table.
- Copy the 8-byte data of the CAN frame to the PDU buffer.
- Call `PduR_CanIfRxIndication(pduId, &pduInfo)`.

**Layer 3: PDU Router (PduR)**

PDU Router is the switch of the communication stack. A PDU comes up from CanIf, and PduR determines which upper-layer module to route to based on the configuration of the PDU ID. For normal signal frames (not diagnostics, not TP segments), PduR calls `Com_RxIndication(pduId, &pduInfo)` directly.

**Tier 4: Com Stack (Com)**

The Com module is responsible for unpacking the raw byte stream of the PDU into independent signals. This is the layer in the entire communication stack that best embodies the AUTOSAR design philosophy: complete decoupling of signals and frames. 

In bare-metal programming, you parse CAN frames directly:

```c
/* Bare metal method: manual bit mask extraction */
uint16_t speed_raw = can_data[0] | (can_data[1] << 8);
float speed = speed_raw * 0.05625f;
```

In AUTOSAR, Com's generated code compiles the signal definitions in ARXML into a static table, and automatically completes signal extraction according to the table at runtime:

```c
/* Com_SignalProcessing.c - Com signal extraction (simplified) */
void Com_RxIndication(PduIdType pduId, const PduInfoType *pduInfo)
{
    ComPduIdType comPduId = Com_PduIdFromRouting(pduId);
    const ComSignalConfig_t *signals = Com_GetSignalsForPdu(comPduId);

    for (uint16_t i = 0; i < signals->num_signals; i++) {
        const ComSignal_t *sig = &signals->signals[i];
        uint8_t *data = pduInfo->SduDataPtr;

        /* Extract the original value of the signal from the PDU byte stream */
        uint64_t raw = Com_ExtractBits(data,
                                        sig->bitPosition,
                                        sig->bitSize,
                                        sig->format);

        /* Physical value conversion */
        float physical = (float)(int64_t)raw * sig->factor + sig->offset;

        /* Update the RTE buffer (suggestion: the real interface is generated by the RTE generator by port) */
        Rte_Write_Signal(sig->handle, &physical);
    }
}

/* Bit extraction function, handles crossing byte boundaries and sign extension (here according to little endian/Intel layout) */
uint64_t Com_ExtractBits(const uint8_t *buffer,
                          uint16_t bitPos, uint8_t bitSize,
                          Com_Format_t format)
{
    /* Calculate starting byte and bit offset */
    uint16_t byteIdx = bitPos / 8;
    uint8_t  bitOff  = bitPos % 8;

    /* Read and concatenate by bytes, supporting crossing byte boundaries */
    uint64_t value = 0;
    for (uint8_t i = 0; i < (bitSize + bitOff + 7) / 8; i++) {
        value |= (uint64_t)buffer[byteIdx + i] << (i * 8);
    }
    value >>= bitOff;
    value &= (1ULL << bitSize) - 1;

    /* Sign extension: if the highest bit is 1 and the signal is signed */
    if (format == COM_SIGNED && (value & (1ULL << (bitSize - 1)))) {
        value |= ~((1ULL << bitSize) - 1);
    }

    return value;
}
```

This code is the fundamental reason for the existence of the Com layer. There may be 500+ CAN signals in an ECU, spread across 50+ PDUs. Letting each SWC application engineer manually parse the byte stream is not only inefficient, but also a breeding ground for bugs, because a bit offset error in the signal layout may cause incorrect data to be distributed to all subscribed SWCs.

Com uses a configuration-driven approach to achieve once-and-for-all signal extraction: the configuration is defined in ARXML, Com's generation code is automatically generated based on the configuration, and application engineers never need to write bit masks.

**Tier 5: RTE and SWC**

RTE is "the world" as SWC sees it. For SWC, the hardware does not exist, CAN does not exist, Flash does not exist, there is only RTE: a set of ports that can be read and written.

```c
/* SWC: VehicleSpeed_Implementation.c */
#include "Rte_VehicleSpeed.h"

/* This Runnable is triggered periodically by RTE, which schedules it according to the OS schedule */
void VehicleSpeed_MainFunction(void)
{
    float speed = 0.0f;
    boolean over_speed = FALSE;

    /* Read the port through RTE, behind which is the signal value provided by the Com layer */
    Rte_Read_SpeedValue_VehicleSpeed(&speed);

    /* Application logic: overspeed judgment */
    if (speed > 120.0f) {
        over_speed = TRUE;
    }

    /* Write to the output port through RTE, which is responsible for routing the value to the subscribed SWC */
    Rte_Write_OverSpeedWarning_VehicleSpeed(over_speed);

    /* If you need to trigger diagnosis, call RTE's client-server interface */
    if (over_speed) {
        Rte_Call_SetEventStatus_OverSpeedMonitor(DTC_OVERSPEED, TRUE);
    }
}
```

The implementer of SWC does not need to know "where the vehicle speed signal comes from": is it a signal in the CAN frame? Is it read directly by the SPI sensor? Is it calculated internally? Is it coming from another chip via Ethernet? SWC doesn't care. It only recognizes RTE ports. This is the highest level of AUTOSAR layered decoupling.

Entire path: Physical CAN Bus → MCAL Interrupt → CanIf Match → PduR Routing → Com Unpacking → RTE Distribution → SWC Calculation. **Each layer only does one thing, and each layer only knows the adjacent layers. **

## ARXML: The soul of AUTOSAR - using configuration instead of code

The Com signal extraction above is not hard-coded, but configured. The essence of AUTOSAR is not in the C code, but in the **ARXML** file. ARXML is the configuration language of AUTOSAR, which uses XML to describe each configurable parameter of the ECU software.

A simplified ARXML diagram of a CAN signal (omitting outer AR-PACKAGE/ELEMENTS and other structures):

```
<!-- Signal: vehicle speed, 16-bit unsigned, Little-Endian, bit offset 0 -->
<Signal name="ComSignal_VehicleSpeed">
  <bitPosition>0</bitPosition>
  <bitSize>16</bitSize>
  <endianness>LITTLE_ENDIAN</endianness>
  <type>UINT16</type>
</Signal>

<!-- IPDU: The receiving PDU to which the vehicle speed signal belongs -->
<IPdu name="ComIPdu_VehicleSpeedPdu">
  <signalRef>/ComSignal_VehicleSpeed</signalRef>
  <direction>RECEIVE</direction>
</IPdu>

<!-- Physical value conversion: raw × 0.05625 + 0.0, range 0-350 km/h -->
<CompuMethod name="ComSignal_VehicleSpeed_CompuMethod">
  <factor>0.05625</factor>
  <offset>0.0</offset>
  <lowerLimit>0.0</lowerLimit>
  <upperLimit>350.0</upperLimit>
</CompuMethod>
```This XML tells the BSW configuration generator (such as Vector DaVinci Configurator or EB tresos Studio):
- "Vehicle Speed Signal" is a 16-bit unsigned integer in Little-Endian order, starting at bit 0 of the PDU.
- Physical value = original value × 0.05625.
- The valid range is 0-350 km/h; values ​​outside the range can be filtered by Com or marked as invalid. Whether to report to Dem (diagnostic event manager) is determined by the application/monitoring module.

**BSW configuration generator reads this XML and generates the corresponding C code data structure: ComSignal configuration structure, signal extraction parameter table. ** This is AUTOSAR's transformation from "hand-written code for each project" to "configuration-driven generated code". Your hands no longer touch bit masks, you describe what you want, and the tool generates code that serves you.

## Another face of AUTOSAR: Adaptive Platform (AP)

The CP is designed for classic real-time ECUs, the OS is OSEK/VDX, the configuration is static and all tasks and communication schedules are fixed at compile time.

But cars are changing. ADAS domain controller, autonomous driving platform, V2X communication unit, these ECUs require:
- Powerful computing power (multi-core CPU, GPU, AI accelerator)
- Dynamic deployment: tasks can be started or stopped at runtime
- Service discovery: SOME/IP protocol allows newly added components to be automatically discovered
- OTA upgrade: partial firmware update without affecting the entire vehicle

AP uses **POSIX operating system** (Linux, QNX) instead of OSEK/VDX. Support C++ instead of pure C. ARA (AUTOSAR Runtime for Adaptive Applications) replaces RTE and provides service-oriented communication.

```
Application (C++) → ARA → Foundation Services → POSIX OS → Hardware
```

In the AP, the communication between SWCs is not fixed "port read/write", but **Service Invocation** (Service-Oriented Architecture, SOA). A SWC announces the services it provides to the network through the SOME/IP protocol when starting, such as "ADAS_SensorFusion provides SensorData service". Another SWC finds this service through the service discovery mechanism of SOME/IP, establishes a TCP/UDP connection, and starts subscribing to the data stream.

**SOME/IP service discovery process:**

```
ECU-A (provider) ECU-B (consumer)
    |                                    |
    |  Offer Service (SensorData, UDP)   |
    |  ─────────────────────────────>    |  (multicast to subnet)
    |                                    |  "Someone provide SensorData? I want it."
    |                                    |  Subscribe (SensorData, UDP)
    |  <─────────────────────────────    |
    |  "OK, let’s start sending you data."               |
    |  SensorData stream (UDP/TCP) ====>  |
```

CP is statically configured, AP is dynamically configured. CP is oriented towards high determinism, and the priority and schedule of each OS task are fixed at compile time. AP is designed for high flexibility, and ADAS functions can be dynamically deployed, dynamically upgraded, and dynamically associated while the vehicle is driving.

A high-end car runs both CP (Engine Control) and AP (Autonomous Driving Perception). Both worlds coexist behind the same CAN gateway, with the CP side of the gateway processing real-time CAN/CAN-FD messages and the AP side providing vehicle status data to ADAS applications via SOME/IP.

## Your real workflow on real chips

Assuming your hardware is **SPC58NN84** (Power Architecture e200 core, lockstep), you need to integrate a complete AUTOSAR CP stack on it. A typical workflow has five stages.

**Phase 1: MCAL configuration. ** Configure MCAL modules: CAN, SPI, GPT, ADC in Tresos Studio (EB) or ISOLAR (Vector). This step generates MCAL configuration parameters, telling the driver the specific settings of each peripheral. For example CAN controller configuration: baud rate, CAN ID filters per mailbox, receive/transmit type.**Phase 2: BSW configuration. ** Configure ECU state management (EcuM), communication stack (Com/PduR/CanIf/CanTp), and diagnostic stack (Dcm/Dem). The parameters of each module are defined through ARXML files. The BSW configuration generator translates ARXML into C configuration structures: you link at compile time, rather than parsing the XML at runtime.

**Phase 3: RTE configuration. ** Based on the description of the SWC (what ports the SWC has, whether the port is transmit or receive, what is the data type), the RTE generator generates `Rte_<SWC>.h` and `Rte_<SWC>.c` for each SWC. These generated files map SWC port reads and writes to Com signals, NvM storage blocks, or operating system events.

**Phase 4: SWC writing. ** Application engineers only write the logic code of SWC (C language or MATLAB/Simulink automatic code generation) without touching any underlying layers. In the world of SWC, there are only `Rte_Read_xxx()`, `Rte_Write_xxx()`, and `Rte_Call_xxx()`. These are the only operations the SWC can do.

**Phase 5: System integration. ** Compile and link each part: SWC object file, RTE generation file, BSW configuration generation file, MCAL and OS, then burn it into the ECU and run the integration test.

**Key Benefits:** When you change to another chip platform, such as from SPC58NN84 to Infineon TC399, the application SWC and most of the BSW can be reused. Mainly need to redo MCAL configuration (different peripheral register mappings for different chips) and OS configuration (different number of cores, different interrupt controllers). This significantly reduces Tier-1 development costs and ensures software consistency across OEMs and hardware platforms.

## Standard: Not restraint, but release

In the era before AUTOSAR, each Tier-1 and OEM worked in their own silo. Good engineers make good systems, but their knowledge and code cannot be passed on or reused. The field of automotive electronics software is like a "small farmer economy": each company is doing its own thing, working hard but inefficiently.

What AUTOSAR does is **industrial standardization**. Breaking ECU software into hierarchical, modular, configurable components is like ISO standardizing the thread specifications of screws. This way:

- Chip manufacturers can only do MCAL and not worry about the upper-layer application logic.
- Tier-1 can reuse application SWC across platforms and OEMs.
- OEMs can bid across different Tier-1s without fear of being locked into a certain vendor’s proprietary platform.

**Standardization does not constrain creativity, but releases greater creativity. ** When you don’t have to rewrite the CAN driver for each ECU, your energy can be used on more advanced issues: energy management in hybrid mode, ADAS sensor fusion algorithm, safety architecture for OTA upgrade.

Looking back at the path taken in this chapter:

1. **Bare Metal**: One person controls everything. Simple, flexible, and non-scalable.
2. **RTOS**: Introduce task scheduling and communication mechanism under limited resources. Scalability is improved, but stronger system design capabilities are required.
3. **AUTOSAR**: industrialization, standardization, and cross-platform reuse. Unleash the scale effect of the entire industry.

Your work at any of these stages is part of the progress of civilization in this industry.

But the ECU can not only "run", it also can "talk". When something goes wrong with it, it needs to be able to tell the maintenance technician: What's wrong with me, when it's wrong, and what contextual data comes with it.

This is diagnostics, UDS: Unified Diagnostic Services.

## Summary

Today we did one thing: understand how AUTOSAR unpacks a frame of 8-byte messages on the CAN bus into a signal read by Rte_Read() in SWC through industrial standardization, and how this standardization releases the scale effect of the entire industry. Key takeaways:
1. **AUTOSAR is not "another big framework", but an industrial standardization of ECU software**: splitting ECU software into hierarchical, modular, and configurable components, just like ISO standardizes screw threads. The CAN driver is written once, the diagnostic stack is written once, and the safety component is encapsulated once. Cross-platform reuse.
2. **CP (classic platform) and AP (adaptive platform) divide the two worlds of automotive electronics**: CP is oriented to real-time MCU (deterministic delay, static configuration), and AP is oriented to high-performance MPU (POSIX OS, dynamic service discovery).
3. **AUTOSAR has evolved from the "manual economy" of bare metal and RTOS to the "industrial economy"**: Application engineers only write SWC logic code and do not touch any underlying layers. When changing chip platforms, MCAL and OS are mainly reconfigured. The freed-up energy can be directed toward higher-value system-level issues.
