# 5.1 Bare-Metal Programming: One Person Rules the World

## That late night without an operating system

Do you still remember the late night when you first wrote an embedded bare metal program?

There is no operating system, no threads, no `printf` (the UART has not been tuned yet). There is only one MCU, one reset vector, and a blank main loop.

You write a `while(1)` in `main()`, and execute several functions sequentially in it: read the sensor, do calculations, update the output, and wait for the next loop. The LED lights up and you almost tip over the breadboard with excitement.

After running for a few days, you find that occasionally one sensor data cannot be read. You examine the SPI waveforms and discover that the read operation conflicts with another interrupt service routine, an ISR operating another peripheral on the same SPI bus at the same time.

In the world of bare metal programming, you alone control everything. But it also means: **You are the only one who is responsible for all the problems. **

---

## Super Cycle: One `while(1)` can carry the whole world

The core of the bare metal system is a structure called **Super Loop**. It is the mother of all embedded software, and the RTOS scheduler essentially evolved from the hyperloop.

Let's look at a complete bare metal system: an engine intake air temperature monitoring unit (this section takes STM32F407 as an example. The following register configuration and clock tree parameters are given in the STM32F407 reference manual. For different models, packages or library versions, please refer to the corresponding RM):

```c
#include "stm32f4xx.h"

/* Global variables, shared communication channels in the bare metal world */
volatile uint16_t g_intake_temp_raw;    /* ADC raw value */
volatile float    g_intake_temp_degc;   /* Celsius temperature */
volatile uint8_t  g_can_tx_flag;        /* CAN send request flag */
volatile uint32_t g_system_ticks;       /* 1ms system beat count */

/* Sensor data table: NTC thermistor R-T lookup table (indicative value, actual device R-T table shall prevail) */
static const uint16_t ntc_lut[101] = {
    /* -40°C to +125°C, one point every 1.65°C; only the first few items are shown here */
    [0]=3950, [1]=3720, [2]=3500, /* ... 101 items in actual projects ... */
};

static void system_clock_init(void)
{
    RCC->CR |= RCC_CR_HSEON;
    while (!(RCC->CR & RCC_CR_HSERDY));
    /* HSE 8MHz → PLL → SYSCLK 168MHz，APB1 42MHz */
    RCC->PLLCFGR = (8U << RCC_PLLCFGR_PLLM_Pos) | (336U << RCC_PLLCFGR_PLLN_Pos) |
                   (7U << RCC_PLLCFGR_PLLQ_Pos) | RCC_PLLCFGR_PLLSRC_HSE;
    RCC->CR |= RCC_CR_PLLON;
    while (!(RCC->CR & RCC_CR_PLLRDY));
    FLASH->ACR = FLASH_ACR_LATENCY_5WS | FLASH_ACR_PRFTEN;
    RCC->CFGR |= RCC_CFGR_PPRE1_DIV4 | RCC_CFGR_PPRE2_DIV2 | RCC_CFGR_SW_PLL;
    while ((RCC->CFGR & RCC_CFGR_SWS) != RCC_CFGR_SWS_PLL);
    SystemCoreClock = 168000000;
}

static void adc_init(void)
{
    RCC->APB2ENR |= RCC_APB2ENR_ADC1EN;  ADC->CCR |= ADC_CCR_ADCPRE_0;  /* ADC clk = APB2/4 = 21MHz */
    ADC1->CR2 |= ADC_CR2_ADON;
    ADC1->SMPR2 |= ADC_SMPR2_SMP0_2 | ADC_SMPR2_SMP0_1 | ADC_SMPR2_SMP0_0;  /* 480 cycles sample time */
}

static void can_init(void)
{
    RCC->APB1ENR |= RCC_APB1ENR_CAN1EN;
    CAN1->MCR |= CAN_MCR_INRQ;
    while (!(CAN1->MSR & CAN_MSR_INAK));
    CAN1->BTR = 0x001c0003;  /* ~656kbps @ 42MHz APB1 (prescaler=4, 16 tq) */
    CAN1->MCR &= ~CAN_MCR_INRQ;
}

static void timer_init(void)
{
    SysTick_Config(SystemCoreClock / 1000);  /* 1ms */
}

float raw_to_temperature(uint16_t raw, const uint16_t *lut, uint8_t len)
{
    /* Linear interpolation: raw is a 12-bit ADC value 0-4095, mapped to NTC voltage divider */
    uint8_t i;
    float v_ratio = (float)raw / 4095.0f;
    for (i = 0; i < len - 1; i++) {
        /* Lookup table reverse mapping...actual code is longer */
        (void)lut;
    }
    return 25.0f + v_ratio * 60.0f;  /* Simplify */
}

void SysTick_Handler(void)
{
    g_system_ticks++;
}

int main(void)
{
    uint32_t last_sensor_read = 0;
    uint32_t last_can_send = 0;

    system_clock_init();
    adc_init();
    can_init();
    timer_init();

    while (1) {
        /* First stop: sensor collection (every 10ms) */
        if (g_system_ticks - last_sensor_read >= 10) {
            last_sensor_read = g_system_ticks;

            ADC1->CR2 |= ADC_CR2_SWSTART;
            while (!(ADC1->SR & ADC_SR_EOC));
            g_intake_temp_raw = ADC1->DR;
            g_intake_temp_degc = raw_to_temperature(g_intake_temp_raw,
                                                     ntc_lut, 101);
        }

        /* Second stop: Control calculation (use the latest collection value in each round) */
        {
            float temp = g_intake_temp_degc;
            if (temp > 85.0f) {
                /* Intake temperature is too high, limiting engine power */
                g_can_tx_flag = 1;
            }
        }

        /* Third station: Communication output (check and send a CAN frame every 100ms) */
        if (g_system_ticks - last_can_send >= 100) {
            last_can_send = g_system_ticks;
            if (g_can_tx_flag) {
                /* CAN ID 0x300: Intake system status */
                CAN1->sTxMailBox[0].TIR = 0x300 << 21;
                CAN1->sTxMailBox[0].TDTR = 3;  /* 3-byte data: temperature (2B) + over-temperature flag (1B) */
                CAN1->sTxMailBox[0].TDLR =
                    (uint32_t)(uint16_t)(g_intake_temp_degc * 10.0f) |
                    ((uint32_t)g_can_tx_flag << 16);
                CAN1->sTxMailBox[0].TIR |= 1;  /* Request to send */
                g_can_tx_flag = 0;
            }
        }
    }
}
```

This is the most complete form of the super cycle. The system beat is checked every cycle. There is no scheduler making decisions for you, the loop itself is the scheduler. You personally decide the execution frequency, execution order, and priority of each task.

But is everything perfect? Far from it. Two roadblocks are waiting for you.

## Software Crisis and ‘No Silver Bullet’

In 1968, NATO held a conference in Garmisch, Germany. The theme of the conference was ‘Software Engineering’. This word was chosen intentionally because writing software at the time was more like craft than engineering. Ten programmers can write ten completely different implementations of the same function. Large software projects are delayed, over budget, and full of bugs. This phenomenon is called a ‘software crisis’.

Seven years later, IBM's Fred Brooks, who led the development of the OS/360 operating system, wrote a book called "The Mythical Man-Month". The core argument of the book is that adding people to an already delayed software project will only make it slower. Because new people join need learning costs and need to communicate with the existing team, and the number of communication channels increases squarely as the number of people increases. There are n(n-1)/2 communication channels for n people. This is Brooks’ Law. It's the same reason as the 'hyperloop cannot expand infinitely' you face in bare-metal programming: resources are limited and not linearly additive.

Brooks wrote another famous paper "No Silver Bullet" in 1986. The essential complexity of software engineering cannot be eliminated by any single technology. This echoes Gödel's incompleteness theorem and Turing's halting problem, which all say: some things are inherently limited, and skills cannot change the essence. If you accept that "the interrupt-off time must be less than the peripheral tolerance limit" in bare-metal programming and "task switching overhead cannot be eliminated" in RTOS, you are accepting that "there is no silver bullet."

## The first stumbling block: where is the boundary of polling?

You can poll each peripheral's status flags in a superloop:

```c
while (1) {
    if (SPI1->SR & SPI_SR_RXNE) {
        uint8_t data = SPI1->DR;
    }
}
```

The problem is: if the SPI FIFO is full and you haven't had your turn yet, the next byte will overrun. In polling mode, your super loop loop time must be shorter than the fastest data arrival rate of the peripheral. A 10Mbps SPI sends a byte approximately every 0.8 microseconds, which means your loop must complete a full round within 0.8μs, otherwise data will be lost.

This forces you to ask the question: How long will it take to run my fastest lap of the loop? How long is the slowest? The time of bare metal programmers is not spent on "implementing functions", but on "calculating time". Worst-case execution time (WCET) analysis is a basic skill for bare metal engineers. You need to count the instructions of each branch path instruction by instruction, multiply by the number of cycles of each instruction, and find the longest execution path. Sometimes you will be surprised to find that the `for` loop in `raw_to_temperature` runs 30 more loops than expected under the worst input, which means that your system has missed 30 SPI bytes.

## The second stumbling block: interruption comes, the world pauses

**Interrupt** solves the problem of untimely polling. Peripherals proactively notify the CPU when data arrives. The following is a classic implementation of a CAN receiving ISR, that is, a ring buffer:

```c
#define CAN_RING_BUF_SIZE 64

typedef struct {
    uint32_t id;
    uint8_t  dlc;
    uint8_t  data[8];
    uint32_t timestamp;
} can_frame_t;

typedef struct {
    volatile uint8_t head;   /* ISR write */
    volatile uint8_t tail;   /* Main loop reading */
    can_frame_t frames[CAN_RING_BUF_SIZE];
} can_ring_buf_t;

static can_ring_buf_t can_rx_buf;

/* CAN receive interrupt, must be completed at microsecond level */
void CAN1_RX0_IRQHandler(void)
{
    can_frame_t frame;
    uint8_t next_head;

    /* Read a frame from the hardware FIFO */
    frame.id = CAN1->sFIFOMailBox[0].RIR >> 21;
    frame.dlc = CAN1->sFIFOMailBox[0].RDTR & 0x0f;
    frame.data[0] = CAN1->sFIFOMailBox[0].RDLR & 0xff;
    frame.data[1] = (CAN1->sFIFOMailBox[0].RDLR >> 8) & 0xff;
    frame.data[2] = (CAN1->sFIFOMailBox[0].RDLR >> 16) & 0xff;
    frame.data[3] = (CAN1->sFIFOMailBox[0].RDLR >> 24) & 0xff;
    frame.data[4] = CAN1->sFIFOMailBox[0].RDHR & 0xff;
    frame.data[5] = (CAN1->sFIFOMailBox[0].RDHR >> 8) & 0xff;
    frame.data[6] = (CAN1->sFIFOMailBox[0].RDHR >> 16) & 0xff;
    frame.data[7] = (CAN1->sFIFOMailBox[0].RDHR >> 24) & 0xff;
    frame.timestamp = g_system_ticks;

    /* Ring buffer writing, interrupts are not disabled, single writing and single reading are lock-free */
    next_head = (can_rx_buf.head + 1) % CAN_RING_BUF_SIZE;
    if (next_head != can_rx_buf.tail) {  /* Not full */
        can_rx_buf.frames[can_rx_buf.head] = frame;
        can_rx_buf.head = next_head;
    }
    /* Buffer full, frame dropped. A thousand times better than blocking the ISR. */

    CAN1->RF0R |= CAN_RF0R_RFOM0;  /* Release FIFO mailbox */
}

/* Main loop consumption */
void can_rx_process(void)
{
    while (can_rx_buf.tail != can_rx_buf.head) {
        can_frame_t frame = can_rx_buf.frames[can_rx_buf.tail];
        can_rx_buf.tail = (can_rx_buf.tail + 1) % CAN_RING_BUF_SIZE;
        /* Process frame... */
    }
}
```

The ISR completes in dozens of clock cycles. The frame data is thrown into the ring buffer and exits immediately. The main loop consumes data at a convenient time and does not need to turn off interrupts.

But the disruption brought new troubles.

## Critical Zone: When you have to shut down the whole world

When the main loop and ISR share data, a race condition lurks quietly. Look at this dangerous code:

```c
/* Main loop */
void can_rx_process(void)
{
    uint8_t count;
    count = can_rx_buf.head;  /* Read head */
    /* ---- If a CAN interrupt occurs here ----
       ISR modifies can_rx_buf.head = new_head */
    if (count != can_rx_buf.tail) {
        /* count is the old value, but you have already made a judgment based on the old value */
    }
}
```

It's not just a matter of "getting the old value". Let's see clearly at the assembly level why this is a recipe for disaster. On Cortex-M4, `count = can_rx_buf.head` may compile to:

```asm
    LDR  R0, =can_rx_buf      ; Load buffer address
    LDRB R1, [R0, #0]         ; Load head into R1 ← Interrupts can occur here
    ; ... ISR modified can_rx_buf.head ...
    LDRB R2, [R0, #1]         ; Load tail to R2, now head and tail are not snapshots at the same time!
    CMP  R1, R2               ; Compare two values from different moments in time
```

What you get is a **tear snapshot**, the head is from before the interruption, and the tail is from after the interruption. This inconsistent value can cause you to miss a frame, double-process a frame, or read garbage data past the end of the buffer. In an automotive ECU, this may mean missing a frame of brake message.

Solution: **Turn off interrupts** when accessing shared data (enter critical section):

```c
uint32_t primask;
primask = __get_PRIMASK();
__disable_irq();              /* CPSID I */
count = can_rx_buf.head;
tail  = can_rx_buf.tail;
__set_PRIMASK(primask);       /* restore previous state */
```

`__disable_irq()` compiles to the `CPSID I` instruction on the Cortex-M, which is used to set the PRIMASK register and mask all interrupts with configurable priority levels. `__get_PRIMASK()` Save the previous shielding state first, because you may already be in the critical section and need nesting protection.

The side effect of turning off interrupts is fatal: the interrupt response delay increases. If a CAN interrupt of the brake signal occurs while interrupts are turned off, it will be suspended until you turn interrupts back on. On a 168MHz STM32F4, one microsecond is 168 clock cycles. A critical section of 50 cycles is 300ns of additional delay, which is acceptable. A critical section of 5000 cycles is 30μs, accounting for 30% of the 100μs control period, which is unacceptable.

**The daily work of bare metal system designers: accurately calculate the maximum off-interrupt time to ensure that the real-time requirements of all peripherals are met. ** With a piece of paper, a pen, and a stack of data sheets, you are calculating the worst-case arrival interval for each interrupt source.

## MCU from Scratch: The Secret of Boot Files

Before `main()` is executed, the world is not blank. The first concept that bare metal programmers must understand is: your program does not start from `main()`, it starts from the reset vector.

After the MCU is powered on, the hardware does three things:
1. Read the initial stack pointer (MSP) from address 0x00000000
2. Read the reset vector from address 0x00000004, which is the address of Reset_Handler
3. Jump to Reset_Handler

Reset_Handler is the "creation function" of the bare metal world. In it, you must complete `.bss` clearing and `.data` initialization, otherwise the world of C language does not exist at all:

```c
/* The symbols exported by the link script are not variables, but addresses */
extern uint32_t _sidata;   /* LMA starting address of .data in Flash */
extern uint32_t _sdata;    /* VMA starting address of .data in RAM */
extern uint32_t _edata;    /* End address of .data in RAM */
extern uint32_t _sbss;     /* The starting address of .bss */
extern uint32_t _ebss;     /* The end address of .bss */

void Reset_Handler(void)
{
    uint32_t *src, *dst;

    /* Step 1: Copy the .data segment from Flash to RAM */
    src = &_sidata;
    dst = &_sdata;
    while (dst < &_edata) {
        *dst++ = *src++;
    }

    /* Step 2: Clear the .bss section */
    dst = &_sbss;
    while (dst < &_ebss) {
        *dst++ = 0;
    }

    /* Step 3: Optional FPU, MPU, Cache initialization */

    /* Step 4: Call the entrance to the C world */
    main();

    /* main() should never return. If it returns, it will be an infinite loop. */
    while (1);
}
```For every `static int g_counter = 5;` you pass to the compiler, that initial value of 5 is stored in the `.data` LMA area of ​​Flash. It is not in RAM when powering on. It is Reset_Handler that uses `memcpy` (or copy it word by word) to move it from Flash to the actual address of `g_counter` in RAM. For every `static int g_buffer[256];` you declare, the initial values ​​are all zeros, but the SRAM when the chip is powered on is a random value. The Reset_Handler uses the `while` loop to write 0 over and over again until the entire `.bss` segment is cleared.

Before you write `printf("Hello\n")`, this inconspicuous assembly + C code has already been run. Bare metal programmers must know it exists. Because if it is wrong, `if`, `for`, and global variables in `main()` are all random.

## Linker script: Draw a map for C language

Who defined where `.data` is placed in Flash and copied to RAM? **Linker Script**. It is the linker configuration file that defines the storage layout of the entire program. The following is a typical linker script fragment for STM32F407:

```ld
MEMORY
{
    FLASH (rx)  : ORIGIN = 0x08000000, LENGTH = 1024K
    RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
    CCMRAM(rwx) : ORIGIN = 0x10000000, LENGTH = 64K
}

SECTIONS
{
    /* The interrupt vector table must be placed at offset 0 of Flash */
    .isr_vector :
    {
        KEEP(*(.isr_vector))
    } > FLASH

    /* Code segment: all .text, machine code of functions */
    .text :
    {
        *(.text*)
        *(.rodata*)
        . = ALIGN(4);
    } > FLASH

    /* The loading address (LMA) of .data is in Flash, and the running address (VMA) is in RAM */
    .data : AT(ADDR(.text) + SIZEOF(.text))
    {
        _sidata = LOADADDR(.data);
        _sdata = .;
        *(.data*)
        . = ALIGN(4);
        _edata = .;
    } > RAM

    /* The .bss section is in RAM and does not occupy Flash space */
    .bss :
    {
        _sbss = .;
        *(.bss*)
        *(COMMON)
        . = ALIGN(4);
        _ebss = .;
    } > RAM

    /* Stack, at the end of RAM */
    .stack (NOLOAD):
    {
        . = ALIGN(8);
        . = ORIGIN(RAM) + LENGTH(RAM);
        _estack = .;
    } > RAM
}
```

The `MEMORY` block tells the linker the actual physical address of the chip: Flash at 0x08000000 and RAM at 0x20000000. The `SECTIONS` block defines which physical area each segment is placed in. `AT(ADDR(...))` is the essence of the linker script, which says that `.data`'s load address (LMA) is in Flash immediately after the end of `.text`, but its virtual address (VMA) is in RAM. The program runs in place in Flash, but global variables must be in RAM to read and write, and the link script builds a bridge between them.

Those `_sidata`, `_sdata`, `_edata`, `_sbss`, `_ebss` symbols: they are the **contract** between the linker script and the Reset_Handler. Reset_Handler uses the addresses of these symbols to know where to copy and where to clear. If the link script points to the wrong location of `_ebss`, the `while` loop of Reset_Handler will not know where to stop. It will keep writing, write the stack, and then HardFault.

Bare metal programmers read link scripts as much as they read their own code. **An offset error for each address here means that the chip will fail in less than one second after power-on. **

## A complete bare metal project: main + ISR + link script + Makefile

The end point of the bare metal project is not to finish writing `main()`. It is a programmable hex file. You string the entire project together:

```makefile
# Makefile for STM32F407 bare-metal project
CC      = arm-none-eabi-gcc
CFLAGS  = -mcpu=cortex-m4 -mthumb -O2 -ffunction-sections -fdata-sections
LDFLAGS = -Tstm32f407.ld -nostartfiles -Wl,--gc-sections

OBJS = startup.o main.o isr.o

all: firmware.elf firmware.bin

firmware.elf: $(OBJS)
    $(CC) $(LDFLAGS) -o $@ $^

%.o: %.c
    $(CC) $(CFLAGS) -c -o $@ $<

%.o: %.s
    $(CC) $(CFLAGS) -c -o $@ $<

firmware.bin: firmware.elf
    arm-none-eabi-objcopy -O binary $< $@

flash: firmware.bin
    st-flash write firmware.bin 0x08000000

clean:
    rm -f *.o *.elf *.bin
```

This Makefile does four things: compile C and assembly files into object files (`-mcpu=cortex-m4 -mthumb`), link with linker scripts (`-Tstm32f407.ld`), convert ELF into binary images (`objcopy -O binary`), and burn the binary into the chip (`st-flash write`).

Behind a `make flash` command is: Compiler→Assembler→Linker→ELF→Binary→SWD Programmer→Chip Flash. Bare metal programmers understand every step, not because they have to, but because if any step goes wrong, you don’t know where to look.

## How far can one person’s tribe go?

Bare metal programming brings an indescribable experience to programmers: a complete sense of control. 

You know how many clock cycles each instruction consumes. You know the meaning of every bit in every peripheral register. You know which registers to push before jumping into the ISR. You have no help from the operating system. You don't need its help either, you manage everything yourself.This is very similar to early human civilization. Before the advent of written law, tribal chiefs personally judged every dispute. There is no "procedural justice", it is all "substantive justice". Extremely efficient, but limited in scale.

A tribe of dozens of people is okay, but a tribe of several hundred people starts to become chaotic.

Bare metal programming is for the "tribe of one." You alone write the code, you alone understand the system, and you alone manage the complexity. Many CAN node gateways and sensor front-end MCUs use bare metal. 1000 lines of C code, running without errors for 10 years. Stability is not guaranteed by the framework, but by your absolute understanding of each line.

But when the code exceeds 10,000 lines, the peripherals exceed 10, and the interrupt sources exceed 20, the "tribe of one person" begins to show cracks. Interrupt priority allocation, critical section duration, and consistency of shared data are not problems that can be solved by "just remembering them."

You have changed from an engineer who writes startup files to a person who relies on memory and will to carry everything. Then one day you realize that you can't bear it anymore.

You need a higher level to organize complexity. At that level there are tasks, there are schedulers, there are structured communications. It manages interrupts and context switches on top of you.

## Summary

Today we did one thing: ** Starting from the first instruction after the CPU was powered on, we completely tracked the startup process and runtime panorama of the bare metal program. **

Key takeaways:
1. **Bare metal programming gives you an absolute sense of control, but the scale is limited**: You know how many cycles each instruction consumes, the meaning of each bit of each register, and which registers are pushed by the ISR. 1,000 lines of C code can run without error for 10 years. But over 10,000 lines, 10 peripherals, 20 interrupt sources. The "tribe of one" begins to collapse.
2. **Volatile, critical sections, and interrupt nesting are not syntactic sugar, but the mapping of physical world constraints at the software layer**: Compiler out-of-order optimization will rearrange access to hardware registers, and interrupts can interrupt any non-atomic operations. Each layer of abstraction responds to real race conditions at the physical layer.
3. **Polling loop and interrupt-driven are two philosophies, which one you choose depends on your time constraints**: polling is a time swap (exchanging CPU utilization for predictability), and interrupts are a response speed swap (low latency but unpredictable nesting). The core ability of bare metal programming is to make precise judgments between the two.

Next section, when the "tribe of one" doesn't hold up, you need a higher level to organize the complexity. The RTOS kernel can complete a context switch within 1-2 microseconds, but priority inversion, stack overflow, and deadlock are new types of bugs that have never been seen in the bare metal world.
