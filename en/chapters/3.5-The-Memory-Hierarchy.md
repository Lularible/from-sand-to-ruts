# 3.5 The Memory Hierarchy

## Librarian’s clever approach

You are a librarian. The library has millions of books, all in underground warehouses. When readers come to borrow books, you have to go to the underground warehouse to find them. 10 minutes round trip. Readers lined up and everyone had to wait 10 minutes.

You can't take it anymore.

You place a small bookshelf behind the lending desk with 50 books on it. Every time a reader returns a book, you put the most commonly used books on the small bookshelf. Someone comes to borrow it: If the book is on the small bookshelf, take it out in 3 seconds. If it's not there, go to the underground warehouse to get it. By the way, I also put the retrieved books on the small bookshelf, excluding the least frequently used ones.

This is **Cache** (cache).

You can't keep all the books on hand (it's too expensive), but you can keep the ones you use most handy. This strategy is effective because of two rules:

- **Temporal locality**: The book you just read will most likely be read again.
- **Spatial Locality**: You are reading Chapter 5 and will most likely need Chapter 6 soon.

The storage hierarchy of all computers. From registers to SSD, the same logic is followed.

## Storage Pyramid

```
Fastest/most expensive/smallest
     +----------+  
     | Register | ~1ns, ~1KB, in CPU core
     +----------+
     | L1 Cache| ~1-2ns, ~32KB, in core
     +----------+
     | L2 Cache| ~3-10ns, ~256KB, on the same die
     +----------+
     | SRAM | ~5-20ns, ~64-256KB, on-chip
     +----------+
     | DRAM | ~50-100ns, ~hundreds of MB, external chip
     +----------+
     | Flash | ~50-100ns (read), ~ms (erase and write), on-chip or external
     +----------+
     | SSD/HDD | ~μs-ms, ~GB-TB, external storage
     +----------+
    slowest/cheapest/largest
```

Note: This is the storage hierarchy of a general-purpose computer. In automotive MCUs (such as Cortex-M4/M7), there is usually only L1 Cache or no Cache, and the on-chip SRAM is directly hung on the system bus, with a delay of a certain single cycle or several cycles.

Between each layer, the delay differs by an order of magnitude. Register ~1ns, L1 Cache ~1-2ns, SRAM ~5-20ns, DRAM ~50-100ns. From registers to DRAM, the difference is two orders of magnitude. From registers to SSDs, the difference is several orders of magnitude (depending on the medium and access method).

Without two localities, the Cache is of no use to you if your memory accesses are completely random. Because every access may miss, you are just paying extra search overhead for data that cannot be stored.

Fortunately, the memory access patterns of almost all programs follow these two localities. Instructions are executed sequentially and data are distributed centrally. This is the gift brought to us by Turing machines and von Neumann architecture.

## How Cache works: Tag, Index, Offset

Take the simplest direct-mapped Cache as an example.

The Cache is divided into several Cache Lines (for example, 32 bytes each). The memory address is split into three fields:

```
| Tag (high) | Index (middle) | Offset (low) |
```

- **Index**: Determines which Cache Line the data is mapped to. Different addresses of the same Index share the same Line location.
- **Tag**: Save to the Cache Line to determine whether the currently cached data is the address you want.
- **Offset**: Locate specific bytes within Cache Line.

When the CPU accesses an address:
1. Use Index to find the corresponding Cache Line.
2. Compare the tags, and if the match is **Cache Hit**, the data will be returned directly in 1 clock.
3. Mismatch is Cache Miss. The hardware automatically loads the entire Cache Line from the next level storage (L2 or main memory) and replaces the old one. Delay 10-100 clocks.

### Dismantle an address with your own hands

Assume a direct mapped Cache:
- Cache capacity 16KB
- Cache Line = 32 bytes
- So there are 16KB / 32B = 512 Cache Lines (Index accounts for 9 bits)
- Offset accounts for 5 bits (log2 32)
- In the 32-bit address, Tag occupies 32 - 9 - 5 = 18 bits

Access address `0x0000A010`:

```
0x0000a010 = 0000 0000 0000 0000 1010 0000 0001 0000 (binary)
              |___ Tag (18) ____| | Index (9) _| |_Off(5)_|

Tag   = 0x00002
Index = 0b100000000 = 256
Offset = 0x10 = 16
```What the Cache controller does: Check whether the Tag field in Set 256 is equal to `0x00002` and whether the Valid bit is 1. If it matches, it's a Cache Hit. If it does not match, it is a Cache Miss. Load the entire 32-byte block (from `0x0000A000` to `0x0000A01F`) at the main memory address `0x0000A010` to Set 256, write the Tag as `0x00002`, and set Valid to 1.

Before reading the code, go through this address in your mind: Index=256 points to Cache Line No. 256. The hardware checks whether the Tag of this line is equal to 0x00002. If it is: Hit, read the data at offset=16 directly. If not: Miss, the hardware automatically loads the entire 32-byte block from the next level of storage (L2 or main memory), replaces this line, and updates the Tag. The following C code simulates this "check → hit/missing → replace" cycle.

### Implement a direct-mapped Cache emulator in C

```c
#include <stdio.h>
#include <stdint.h>
#include <string.h>

#define CACHE_LINES 512
#define LINE_SIZE   32

typedef struct {
    uint8_t  valid;
    uint32_t tag;
    uint8_t  data[LINE_SIZE];
} CacheLine;

CacheLine cache[CACHE_LINES];
uint32_t hits = 0, misses = 0;

uint8_t cache_access(uint32_t addr, uint8_t write, uint8_t data) {
    uint32_t offset = addr & 0x1f;           // Low 5 bits
    uint32_t index  = (addr >> 5) & 0x1ff;   // 9th place
    uint32_t tag    = addr >> 14;             // High 18 bits

    CacheLine *line = &cache[index];

    // Cache Hit
    if (line->valid && line->tag == tag) {
        hits++;
        if (write) line->data[offset] = data;
        return line->data[offset];
    }

    // Cache Miss
    misses++;
    // In real hardware, the entire Cache Line is loaded from main memory.
    // In simulation, we directly set Valid and Tag
    line->valid = 1;
    line->tag   = tag;
    if (write) line->data[offset] = data;
    return line->data[offset];
}

void run_trace(uint32_t addrs[], int count) {
    hits = misses = 0;
    memset(cache, 0, sizeof(cache));
    for (int i = 0; i < count; i++)
        cache_access(addrs[i], 0, 0);
    printf("Hit rate: %.2f%% (%u hits, %u misses)\n",
           100.0 * hits / count, hits, misses);
}
```

Test: Sequential access to `0x1000, 0x1004, 0x1008, 0x2000, 0x100C`.

```
0x1000 → Index=128, Tag=0 → Miss (cold)
0x1004 → Index=128, Tag=0 → Hit  (same line, 0x1000-0x101f)
0x1008 → Index=128, Tag=0 → Hit
0x2000 → Index=256, Tag=0x0 → Miss(first access to Set 256, cold miss)
0x100c → Index=128, Tag=0 → Hit  (still in line 128)
```

Hit rate = 3/5 = 60%. 0x2000 (Index=256) and 0x1000 (Index=128) fall in different Cache Lines and do not conflict with each other. If subsequent access is to 0x00201000 (Index=128, Tag=0x80), the current Cache Line of 0x1000 will be evicted, which is a conflict.

This is the "Conflict Miss" of direct mapping: two different addresses are mapped to the same Cache Line.

## Group connection and LRU replacement

The shortcomings of direct mapping are obvious: if two frequently accessed addresses happen to hit the same Index, they will kick each other out repeatedly, causing thrashing.

**Set-Associative Cache** (Set-Associative Cache) alleviates this problem: each Index corresponds to N Cache Lines (N ways), and the address can be stored in any one of the N ways. N=2 means 2-way group connection, N=16 means 16-way group connection. The larger N, the fewer conflicts, but the more complex the hardware (needs to compare N tags in parallel).

When N roads are full and one needs to be kicked out, which strategy should be used?

LRU (Least Recently Used) is the most classic replacement algorithm: kick out the path that has not been visited for the longest time. Implement a 4-way group connected LRU Cache in C:

```
// LRU replacement strategy (conceptual pseudocode):
function access_cache(set_index, tag):
    for way in 0..WAYS-1:
        if cache[set][way].valid && cache[set][way].tag == tag:
            // Cache Hit
            update_lru(set_index, way)
            hits++
            return cache[set][way].data

    // Cache Miss: Find an empty path first
    for way in 0..WAYS-1:
        if !cache[set][way].valid:
            fill_line(set_index, way, tag)
            return

    // No empty way: kick out the LRU way that has not been visited for the longest time
    victim = find_lru_way(set_index)
    if cache[set][victim].dirty:
        write_back(victim)
    cache[set][victim].tag = tag
    cache[set][victim].valid = 1
    update_lru(set_index, victim)
    misses++
```

Core idea: Each channel in each Set maintains an "age" count. Each time a visit hits, the age of the hit road is reset to the maximum (latest), and the age of other roads is decremented. When replacement is required, the path with the youngest age is chosen because it has not been visited for the longest time.

In fact, `find_lru_way` and `update_lru` do not need to store the full timestamp. Taking 4-way group connection as an example, 6 bits are commonly used to encode 4! = 24 relative access sequences. Just use an LRU state machine instead of a 32-bit counter for each channel.

This simulator lets you see: the implementation cost of LRU grows linearly with the number of channels N. Within each Set, you need to store N LRU timestamps and do N-way comparisons. In real hardware, a 6-bit LRU state machine (not a complete timestamp, but a relative ordering encoding) is commonly used for 4-way group connection, but for 16 or more channels, pseudo-LRU (PLRU) or random replacement is usually used instead, because the hardware overhead of real LRU is no longer worth the tiny hit rate improvement.

## Writing strategy: Write-Through vs Write-Back

When the CPU writes data, the Cache faces a choice:Write-Through: Write to Cache and lower-level storage (main memory) at the same time. Advantages: Simple, Cache and main memory are always consistent, no dirty bit is required. Disadvantages: Every time Store has to wait for main memory write confirmation, high latency and high power consumption. Usually used with Write Buffer: the CPU puts the write data into a FIFO, and Write Buffer slowly writes the main memory in the background, and the CPU does not have to wait. But if the Write Buffer is full, the CPU still has to stall.

Write-Back: Write only to the Cache and mark the Line as "dirty". When the Line is replaced, the entire Line is written back to main memory. Advantages: Low Store latency (write-only Cache) and less bus traffic. Disadvantages: dirty bit is required, and the Cache controller logic is more complex; dirty data in the Cache is lost when power is lost.

There are two options when writing misses:

Write-Allocate: First load the entire Line into Cache, and then write the byte in Cache. It takes advantage of spatial locality because you may also write to adjacent bytes of this Line immediately.

No-Write-Allocate: bypass Cache and write directly to main memory. Suitable for streaming writing (large data blocks are only written once and will not be reused).

Typical combination:
- Write-Back + Write-Allocate: The most common, such as the L1/L2 Cache of the Cortex-A series.
- Write-Through + No-Write-Allocate: Commonly seen in real-time systems. It reduces the complexity of Cache consistency maintenance and ensures certainty.

## Multi-core consistency issues: MESI protocol

If you have two CPU cores. Each has its own L1 Cache, and they each cache a copy of the same block of main memory at address 0x2000. CPU0 modifies it, but CPU1 still sees the old value.

This is the Cache Coherence problem.

Imagine two librarians each have a small bookshelf (L1 Cache), sharing the same underground warehouse (main memory). When administrator A modifies a book on his bookshelf, the same book on administrator B's bookshelf becomes the "old version". They need a way to notify each other. The MESI protocol is this set of notification rules: M (Modified, my book is newer than the warehouse, others cannot have it), E (Exclusive, my book is as new as the warehouse, others cannot have it), S (Shared, my book is as new as the warehouse, others can have it), I (Invalid, my book is out of date, if you want to read it, get it from the warehouse again).

**MESI protocol** is the most classic snooping-based consistency protocol. Each Cache Line is in one of four states:

- Modified (M): The Line only has a copy in this Cache and has been modified (dirty). The copy in main memory is out of date.
- Exclusive (E): The Line only has a copy in this Cache and is consistent with the main memory (clean).
- Shared (S): The Line has copies in multiple Cache, and all copies are consistent with the main memory.
- Invalid(I): The Line is invalid.

Core rules for state transitions:

```
CPU read → if I: send BusRd, go to S (or E if there are no other sharers)
CPU write → If S: Send BusUpgr (invalidate other copies), go to M; if E: Go directly to M, no bus transaction required
Snoop BusRd → if M: write back to main memory, go to S
Snoop BusRdX (to be written by other CPUs) → Go to I
```

MESI is a snooping protocol: each Cache controller monitors the read and write operations of other Cache on the bus, and determines whether its own status needs to be updated based on the address. This works well in bus systems, but in large multicores (16+ cores) the bus bandwidth becomes the bottleneck. Modern CPUs turn to directory protocols, with a central directory recording which cores each Cache Line is shared with.For automotive MCUs, multi-core coherence is generally much simpler. In the Cortex-R5's dual-core lockstep mode, both cores run the same code. There are no consistency issues. Even for non-lock-step multi-core MCUs (such as Renesas RH850, Infineon Aurix), inter-core communication uses shared SRAM instead of hardware-coherent Cache, and programmers use memory barrier instructions (DSB/DMB/ISB in ARM) to explicitly manage consistency.

## Why doesn’t the automotive MCU love Cache?

Many automotive grade Cortex-M4 MCUs have no Cache (or only a simple instruction Cache). Cortex-M7 usually has both I-Cache and D-Cache, which is determined by its architectural characteristics (a six-stage pipeline requires low-latency instruction and data supply). However, on the functional safety critical path, engineers often actively disable D-Cache to ensure the predictability of WCET analysis. They use tightly coupled SRAM (System RAM), and the access latency of the on-chip SRAM is a deterministic single cycle (or two or three wait cycles).

There is only one reason why it is not used: WCET cannot be analyzed.

- At which loop iteration does the Cache miss occur? have no idea. Depends on historical access patterns.
- What is the wait period of the Flash at the current VCC and temperature? uncertain.
- The ISR may take twice as long due to a cache miss. Do you dare to allow ABS's ISR to have such uncertainty?

Automotive MCUs would rather use this silicon area to make more on-chip SRAM instead of Cache. Trade area for certainty.

## TCM: "Deterministic Cache" explicitly managed by software

The TCM design of Cortex-R5 pushes this idea to the limit: it is not a "blind transparent Cache", but a tightly coupled storage explicitly managed by software.

Let me give you a concrete picture. In the Cortex-R5 MPU configuration, I locked the ISR code to the A region of the TCM (ATCM):

```
TCM A (ATCM)：0x00000000-0x00003fff，ISR code + critical data
TCM B (BTCM)：0x00004000-0x00007fff，stack space
TCM R (TCMR): Configuration register
```

The access latency of TCM is deterministic one or two cycles. As fast as Cache Hit, but without the uncertainty. Every time the CPU accesses the TCM address space, data must be returned within that cycle. No tag comparison, no miss, no substitution, no state machine.

What's the cost? The total capacity of the TCM is small (typically 32-64KB on Cortex-R5) because it is made of SRAM and competes for the same silicon area as the Cache. And the content must be explicitly managed by the programmer. You declare in the linker script which sections should be placed in TCM, use DMA to move key data into TCM at runtime, and move it out after use. There is no hardware automation.

The fundamental difference between TCM and Cache: TCM is "what I know is fast", Cache is "what I believe is fast". In safety-critical systems, "I believe" is not enough, you need "I know."

## Physical vulnerability of SRAM cells

An SRAM cell consists of 6 transistors: 4 forming two cross-coupled inverters (storing 0 or 1), and 2 being access transistors (connecting word and bit lines).

```
         WL (word line)
          │
    M5 ───┼─── M6
          │
    ┌──M1─┴──┐
    │ Cross  │
    │Couple  │
    └──M2─┬──┘
          │
         BL   BL'
        (bit line)
```

The stability of this structure depends on the Vt (threshold voltage) matching of the 6 transistors. During the manufacturing process, there may be slight differences in the Vt of M1 and M2 due to random dopant fluctuation (RDF, Random Dopant Fluctuation). In small-size processes (below 28nm), the impact of RDF is more significant. There are only dozens of dopant atoms in a transistor. One more or one less may cause Vt to drift by tens of mV.If M1's Vt drifts high (becomes more difficult to conduct) and M2's Vt is normal, then during the read operation, M1's driving force is insufficient when M5 is turned on and BL is pulled low. The positive feedback of the cross-coupled inverter can be destroyed, and the stored "0" is flipped to a "1".

This is called Read Disturb, which is the most common physical failure mechanism of SRAM in small sizes. It's not a circuit design error, it's manufacturing variation that reduces the noise margin of a single bit cell to less than one standard deviation.

The existence of MBIST (Memory Built-In Self Test) is to torture every storage bit with the most stringent access sequence (continuous read and write, read and write flip, neighbor interference) before the chip leaves the factory, and not let go of any weak bits with insufficient noise margin. Automotive SRAM requires close to 100% test coverage. The reason is simple: you cannot tolerate the ECU's decision-making system crashing due to the soft failure of an SRAM bit in a high-speed corner.

## Flash erasure life: a story of convergence

The erase and write life of a standard embedded NOR Flash is 100,000 times.

Let's say your DTC (diagnostic trouble code) log records diagnostic data every 10 seconds, writing a 4-byte DTC entry each time.

If you put the DTC log directly in a sector of Flash. Each write erases the entire sector and writes it back, 100,000 times ÷ (24 hours × 3600 seconds / 10 seconds) ≈ 11.6 days. Your Flash died in less than two weeks.

This is why almost all Flash storage systems must require wear leveling. Instead of repeatedly erasing and writing the same physical sector, you use software to cycle through sectors within a larger Flash area (such as 64KB). Each time a new location is written, a mapping table is maintained: telling you which current physical sector corresponds to "logical address 0x0000".

Going a step further, you can use SRAM for buffering. DTC data is first accumulated in SRAM (accumulated to 512 bytes), and then programmed into Flash at one time. The write frequency of 10 seconds becomes (512/4) × 10 = 1280 seconds ≈ 21 minutes. With the same lifespan of 100,000 erasing and writing, a single sector can now support 10^5 × 1280 s ≈ 4.1 years, which is still not enough to cover the life of the entire vehicle. Add the wear leveling of the previous 64KB area (multiple sectors take turns erasing and writing), and the lifespan is multiplied by the number of sectors to exceed the design life of the vehicle.

### Three layers of collaboration: why no layer can solve problems alone

There are three layers of collaboration hidden within this design. Each layer alone is not enough. Only when combined can it meet the full life cycle requirements of the vehicle:

```
SRAM (speed) → fast buffer, but lost on power outage
Flash (persistent) → will not be lost when power is turned off, but is slow to erase and write and has a limited lifespan
Wear leveling (lifetime) → amortized erases, but requires additional calculations
Cooperation among the three → Complete non-volatile storage system
```

The three layers address speed, durability and life respectively: SRAM provides fast buffering, Flash provides persistent storage, and the wear leveling algorithm averages erase and write. At the hardware level, SRAM and Flash are two physical media; at the software level, the wear leveling algorithm is a piece of code. The three layers span the boundaries of hardware and software and together form a reliable storage subsystem.

## Your Embedded C and storage hierarchy

### Interrupt response: ISR in Flash

You write an ISR that reads CAN messages and stores them in a ring buffer. The ISR is placed in Flash. Flash read latency, at 112MHz, may be 3-5 wait cycles. Without the instruction cache, each fetch would directly suffer these wait cycles.

**Optimization**: Remap the ISR to SRAM (placed through the section of the linker script), or enable the instruction Cache + to lock critical code to the Cache Line.

### Loops: A textbook on locality

```c
for (int i = 0; i < 1024; i++) {
    dst[i] = src[i] * gain;
}
```Perfect spatial locality (sequential access to `src` and `dst`) and temporal locality (repeated execution of loop body instructions). With data cache, the hit rate is close to 100%. Without Cache, the on-chip SRAM is also single-cycle, but the power consumption is higher (the SRAM is read in each iteration).

(Note: This example is a classic microcosm of the discussion of memory hierarchy and locality principles in "In-depth Understanding of Computer Systems". The cover of the book is a three-dimensional performance surface chart with this theme, which is also the "Storage Mountain".)

### Flash emulated EEPROM: multi-layer collaboration

Your MCU does not have an independent EEPROM, but the calibration parameters need to be powered off and not lost. You use on-chip Flash to simulate:

- Flash is erased on a sector-by-sector basis (several KB to tens of KB), and the erase and write life is ~100,000 times.
- Before updating parameters: Back up other valid data in the sector to SRAM → Erase the entire sector → Write SRAM backup + new parameters back to Flash.

This implies the cooperation of storage levels: Flash (non-volatile, slow erasing and writing) + SRAM (volatile, fast reading and writing) = a reliable non-volatile storage system. You take advantage of the respective advantages of two layers: the persistence of Flash and the flexible reading and writing of SRAM to build capabilities that a single layer of storage cannot provide.

## Optimal solution for limited resources

The question answered by the storage layer is: How to achieve "near fastest" performance with limited resources?

You can't put all the data in registers because there are only a few dozen registers. You can't put them all in the Cache, because the Cache is only a few tens of KB. It can't all be placed in SRAM, because SRAM is only a few hundred KB. But you can combine these layers so that programmers don't feel the existence of multi-layer storage when writing `data[x] = y`.

This is "transparent optimization": using limited resources to the limit without the user being aware of it.

This philosophy runs through the entire computer system design:
- You don’t have unlimited storage, but you have multiple layers of cache, which is the optimal solution for limited resources.
- You don’t have a perfect network, but you have time synchronization and deterministic scheduling, which is the optimal solution for limited resources.
- You don’t have unlimited manpower to do sufficient testing, but you use MISRA C, ISO 26262 processes, and formal methods to reduce risks to the ASIL level. This is still the optimal solution with limited resources.

When you use 128KB SRAM to run through a CAN diagnostic stack on an ECU, you are practicing this credo. You're living this creed by using hardware triggers and combinational logic to capture timestamps with nanosecond precision. If you design a storage architecture based on Flash simulated EEPROM and eliminate the need for an external chip, you are still practicing this creed.

The storage hierarchy is the most elegant embodiment of "optimal solution for limited resources".

## Summary

Today we did one thing: we understood the storage hierarchy, "fast" and "big" cannot have both, so we used multi-level storage to cheat this limitation.

Key takeaways:
1. The storage level is a compromise step by step: register (about 1ns/several KB) → Cache (several nanoseconds/tens of KB) → SRAM (tens of nanoseconds/hundreds of KB) → DRAM (tens of nanoseconds/hundreds of MB) → Flash (about hundreds of nanoseconds for reading, millisecond level erasure/GB level), and the speed of each layer differs by an order of magnitude.
2. Cache works based on locality: temporal locality (the ones just used may be reused) and spatial locality (nearby ones may be used). The hit rate is usually above 90%.
3. Hard real-time systems require determinism: Cache miss time is unpredictable, so automotive MCUs tend to use TCM to lock key codes and data in SRAM at fixed locations, so the delay is completely determined.
