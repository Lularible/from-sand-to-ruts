# 3.3 The Datapath and the Controller: A Pas de Deux

## A pile of blocks, missing a conductor

There is a pile of wooden blocks spread out in front of you: adders, multiplexers, register files, ALUs, and program counters (PCs). They are the protagonists of the first two sections, and each one can work independently. But they are laid out haphazardly on the desktop, and you don't get a processor that can execute the program.

Just like a symphony orchestra, each instrument cannot play its own part at the same time. It takes one person to stand up front and wave the baton. Tell the violins when to come in and the timpani when to hit.

Who tells the adder "do addition this cycle", tells the register file "write the result into R3", tells the PC "jump to 0x2000 for the next instruction"?

You need a Control Unit.

The relationship between it and the controlled object (data path) is the core pair of relationships in the computer architecture.

In this chapter, we use “conductor and orchestra” to understand this coordination. The data path is the orchestra, the adder is the string section, the register is the wind section, and the ALU is the percussion section. The controller is the conductor, it makes no sound, but its gestures determine when each instrument comes in and when it stops. Without a conductor, the orchestra is just noise. Without an orchestra, the conductor's gestures are just air.

## Data path: the "highway" of data

First build the hardware skeleton. Datapath is the pipeline for data flow:

1. **Program Counter (PC)**: A register that holds the address of the next instruction.
2. **Instruction Memory**: Fetch the 32-bit instruction from the address pointed by PC.
3. **Register file**: Decode the source register number from the instruction field and read out the two source operands.
4. **ALU**: Perform arithmetic/logical operations on the source operands.
5. **Data memory**: If it is a Load/Store instruction, read and write memory.
6. **Write back**: Write the ALU result or memory data back to the target register.

The connections (paths created using multiplexers) between these components determine how data can flow. But how the data actually flows requires control signals.

## Controller: an instruction, a set of signals

The controller does one thing: decodes all control signals from the opcode of the current instruction.

Take the ADD instruction as an example (ARM: `ADD R1, R2, R3`):

| Control signal | Value | Meaning |
|---------|-----|------|
| RegSrc | 10 | Select the source register number from the instruction field |
| ALUSrc | 0 | ALU second operand comes from register file (non-immediate value) |
| ALUControl | 0010 | ALU does addition |
| MemtoReg | 0 | Write back data from ALU results (non-memory) |
| RegWrite | 1 | Write back the result to the destination register |
| MemWrite | 0 | Do not write to memory |
| Branch | 0 | No jump |

Take the LOAD instruction as an example (`LDR R1, [R2, #4]`):

| Control signal | Value | Meaning |
|---------|-----|------|
| ALUSrc | 1 | ALU second operand is immediate (offset) |
| ALUControl | 0010 | ALU does addition (base address + offset = effective address) |
| MemtoReg | 1 | Write back data from memory |
| MemWrite | 0 | Do not write to memory |
| RegWrite | 1 | Write back the result to the destination register |

This is the conductor's score: the ADD command points to the string section (RegWrite=1, ALUSrc=0), and the LDR command points to the wind section (MemtoReg=1, ALUSrc=1).

The controller is essentially a combinational logic lookup table. If written as C code:

```c
struct control_signals {
    int reg_src, alu_src, alu_control;
    int mem_to_reg, reg_write, mem_write, branch;
};

struct control_signals control_logic(uint8_t opcode) {
    switch (opcode) {
        case ADD: return (struct control_signals){0, 0, 0, 0, 1, 0, 0};
        case SUB: return (struct control_signals){0, 0, 1, 0, 1, 0, 0};
        case LDR: return (struct control_signals){0, 1, 0, 1, 1, 0, 0};
        case STR: return (struct control_signals){0, 1, 0, 0, 0, 1, 0};
        case B:   return (struct control_signals){0, 0, 0, 0, 0, 0, 1};
    }
}
```

The input is an opcode and the output is a set of control signals. The controller is just such a "hardwired lookup table".

## Simulate an 8-instruction CPU in CLet's simulate the entire processor (data path and controller) completely in C. It's not a simulation, it's a behavioral model. The goal is to make how instructions flow through the data path from abstract to tangible.

First define the hardware structure:

```c
#include <stdint.h>
#include <stdio.h>
#include <string.h>

// ---Command format ---
// 16-bit fixed-length instructions
// RRR: [opcode:4][rd:4][rs1:4][rs2:4]
// RRI: [opcode:4][rd:4][rs1:4][imm4:4]
// B:   [opcode:4][cond:4][offset:8]
typedef struct {
    uint8_t opcode : 4;
    uint8_t rd     : 4;
    uint8_t rs1    : 4;
    uint8_t rs2    : 4;   // or imm4 (depending on the instruction type)
    int8_t  imm8;         // branch offset
} Instruction;

// ---Operation code ---
#define OP_ADD  0
#define OP_SUB  1
#define OP_AND  2
#define OP_OR   3
#define OP_LDR  4
#define OP_STR  5
#define OP_BEQ  6
#define OP_HALT 7

// ---Control signal ---
typedef struct {
    uint8_t alu_op;     // 0=ADD,1=SUB,2=AND,3=OR,4=NOP
    uint8_t alu_src;    // 0=reg, 1=imm
    uint8_t mem_read;
    uint8_t mem_write;
    uint8_t reg_write;
    uint8_t mem_to_reg;
    uint8_t branch;
} ControlSignals;

// ---CPU status ---
typedef struct {
    uint16_t reg[16];       // R0-R15
    uint16_t pc;            // program counter
    uint8_t memory[65536];  // 64KB unified memory (including instructions and data)
    uint8_t running;
    uint16_t ir;            // instruction register
} CPU;
```

The last is single-cycle execution (fetch, decode, execute, write back), completed in one clock cycle:

```c
void cpu_step(CPU *cpu) {
    if (!cpu->running) return;

    // IF: Fetch, PC driver address, read 16-bit instructions from unified memory
    Instruction inst;
    uint16_t raw = cpu->memory[cpu->pc] | (cpu->memory[cpu->pc+1] << 8);
    cpu->pc += 2;
    cpu->ir = raw;

    // Decode instruction fields (hardwired to distribute to components)
    inst.opcode = (raw >> 12) & 0xf;
    inst.rd     = (raw >> 8)  & 0xf;
    inst.rs1    = (raw >> 4)  & 0xf;
    inst.rs2    = raw & 0xf;

    // ID: decoding. The controller looks up the table and sends out the control signal
    // (Opcode → control signal mapping, see the previous article control_logic)

    // EX: ALU execution. Taking ADD as an example, the data path:
    //   Register file[rs1] → MUX → ALU input A
    //   Register file [rs2] → MUX → ALU input B
    //   ALUControl = ADD → addition operation
    uint16_t result = cpu->reg[inst.rs1] + cpu->reg[inst.rs2];

    // WB: Write back, RegWrite=1, MemtoReg=0
    //   ALU result → MUX → register file [rd] data input
    cpu->reg[inst.rd] = result;
}
```

Different instruction types (LDR, STR, branch) only need to change the ALU operation code and control signal, the data path is multiplexed, and the controller is responsible for switching. This is completely consistent with the table lookup logic of `control_logic` mentioned above.

## Trace an instruction

Now let us trace the execution process of `ADD R1, R2, R3` on this micro CPU.

Assuming encoding: `[opcode=0000][rd=0001][rs1=0010][rs2=0011]` → 16-bit instruction word = `0x0123`. R2 = 5, R3 = 3.

**Phase 1: Instruction Fetch (IF)**: PC = 0x0100. Read `0x0123` from memory[0x0100]. PC increments to 0x0102.

**Phase 2: Decoding (ID)**: control_logic(0x0) → `{alu_op=ADD, alu_src=reg, reg_write=1, mem_read=0, mem_write=0, mem_to_reg=0, branch=0}`. All control signals are sent out in parallel, like a symphony orchestra conductor giving gestures to each part at the same time.

**Phase 3: Execution (EX)**: ALU reads R2=5, R3=3 from the register file, executes ADD → result = 8, `zero` flag = 0.

**Phase 4: Memory access (MEM)**: ctrl.mem_read=0, ctrl.mem_write=0 → skip memory. The data memory is completely idle on this instruction, but we cannot omit this stage because all instructions in a multi-cycle processor must go through the same stage.

**Phase 5: Writeback (WB)**: ctrl.reg_write=1, ctrl.mem_to_reg=0 → Write ALU result 8 to R1.

One clock cycle later, R1 = 8, PC = 0x0102, and the next instruction is ready.

In a single-cycle processor, all this is done in one clock cycle. The 7 control signals sent out in parallel by the controller during the decoding stage drive all actions in the 5 stages.

When the instruction is `LDR R3, [R1, #4]` (R1=0x1000, memory[0x1004]=0x2A), the data path is diverted:

- ALU still does addition (0x1000 + 4 = 0x1004). This is because the LDR controller sets `alu_src` to 1 (immediate value) and `alu_op` to ADD. The ALU doesn't care whether you're doing arithmetic or calculating addresses, it just does alu_op on both operands.
- `mem_read=1` → Read 0x2A from memory[0x1004].
- `mem_to_reg=1` → Write back 0x2A to R3 instead of the ALU result 0x1004.

The ALU calculates an "address" rather than a "value" in the LDR instruction. This makes no difference to the ALU, but is the core functionality of the controller: "reuse". The same ALU is multiplexed by different instructions with different control signals to different semantics: arithmetic values, logical values, memory addresses, branch targets.

One clock cycle is one measure. In this section, the conductor (controller) gives a gesture to all musicians (data path), and all musicians move at the same time, including register readout, ALU calculation, and multiplexer selection. Next clock cycle, new bar, new gesture.

## Controller as finite state machine

What we just showed is a **hardwired controller**: the opcode goes in, the control signal comes out, pure combinational logic. This is the defining philosophy of RISC: single-cycle, simple decoding.

But more complex instruction sets (such as x86) cannot do single-cycle with pure hardwiring. A `REP MOVSB` (repeating string transfer) may require hundreds or thousands of micro-operations. At this time the controller must be a finite state machine (FSM).

```
     reset
       ↓
    [IDLE] ──(opcode != HALT)──→ [FETCH]
       ↑                            |
| Decoding completed
       |                            ↓
       |                        [DECODE]
       |                            |
       |                   ┌───────┼────────┐
       |                   ↓       ↓        ↓
       |              [EXEC]   [MEM]    [BRANCH]
       |                   ↓       ↓        ↓
       |              ┌────────────┼────────┘
       |                   ↓
       |              [WRITEBACK]
       |                   ↓
       └───────────────────┘
```After each instruction cycle, this FSM will jump back to the FETCH state to obtain new instructions. For multi-cycle instructions such as multiplication and division, the FSM will stay in the EXEC state for multiple clock cycles, and an internal micro-operation counter controls the execution sequence of each micro-operation.

### Hardwired Controllers: The Price of Speed

**Hardwired Controller**: Opcode → Combinational Logic → Control Signal. Fast (single cycle), small silicon area, but only suitable for simple instruction sets. ARM, MIPS, RISC-V are all hardwired.

But when the instruction set expands to a certain scale, just like the historical baggage of x86, the "simple" of hardwiring will become "impossible." Each additional instruction requires additional logic, and some instructions themselves (such as string operations) cannot be completed in one cycle. This time another solution is needed.

### Microcode Controllers: The Price of Flexibility

**Microcode controller**: operation code → microcode ROM address → read out a series of micro-operations → execute sequentially. Slow (LDR may take 2-3 cycles), large silicon area (tens of KB for microcode ROM), but flexible. Can support extremely complex instructions. The x86 microcode ROM stores thousands of micro-operation sequences in the Intel Core series.

Modern x86 CPUs are actually a **hybrid solution**: simple instructions (ADD, MOV) are directly hardwired to decode, producing 1-4 micro-operations; complex instructions (string operations, floating point transcendental functions, encrypted instructions) go through microcode ROM. This is a design choice of "trading area for compatibility": there are 1500+ instructions in the x86 instruction set, most of which are used only once every ten years, but the microcode ROM must reserve space for them.

The RISC idea is the opposite: don't design instructions that require microcode. If an instruction cannot be hardwired to complete in one (or several) cycles, don't put it in the ISA. This is "trading simplicity for performance and certainty."

## More than half of the silicon area of the controller is interconnect lines

If you thought a controller was "a PLA (Programmable Logic Array) or a microcoded ROM", you've been deceived by the textbook. In a realistic layout, the largest contributor to the silicon area of ​​the controller is the interconnect line.

The control signals must be distributed from the control unit to the entire chip, to the write enable of the register file, to the op selection of the ALU, to the selection lines of each MUX, and to the load enable of the PC. Dozens of control signal lines, each of which must travel from the controller across the entire width of the data path. In a 32-bit CPU, the width of the data path is several hundred microns, and if each control signal line runs through a metal layer across the entire data path, its parasitic capacitance may reach tens of fF. If the buffer driving this line is not large enough, the signal rise time may occupy half a clock cycle, which becomes a new critical path.

This is why in modern physical design, the layout of controllers is not "centralized" but distributed. The decoding logic is chopped up and placed nearby the unit being controlled. The write decoding logic of the register file is placed next to the register file, and the op decoding logic of the ALU is placed next to the ALU. The "generation" and "use" of control signals are as close as possible physically. This isn't a design preference, it's a physical constraint: trace latency and power consumption don't allow you to put all the controls in one place.

That nice centralized `control_logic` module you wrote in RTL no longer exists after synthesis and layout. Its logic is decomposed, smashed, and scattered throughout the chip, physically integrated with the units it controls.

## One clock cycle, nine things

In a single-cycle processor, all operations required for an instruction are completed in one clock cycle:1. PC output address → instruction memory read instruction.
2. The instruction fields are distributed: opcode → controller, register number → register file, immediate → sign extension.
3. The controller sends all control signals according to the operation code.
4. Read the source operand from the register file.
5. ALU performs operations.
6. If it is a Store instruction, the data is written to the data memory.
7. If it is a normal instruction, the result is written back to the register file.
8. If it is a Load instruction, the data memory output is written back to the register file.
9. PC update: non-jump → PC+2; jump → target address.

All of this is accomplished in one clock cycle per instruction.

Single-cycle processors have a clean design. But it has a fatal flaw: the clock frequency is determined by the longest instruction. If Load takes the longest path (PC → Instruction Memory → Register File → ALU → Data Memory → Write Back), then all instructions have to wait for Load to complete. Addition originally only needs to go through half the path, but it still has to wait for that frequency.

This is why no one actually runs products on single-cycle processors. It is the starting point of teaching, not the end of engineering.

## When you write `val = *ptr;`, what is the hardware doing?

Let's look at a concrete example. This C statement:

```c
val = *ptr;
```

ARM assembly (assuming ptr is in R1 and val ends up in R0):

```asm
LDR R0, [R1]
```

In the three-stage pipeline of Cortex-M4 (fetch → decode → execute), the controller issues:

- **Decoding phase**: `MemtoReg = 1` (result from memory), `RegWrite = 1`, `ALUSrc = 1` (immediate value with offset 0).
- **Execution phase**: Calculate `base + offset` (ALUControl = ADD), and send the address to the address input terminal of the data memory.

Finally: the value of R1 is used as the address, and the read memory value is latched into R0.

What you see is "variable assignment". What the hardware sees is: dozens of control signals, hundreds of metal connections, and the switching actions of thousands of MOSFETs, completed within a dozen nanoseconds. PMOS is turned on, NMOS is turned off, and the voltage on the metal line changes within tens of picoseconds.

## Abstraction: a weapon against complexity

Data path and controller, this "pas de deux" is the core duality in computer architecture.

The data path is the "body" and the controller is the "brain".

The body is responsible for transportation, calculation, and storage. The brain is responsible for saying: "Which number to move this cycle, add or subtract, and where to store the result."

This duality was not accidentally designed, but was endogenized by the von Neumann architecture. Store the program in memory → The program becomes data that can be modified → The controller must read instructions from memory instead of running on a fixed wire. Then the controller and data path must be separated. The elegance of this separation lies in:

- You can just change the controller to support more instructions on the same data path.
- You can just change the data path (add floating point unit, add SIMD) and the controller only add a few new control signals.
- You can map the same ISA to different physical implementations. This is the case with ARMv7-M for Cortex-M4 and ARMv7-R for Cortex-R5.

The power of abstraction: Separating the "what" from the "how".

You write `Rte_Read()` in the SWC of AUTOSAR → there are COM stack, PDU Router, CAN Interface, and CAN Driver below. Each layer is a separation of "what" and "how". This design idea is inherited from the control/data path separation inside the CPU, and penetrates upward through the entire software stack.

Abstraction is humanity’s most effective weapon against complexity.

Controller and data path, this pair of "conductor and orchestra", are the core duality in computer architecture. The RTE/SWC separation you saw later in AUTOSAR and the scheduler/task separation you saw in the operating system are all repeats of the same pattern at different scales.

## SummaryToday we did one thing: we understood the "pas de deux" between the data path and the controller. The data path is the body and the controller is the brain.

Key takeaways:
1. The controller is a lookup table of opcodes to control signals: an ADD instruction issues 6-7 control signals that drive all components of the data path (ALU, register file, multiplexer, memory) in parallel.
2. For the same ALU, different instructions are reused with different semantics: arithmetic values, memory addresses, and branch targets. There is no difference for the ALU, but they are core functions for the controller.
3. The controller is physically distributed: The beautiful centralized `control_logic` module in RTL has been smashed and scattered throughout the chip after layout, and wiring delays are not allowed to be concentrated.
